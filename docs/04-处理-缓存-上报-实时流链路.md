# 处理-缓存-上报-实时流链路

## 1. 数据处理链

核心对象：`core/processor/ProcessResult`

在 `BaseCollector.readPoint/readPoints` 中统一完成：

1. 原始值转目标类型（缩放、偏移、布尔/数值转换）。
2. 调用 `DataQualityProcessor` 做质量判定。
3. 产出 `ProcessResult`，并缓存在采集器 `lastProcessResults`。

## 2. 缓存链路

多级缓存核心：

- `MultiLevelCacheManager`
- `LocalCacheManager`
- `RedisCacheManager`

采集结果落缓存入口：

- `core/cache/aspect/CollectorDataCacheAspect`

切面拦截协议采集器读操作后会执行：

1. 写本地/Redis 缓存
2. 调用上报聚合 `CacheReportService.reportPoint(...)`
3. 调用实时流 `TelemetryStreamService.append(...)`
4. 调用历史存储 `HistoryDataService.savePoint(...)`（开启 TDengine 时生效）

## 3. 上报链路

核心类：`core/report/CacheReportService`

主要机制：

1. 将点位变化聚合进 `ShadowManager`（设备影子）。
2. 只 flush 脏设备（dirty）以降低上报开销。
3. 支持分片、限流、重试、异步上报。
4. 通过 `ReportManager` 分发给 `ReportHandler`（MQTT/HTTP/TCP）。
5. 告警可经 `AlertManager -> CacheReportService.reportAlert(...)` 上报。

### 3.1 进入云平台上报链路的条件

采集值不是采集完成后直接上云，而是先进入后处理流水线：

`CollectorDataCacheAspect -> CollectorDataPostProcessor -> ReportTelemetryPostProcessStage -> CacheReportService.reportPoint(...)`

进入属性或事件上报需要同时满足：

1. 全局上报开启：`collector.report.enabled=true`。
2. 当前协议可用：现有周期 flush 由 `CacheReportService.start()` 启动，当前实现只在 MQTT 上报可用时启动，即 `collector.report.mode=mqtt` 且 `collector.report.mqtt.enabled=true`。
3. 设备具备有效云平台身份：`CloudDeviceIdentityService.resolveTarget(localDeviceId)` 必须能解析出 `productKey + deviceName`，否则该设备点位跳过上报。
4. 属性上报点位必须配置 `additionalConfig.reportEnabled=true` 和 `additionalConfig.reportField`；`reportField` 是上报到云平台的属性标识。
5. 事件/告警上报默认开启，可通过 `additionalConfig.eventEnabled=false` 关闭；事件来源包括点位告警规则、`ProcessResult.metadata` 中的事件标记，以及采集失败或质量降级。

设备标识口径：

1. `localDeviceId` 是本系统内部设备标识，也是设备影子的 key、`rawDeviceId`、`shadowKey`。
2. 上报到云平台报文里的设备标识使用云平台身份中的 `deviceName`，同时在 metadata 中带上 `productKey`、`cloudDeviceName`、`rawDeviceId` 和 `gatewayDeviceId`。
3. 网关设备名来自 `collector.report.mqtt.gateway-device-name`，用于网关 Topic、子设备批量包和 metadata。

### 3.2 属性上报频率

属性上报不是每采集一次就立即发送一条，而是“采集结果写入设备影子，设备标记 dirty，定时 flush dirty 设备”。

当前频率规则：

1. 周期 flush 使用 `collector.report.intervalMs`，代码里执行 `Math.max(1000L, intervalMs)`，所以最小周期是 1000 毫秒。
2. 当前 `application.yml` 中 `collector.report.intervalMs=1000`，因此当前属性上报扫描周期是 1 秒。
3. `collector.report.flush-interval` 当前只是配置映射字段，属性 flush 定时任务实际使用的是 `intervalMs`，不是 `flush-interval`。
4. 如果采集频率快于 flush 周期，同一设备在一个周期内多次变化只会上报最新影子快照，不会逐条上报每次采样。
5. 如果采集频率慢于 flush 周期，只有新采集结果把设备标记为 dirty 后，下一次周期 flush 才会上报。
6. 如果没有 dirty 设备，`flushDirtyDevices()` 直接返回，不产生空上报。

因此，在当前配置下：有新 dirty 数据时，属性上报通常是“最多每 1 秒发送一次最新快照”；没有新 dirty 数据时不发送。

### 3.3 dirty 影子与 flush 执行链路

属性值进入上报链路后的主流程：

1. `ReportTelemetryPostProcessStage.process(...)` 调用 `CacheReportService.reportPoint(...)`。
2. `CacheReportService.reportPoint(...)` 解析设备云平台身份，并把 `localDeviceId -> gatewayDeviceId`、`localDeviceId -> cloudIdentity` 写入本地映射。
3. `ShadowManager.apply(...)` 使用点位 `reportField` 更新设备影子的 reported 值；当点位 `reportEnabled=true` 且 `reportField` 存在时，执行 `markDirty(localDeviceId)`。
4. `markDirty(...)` 会把 dirty 设备写入内存集合；开启影子 Redis 持久化时，还会写入 Redis dirty set，用于重启或多实例恢复。
5. `CacheReportService.flushDirtyDevices()` 按周期读取 dirty 设备集合，优先尝试网关批量包；不满足批量条件的设备走单设备 `flushDevice(...)`。
6. `flushDevice(...)` 构建设备影子快照，按 `collector.report.maxPropertiesPerMessage` 和 `collector.report.maxPayloadBytes` 分片，再调用 `ReportManager.reportAsync(...)`。
7. `ReportManager.reportAsync(...)` 投递到 `reportExecutor`，再由对应 `ReportHandler` 执行 MQTT/HTTP/TCP 发送。
8. 全部分片成功后，`ShadowManager.markReportedWindowCommitted(...)` 提交窗口并清理 dirty；部分失败或重试未耗尽时保留 dirty，后续周期或重试继续补发。

并发保护：

1. `CacheReportService` 使用 `flushingDevices` 避免同一 JVM 内同一设备并发 flush。
2. 开启 Redis 分布式锁时，`FlushSession` 会持有设备级 flush 锁，避免多实例同时 flush 同一设备。
3. 已经在 flush 中的设备会跳过重复 flush，由当前 flush、重试任务或后续周期接管。

### 3.4 变化触发与事件触发

变化触发用于在属性变化超过阈值时尝试立即 flush，但仍受最小间隔限制：

1. 点位配置 `additionalConfig.changeThreshold` 后，`ShadowManager.shouldTriggerChange(...)` 会比较当前值和上次已上报值。
2. 差值达到阈值时触发 `CacheReportService.triggerImmediateFlush(...)`。
3. 立即 flush 受 `additionalConfig.changeMinIntervalMs` 限制；未配置时使用全局 `collector.report.minReportIntervalMs`，默认 2000 毫秒。
4. 当前实现中，变化触发只是“尝试提前 flush”，不是绕过所有限频直接发送。

事件/告警上报走高优先级分发，不等待属性周期 flush：

1. `ShadowManager.evaluateEvent(...)` 基于点位告警规则、`ProcessResult.metadata` 事件标记、采集失败或质量降级生成事件。
2. 事件最小间隔使用 `additionalConfig.eventMinIntervalMs`；未配置时使用全局 `collector.report.eventMinIntervalMs`，默认 5000 毫秒。
3. `CacheReportService.dispatchEvent(...)` 构造 `thing.event.post`，通过 `dispatch(..., highPriority=true, tracker=null)` 立即投递。
4. `AlertManager -> CacheReportService.reportAlert(...)` 也是事件上报，构造告警事件后直接高优先级发送。

### 3.5 网关批量包、ACK 与重试

网关批量包：

1. 周期 flush 中如果同一网关下有多个 dirty 子设备，会先尝试 `tryFlushGatewayBatches(...)`。
2. 批量策略来自 `collector.report.cloud.batch.*`，当前配置启用批量包，限制为最多 50 个设备、500 个属性、128KB 载荷。
3. `max-delay-ms` 是云平台批量策略字段；当前 dirty 扫描节奏仍由 `collector.report.intervalMs` 决定。

ACK 与影子提交：

1. 当前配置为 `collector.report.cloud.ack.mode=async`、`timeout-ms=5000`、`max-pending=10000`、`commit-on=publish-success`。
2. 默认异步 ACK 模式下，MQTT publish 成功后 `ReportResult` 即为成功，影子 reported 窗口会按发送成功提交；平台业务 ACK 在后台闭环，结果 metadata 会带 `ackPending`、`ackMode`、`ackTimeoutMs` 等字段。
3. 如果改成同步 ACK 模式，`MqttReportHandler` 会等待平台业务 ACK；ACK 超时或业务返回非 0 会把 `ReportResult` 标记失败，dirty 不会提交。
4. `commit-on=ack-success` 当前只是预留枚举和元数据口径，不是独立的影子提交策略；实际提交仍看 `ReportResult.isSuccess()`。

失败与重试：

1. `ReportManager.reportAsync(...)` 返回失败、MQTT 离线 deferred、网关限流失败或线程池拒绝时，`CacheReportService` 会根据结果判断是否重试。
2. 重试次数使用 `collector.report.retry-times`，当前为 3。
3. 重试退避使用 `collector.report.retryBackoffMs` 和 `collector.report.maxRetryBackoffMs`，默认 1000 毫秒到 10000 毫秒，并带轻微抖动。
4. 单设备并发 pending 分片受 `collector.report.maxPendingChunksPerDevice` 限制，避免某个设备失败后无限堆积。

补充说明：

- 上下行消息 method、MQTT/TCP 报文结构和当前实现状态见 [上下行消息协议与实现状态](./11-上下行消息协议与实现状态.md)。
- 当前 MQTT 上报通道已支持 ACK 接收；平台 MQTT 下行属性设置、服务调用和配置推送已接入，OTA 升级仍未实际执行。

## 4. Redis Stream 实时流

核心类：

- `TelemetryStreamProperties`
- `StreamRetentionMode`
- `TelemetryStreamServiceImpl`
- `TelemetryStreamRecordBuilder`

### 4.1 COUNT 模式

- 写入时使用 `XADD MAXLEN` 控制保留条数。
- `approximateTrim=true` 时采用近似裁剪，性能更高。

### 4.2 TIME 模式

- 每条记录带事件时间（`eventTs`）。
- 通过定时任务执行 `XTRIM MINID`，保留最近 N 秒。
- 通过 `trimTaskEnabled`/`trimIntervalMs` 控制定时裁剪。

### 4.3 配置示例

```yaml
spring:
  data:
    redis:
      stream:
        enabled: true
        key: collector:telemetry:stream
        retention-mode: COUNT
        max-length: 200
        max-seconds: 60
        approximate-trim: true
        trim-task-enabled: true
        trim-interval-ms: 5000
```

## 5. 端到端数据时序

1. 调度触发采集。
2. 协议采集器读点位并生成 `ProcessResult`。
3. 缓存切面写缓存。
4. 同步写 Redis Stream（实时消费）。
5. 可选写入 TDengine 历史存储（开关控制）。
6. 聚合到影子并按策略上报云端。

## 6. 验证方式

### 6.1 COUNT

1. `retention-mode=COUNT`，`max-length=200`。
2. 连续采集后执行 `XLEN collector:telemetry:stream`。
3. 长时间运行后长度应稳定在 200 左右（近似裁剪可能略浮动）。

### 6.2 TIME

1. `retention-mode=TIME`，`max-seconds=60`，开启 trim 任务。
2. 连续采集 2~3 分钟。
3. 查看流中最早记录时间，窗口应约 60 秒。

### 6.3 兼容性验证

1. 关闭 `spring.data.redis.stream.enabled`。
2. 验证采集、缓存、上报流程仍正常（说明新增功能不破坏主链路）。

## 7. 下行反控边界

当前协议采集器普遍已经实现写入入口，统一由 `CollectionManager.writePoint(...)`、`CollectionManager.writePoints(...)` 和 `CollectionManager.executeCommand(...)` 调度到具体协议。

已新增从云端 MQTT 下行消息到上述统一入口的路由层。因此：

- `thing.property.set` 已写入影子 desired，并调用协议写入。
- `thing.service.invoke` 已调用协议命令入口。
- `thing.config.push` 已接入配置治理，支持 `device/points/connection/collection/all`，并复用 `ConfigSyncService -> ConfigManager -> CollectionScheduler` 触发刷新与运行中设备重载。
- `thing.ota.upgrade` 暂未接入 OTA 流程，仅识别并返回未实现。

## 8. 架构整改后的数据链路契约

详细任务见《16-P0_P1实施任务单与改造方案》的 `PIPE-P1-01`、`EXEC-P1-01` 和 `ALARM-P1-01`。

### 8.1 不可变采集快照

采集线程必须在同步读取完成时生成不可变样本，完整携带设备 ID、点位 ID、原始值、处理值、质量、采集时间、设备代次和元数据。异步后处理不得重新查询 collector 中的“最新结果”拼装本次数据。

轮询和订阅推送统一进入 `TelemetryIngressService`，但不得改变协议解析、批量读取和寄存器地址规则。

### 8.2 通道隔离

最新值缓存、Redis Stream、TDengine 历史、告警和云端上报分别使用有界执行资源。任何一个下游故障都不能占满整条后处理链并阻塞现场采集。

投递语义固定为：

1. 最新值缓存保留最新结果，允许同点位合并。
2. Redis Stream 按配置保留实时流，丢弃必须有指标。
3. TDengine 历史采用批量写入和至少一次重试。
4. 告警状态转换不可静默丢失。
5. 云上报使用持久化 Outbox，按消息 ID 和影子版本幂等。

### 8.3 告警单一出口

告警采用 `NORMAL/PENDING/ACTIVE/ACKED/RECOVERED` 状态机。只有状态转换生成事件，同一告警不得同时通过 `AlertManager` 直报和影子事件重复上报。
