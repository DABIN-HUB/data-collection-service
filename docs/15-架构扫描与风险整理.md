# 架构扫描与风险整理

本文档记录对当前项目的架构扫描结果、风险点、优化方向、可复用能力和适合引入或强化的设计模式。

## 1. 总体架构

当前系统是一个配置驱动的多协议工业数据采集服务，主链路如下：

```text
HTTP API
  -> CollectionService / ConfigController / DataController / MonitorController
  -> ConfigManager 读取设备、点位、连接配置
  -> CollectionScheduler 按时间片调度设备点位
  -> CollectionManager 分发读、写、订阅和命令
  -> CollectorFactory 创建协议采集器
  -> BaseCollector / ConnectionBackedCollector 执行统一采集模板
  -> CollectorDataCacheAspect / TelemetryIngressService
  -> CollectorDataPostProcessor
  -> 本地缓存 / Redis / Redis Stream / TDengine / 设备影子 / MQTT-HTTP-TCP 上报
```

## 2. 核心模块职责

- `api`：HTTP 管理入口，覆盖设备控制、数据查询、配置治理、监控、协议能力查询。
- `core/config`：设备、点位、连接配置加载、缓存、刷新、校验和配置变更事件。
- `core/collector/scheduler`：时间片调度、批次规划、设备启动停止、采集任务分发。
- `core/collector/manager`：采集器注册、连接管理入口、读写订阅命令能力分发。
- `core/collector/protocol`：各协议采集器实现，统一继承 `BaseCollector` 或 `ConnectionBackedCollector`。
- `core/connection`：连接工厂、连接适配器、连接状态和心跳管理。
- `core/processor`：原始值转换、质量判断、`ProcessResult` 组织。
- `core/cache`：多级缓存、采集后处理、Redis Stream 实时流。
- `core/report`：设备影子、聚合上报、MQTT/HTTP/TCP 上报处理。
- `storage`：TDengine 历史数据写入和查询。
- `monitor`：健康、性能、异常和系统资源指标。

## 3. 当前已使用的设计模式

- 模板方法：`BaseCollector` 固定连接、读写、转换、质量处理流程，下沉 `doReadPoint`、`doWritePoint` 等协议差异点。
- 适配器：`ConnectionAdapter` 屏蔽不同协议连接实现。
- 工厂/注册表：`CollectorFactory`、`ConnectionFactory`、`ReportManager` 根据协议或上报类型创建/选择实现。
- 策略：`ReportHandler`、`ProtocolBatchStrategy` 承载不同上报协议和不同协议批次策略。
- 观察者/事件：配置更新事件、连接监听器、采集切面后处理。
- 门面：`CollectionService` 和控制器对外暴露较粗粒度操作。
- 管道：采集结果进入缓存、实时流、历史库、上报链路。

## 4. 可能出问题的位置

| 优先级 | 位置 | 风险 |
| --- | --- | --- |
| P0 | `CollectorDataPostProcessor.saveBatchAsync` | 批量采集时缓存值可能正常，但上报传入 `null ProcessResult`，导致上报跳过。 |
| P0 | `TelemetryStreamServiceImpl.trimByTimeRetention` | `@Scheduled` 使用的配置 key 与 `TelemetryStreamProperties` 前缀不一致，裁剪间隔配置可能不生效。 |
| P0 | `BaseCollector.executeCommand` | `slaveId` 直接 cast 为 `Integer`，JSON 参数为 `Long` 或 `String` 时会失败。 |
| P0 | `BaseCollector.disconnect` | 退订失败可能阻断实际断连，导致连接资源残留。 |
| P1 | `BaseCollector` 订阅状态 | `subscribedPointMap` 和 `subscribedPointsSet` 同时存在，状态统计可能不准确。 |
| P1 | `CollectionScheduler` | 已清理旧批次规划私有方法，后续重点关注 `DeviceBatchPlanner` 的协议策略扩展。 |
| P1 | `DeviceBatchPlanner` | 通用地址数字排序适合 Modbus 类地址，但不一定适合 OPC UA、S7、EtherNet/IP 等符号点位。 |
| P1 | `ConfigSyncService` | 已改为 `RestTemplateBuilder` 并补周期同步；后续可继续补重试、认证拦截器和失败退避。 |
| P2 | `MultiLevelCacheManager` 和部分上报 handler | `MultiLevelCacheManager` 已切到统一 `ioIntensiveExecutor`；部分上报 handler 后续仍可继续收口。 |
| P2 | `TimeSeriesService` | 历史写入缺少独立有界队列和背压，TDengine 慢时可能拖累采集后处理。 |
| P2 | 文档/注释 | 部分历史文档和注释存在编码乱码，影响交接和排障。 |

## 5. 可优化方向

1. 抽取 `ProtocolDescriptor`，统一协议别名、采集器、连接适配器、批次策略、字段 schema 和能力声明。
2. 把采集后处理拆成显式 pipeline stage，例如 cache、stream、history、report，每个 stage 独立失败隔离和指标记录。
3. 对协议批次规划继续下沉策略，避免所有协议共用“提取第一个数字排序”的地址规则。
4. 清理 `CollectionScheduler` 中已被 `DeviceBatchPlanner` 替代的旧批次规划代码。
5. 统一线程池来源，减少自建 executor，便于监控、限流和优雅停机。
6. 为设备生命周期和连接生命周期增加状态机，明确 `STARTING`、`RUNNING`、`RECONNECTING`、`STOPPING`、`ERROR` 等状态迁移。
7. 为历史写入和上报增加有界队列、重试退避、丢弃策略和积压指标。
8. 统一 UTF-8 编码，修复已乱码文档和注释。

## 6. 可共用能力

- PLC4X 协议族可共用连接串构造、认证参数、读写异常归一化、批量读计划和订阅诊断能力。
- 推送型协议可统一通过 `TelemetryIngressService` 进入 `ProcessResult -> 缓存 -> Stream -> 历史 -> 上报` 链路。
- 协议地址解析可共用解析结果模型、校验错误模型和字段文档生成入口。
- 上报 handler 可共用生命周期、重试、限流、指标和错误归一化逻辑。
- 配置治理可共用协议字段 schema、连接校验和接口文档生成逻辑。
- Redis Stream、历史库、设备影子可共用 `ProcessResult` 规范化入口，避免各链路重复判断值类型。

## 7. 建议强化的设计模式

- 策略模式：协议批次规划、地址排序、保留策略、上报策略继续策略化。
- 注册表模式：用协议描述符注册表替代多个工厂和 schema 中重复维护的 switch/map。
- 责任链模式：采集后处理拆成 cache、stream、history、report stage。
- 命令模式：协议命令执行参数解析、校验和执行器按命令拆分。
- 状态机：设备生命周期、连接生命周期、重连流程。
- 熔断和舱壁：按设备或协议隔离连续失败，避免单设备拖垮公共线程池。
- 仓储模式：设备影子持久化、历史存储、配置快照访问继续抽象边界。

## 8. 收口优先级

### 8.1 P0 正确性

1. 修复批量采集上报传值，保证缓存、Stream、历史和上报使用同一个规范化结果。
2. 修复 Redis Stream TIME 裁剪定时配置 key。
3. 修复命令参数类型转换，兼容 `Number` 和数字字符串。
4. 修复断连流程，退订失败不阻断实际断开连接。

### 8.2 P1 可维护性

1. 清理调度器旧批次规划代码。
2. 抽取协议描述符注册表。
3. 注入式管理 `RestTemplate` 或切换为统一 HTTP client。
4. 统一文档和源码编码。

### 8.3 P2 演进能力

1. 引入采集后处理 pipeline。
2. 引入设备和连接状态机。
3. 引入历史写入和上报背压。
4. 引入按设备/协议维度的熔断、限流和隔离。

## 9. 整体工作流程与协议工作流程

### 9.1 统一端到端工作流程

当前工程的端到端流程分为启动、采集、计算、后处理、上报和告警六段：

1. 启动阶段：`CollectionService` 或控制器接收启动请求，`CollectionScheduler.startDevice(...)` 从 `ConfigManager` 读取设备、点位、连接配置。
2. 注册阶段：`CollectionManager.registerDevice(...)` 调用 `CollectorFactory` 按协议创建采集器，并通过 `ConnectionFactory` 创建连接适配器。
3. 调度阶段：`DeviceBatchPlanner` 按协议、数据类型、地址和历史性能生成批次，`CollectionScheduler` 把批次分配到时间片。
4. 数据采集：拉取型协议由调度器调用 `collectionManager.readPoints(...)`，再进入各协议 `doReadPoint/doReadPoints`；推送型协议由协议回调调用 `BaseCollector.ingestPushedValue(...)`。
5. 数据计算：`BaseCollector` 统一执行原始值转换、缩放、偏移、布尔转换、范围校验、告警规则检查，并生成 `ProcessResult`。
6. 数据后处理：拉取型协议通过 `CollectorDataCacheAspect` 进入 `CollectorDataPostProcessor`；推送型协议通过 `TelemetryIngressService` 进入同一个后处理组件。
7. 数据落地：后处理按点位 `needCache()` 判断是否继续执行，写入多级缓存、Redis Stream，并在启用历史存储时写入 TDengine。
8. 数据上报：`CacheReportService.reportPoint(...)` 将结果写入 `ShadowManager`，脏设备按周期或变化触发 flush，再由 `ReportManager` 分发到 MQTT / HTTP / TCP 等上报处理器。
9. 告警事件：`DataQualityProcessor` 在质量异常或告警规则命中时写入事件元数据，并通知 `AlertManager`；`ShadowManager` 也会基于 `ProcessResult.metadata` 或点位事件配置生成事件上报。

当前需要特别注意：

- 拉取链路和推送链路最终共用 `CollectorDataPostProcessor`，所以缓存、Stream、历史和上报的可靠性问题会同时影响所有协议。
- `CollectorDataPostProcessor` 目前以 `point.needCache()` 作为后处理入口条件；未启用缓存的点位不会进入当前缓存、Stream、历史和属性上报链路。
- 属性上报走设备影子聚合，告警事件走高优先级事件上报，两者不是同一条消息，但都依赖上报配置有效。
- `OPC_UA`、`OPCUA`、`OPC_UA_PLC4X`、`OPCUA_PLC4X` 当前都由 `Plc4xOpcUaCollector` 承接；旧的 Milo `OpcUaCollector` 仍在代码中，但不是当前工厂默认路由。

| `IEC61850` | `Iec61850Collector` 通过 IEC61850 模型读取 Logical Device、Logical Node、Data Attribute；报告回调由 `AbstractIec61850Collector` 分发。 | 模型节点和 BDA 值转换后进入 `BaseCollector`；报告值通过 `handleReportValue(...) -> ingestPushedValue(...)` 进入统一质量处理。 | 读取和报告回调共用后处理，上报前进入设备影子。 | 报告值、质量异常和点位告警规则均可触发事件。 | 模型路径、FC、报告控制块和数据集配置是主要联调风险；复杂结构值需要明确字段映射。 |
| `MQTT` / `MQTT_SSL` | `MqttCollector` 订阅点位 topic，消息回调解析 payload 并更新 latest value；读操作返回最近一次值，写操作发布到写 topic。 | 按 topic、JSON path 或 payload 配置提取点位值，推送值走 `ingestPushedValue(...)` 的统一转换和质量处理。 | MQTT 入站数据通过 `TelemetryIngressService` 进入后处理；属性上报仍由本系统的 `ReportManager` 发往配置的上报目标。 | 消息值进入统一告警规则；事件上报和属性上报由后处理链控制。 | 这是典型推送型协议，读值依赖是否已有消息；topic、payload schema 和 retained/离线消息需要约定。 |
| `SNMP` / `SNMP_V1` / `SNMP_V2C` / `SNMP_V3` | `SnmpCollector` 使用 GET/批量 GET 读取 OID，SET 写入；Trap/Inform 监听器将绑定 OID 映射到点位。 | SNMP 变量按 OID 和数据类型转换后进入统一质量处理；Trap/Inform 通过 `ingestPushedValue(...)` 进入推送链路。 | 轮询和 Trap 数据都进入统一后处理和上报链路。 | OID 值异常、范围异常和规则命中会触发告警；Trap 映射到点位后也可触发事件。 | v3 认证、隐私协议、Trap 监听端口和 OID 到点位映射是主要风险。 |
| `COAP` / `COAP_SSL` | `CoapCollector` 通过 CoAP GET 读取资源，POST/PUT/DELETE 写入；开启 observe 时通过 Observe 回调接收变化。 | 响应 payload 按点位配置解析，拉取和 Observe 值都走统一转换、质量和告警处理。 | 拉取和 Observe 回调共用后处理链路。 | 质量异常和告警规则统一触发事件。 | Observe 依赖服务端支持；payload schema、confirmable、重传和 SSL/coaps 参数需要联调。 |
| `HTTP` / `HTTPS` | `HttpCollector` 通过 HTTP 请求读取接口响应，写入时发送写动作请求；订阅当前是本地登记，不存在真实服务端推送。 | 响应 JSON 或文本按点位配置提取字段，再进入统一转换和质量处理。 | 拉取结果进入统一后处理和设备影子上报。 | 告警规则和质量异常按统一机制触发。 | HTTP 适合轮询接口；接口鉴权、响应 schema、分页/批量协议和错误码归一化需要补强。 |
| `WEBSOCKET` / `WEBSOCKET_SSL` | `WebSocketCollector` 建立长连接，读操作可返回缓存值或发送读取请求；消息回调按点位映射处理；订阅/退订通过 JSON 消息下发。 | WebSocket 消息 payload 按点位绑定解析后，经 `ingestPushedValue(...)` 统一转换、质量和告警处理。 | 推送消息和主动读取结果最终进入统一后处理。 | 质量异常、告警规则和事件配置统一触发。 | 长连接重连、消息关联、订阅确认和乱序消息是主要风险。 |
| `CUSTOM_TCP` / `CUSTOM_UDP` | `CustomProtocolCollector` 当前是占位实现，连接只记录日志，读写订阅和命令均抛出不支持。 | 尚未实现协议帧解析、字段映射、校验和数据转换，只能依赖未来自定义解析器。 | 当前没有真实采集结果进入上报链路。 | 当前没有真实点位值，因此不会形成有效点位告警。 | 不能作为生产采集协议使用；需要先补协议描述、帧编解码、地址模型、读写命令和回调入口。 |

### 9.3 协议链路共用点

所有已落地协议都应尽量复用以下能力：

1. 采集入口复用 `BaseCollector` 模板方法，协议只实现连接、原始读写、订阅和命令差异。
2. 数据计算复用 `DataQualityProcessor` 和 `ProcessResult`，避免协议内重复实现缩放、范围和告警判断。
3. 推送型协议复用 `ingestPushedValue(...)`，确保订阅回调与轮询采集使用同一条缓存、Stream、历史和上报链。
4. 上报复用 `CacheReportService`、`ShadowManager`、`ReportManager`，协议层不直接关心 MQTT / HTTP / TCP 上报细节。
5. 告警复用点位 `alarmRule`、`AlertManager` 和影子事件逻辑，协议层只负责把值准确转成点位值。

### 9.4 协议链路主要风险

1. `CUSTOM_TCP` / `CUSTOM_UDP` 仍是占位协议，不能按“已支持真实采集”对外承诺。
2. `OPC_UA` 名称已经路由到 PLC4X 实现，迁移期需要在配置、文档和联调记录中避免新旧实现混淆。
3. 推送型协议如果点位未开启缓存，当前不会进入后处理链路，可能导致“能收到消息但不上报/不入流”。
4. 复杂结构值是多个协议的共性风险，包括 EtherNet/IP UDT、S7 数组/结构、IEC61850 结构节点、OPC UA Variant 和 MQTT/HTTP JSON 深层字段。
5. 协议订阅能力不一致：Modbus 和 HTTP 当前不是实时订阅；S7、ADS、OPC UA、CoAP、MQTT、WebSocket、SNMP Trap、IEC104 自发、IEC61850 Report 才有不同程度的推送入口。
6. 告警事件存在两条出口：`AlertManager.reportAlert` 和 `ShadowManager.dispatchEvent`，后续要继续确认是否需要去重、合并或按事件类型区分目标 topic。
