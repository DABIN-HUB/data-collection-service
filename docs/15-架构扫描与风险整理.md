# 架构扫描与风险整理

本文档记录对当前项目的架构扫描结果、风险点、优化方向、可复用能力和适合引入或强化的设计模式。

## 1. 总体架构

当前系统是一个配置驱动的多协议工业数据采集服务，主链路如下：

```text
HTTP API
  -> CollectionService / ConfigController / DataController / MonitorController
  -> ConfigManager 读取设备、点位、连接配置
  -> CollectionScheduler 按时间片调度设备点位
  -> CollectionManager 分发读、写、订阅和命令
  -> CollectorFactory 创建协议采集器
  -> BaseCollector / ConnectionBackedCollector 执行统一采集模板
  -> CollectorDataCacheAspect / TelemetryIngressService
  -> CollectorDataPostProcessor
  -> 本地缓存 / Redis / Redis Stream / TDengine / 设备影子 / MQTT-HTTP-TCP 上报
```

## 2. 核心模块职责

- `api`：HTTP 管理入口，覆盖设备控制、数据查询、配置治理、监控、协议能力查询。
- `core/config`：设备、点位、连接配置加载、缓存、刷新、校验和配置变更事件。
- `core/collector/scheduler`：时间片调度、批次规划、设备启动停止、采集任务分发。
- `core/collector/manager`：采集器注册、连接管理入口、读写订阅命令能力分发。
- `core/collector/protocol`：各协议采集器实现，统一继承 `BaseCollector` 或 `ConnectionBackedCollector`。
- `core/connection`：连接工厂、连接适配器、连接状态和心跳管理。
- `core/processor`：原始值转换、质量判断、`ProcessResult` 组织。
- `core/cache`：多级缓存、采集后处理、Redis Stream 实时流。
- `core/report`：设备影子、聚合上报、MQTT/HTTP/TCP 上报处理。
- `storage`：TDengine 历史数据写入和查询。
- `monitor`：健康、性能、异常和系统资源指标。

## 3. 当前已使用的设计模式

- 模板方法：`BaseCollector` 固定连接、读写、转换、质量处理流程，下沉 `doReadPoint`、`doWritePoint` 等协议差异点。
- 适配器：`ConnectionAdapter` 屏蔽不同协议连接实现。
- 工厂/注册表：`CollectorFactory`、`ConnectionFactory`、`ReportManager` 根据协议或上报类型创建/选择实现。
- 策略：`ReportHandler`、`ProtocolBatchStrategy` 承载不同上报协议和不同协议批次策略。
- 观察者/事件：配置更新事件、连接监听器、采集切面后处理。
- 门面：`CollectionService` 和控制器对外暴露较粗粒度操作。
- 管道：采集结果进入缓存、实时流、历史库、上报链路。

## 4. 可能出问题的位置

| 优先级 | 位置 | 风险 |
| --- | --- | --- |
| P0 | `CollectorDataPostProcessor.saveBatchAsync` | 批量采集时缓存值可能正常，但上报传入 `null ProcessResult`，导致上报跳过。 |
| P0 | `TelemetryStreamServiceImpl.trimByTimeRetention` | `@Scheduled` 使用的配置 key 与 `TelemetryStreamProperties` 前缀不一致，裁剪间隔配置可能不生效。 |
| P0 | `BaseCollector.executeCommand` | `slaveId` 直接 cast 为 `Integer`，JSON 参数为 `Long` 或 `String` 时会失败。 |
| P0 | `BaseCollector.disconnect` | 退订失败可能阻断实际断连，导致连接资源残留。 |
| P1 | `BaseCollector` 订阅状态 | `subscribedPointMap` 和 `subscribedPointsSet` 同时存在，状态统计可能不准确。 |
| P1 | `CollectionScheduler` | 旧批次规划私有方法仍保留，实际已切到 `DeviceBatchPlanner`，后续容易改错位置。 |
| P1 | `DeviceBatchPlanner` | 通用地址数字排序适合 Modbus 类地址，但不一定适合 OPC UA、S7、EtherNet/IP 等符号点位。 |
| P1 | `ConfigSyncService` | 直接 new `RestTemplate`，超时、重试、认证和拦截器不统一；同步任务语义需要继续收口。 |
| P2 | `MultiLevelCacheManager` 和部分上报 handler | 自建线程池仍然存在，线程池治理、监控和停机行为不完全统一。 |
| P2 | `TimeSeriesService` | 历史写入缺少独立有界队列和背压，TDengine 慢时可能拖累采集后处理。 |
| P2 | 文档/注释 | 部分历史文档和注释存在编码乱码，影响交接和排障。 |

## 5. 可优化方向

1. 抽取 `ProtocolDescriptor`，统一协议别名、采集器、连接适配器、批次策略、字段 schema 和能力声明。
2. 把采集后处理拆成显式 pipeline stage，例如 cache、stream、history、report，每个 stage 独立失败隔离和指标记录。
3. 对协议批次规划继续下沉策略，避免所有协议共用“提取第一个数字排序”的地址规则。
4. 清理 `CollectionScheduler` 中已被 `DeviceBatchPlanner` 替代的旧批次规划代码。
5. 统一线程池来源，减少自建 executor，便于监控、限流和优雅停机。
6. 为设备生命周期和连接生命周期增加状态机，明确 `STARTING`、`RUNNING`、`RECONNECTING`、`STOPPING`、`ERROR` 等状态迁移。
7. 为历史写入和上报增加有界队列、重试退避、丢弃策略和积压指标。
8. 统一 UTF-8 编码，修复已乱码文档和注释。

## 6. 可共用能力

- PLC4X 协议族可共用连接串构造、认证参数、读写异常归一化、批量读计划和订阅诊断能力。
- 推送型协议可统一通过 `TelemetryIngressService` 进入 `ProcessResult -> 缓存 -> Stream -> 历史 -> 上报` 链路。
- 协议地址解析可共用解析结果模型、校验错误模型和字段文档生成入口。
- 上报 handler 可共用生命周期、重试、限流、指标和错误归一化逻辑。
- 配置治理可共用协议字段 schema、连接校验和接口文档生成逻辑。
- Redis Stream、历史库、设备影子可共用 `ProcessResult` 规范化入口，避免各链路重复判断值类型。

## 7. 建议强化的设计模式

- 策略模式：协议批次规划、地址排序、保留策略、上报策略继续策略化。
- 注册表模式：用协议描述符注册表替代多个工厂和 schema 中重复维护的 switch/map。
- 责任链模式：采集后处理拆成 cache、stream、history、report stage。
- 命令模式：协议命令执行参数解析、校验和执行器按命令拆分。
- 状态机：设备生命周期、连接生命周期、重连流程。
- 熔断和舱壁：按设备或协议隔离连续失败，避免单设备拖垮公共线程池。
- 仓储模式：设备影子持久化、历史存储、配置快照访问继续抽象边界。

## 8. 收口优先级

### 8.1 P0 正确性

1. 修复批量采集上报传值，保证缓存、Stream、历史和上报使用同一个规范化结果。
2. 修复 Redis Stream TIME 裁剪定时配置 key。
3. 修复命令参数类型转换，兼容 `Number` 和数字字符串。
4. 修复断连流程，退订失败不阻断实际断开连接。

### 8.2 P1 可维护性

1. 清理调度器旧批次规划代码。
2. 抽取协议描述符注册表。
3. 注入式管理 `RestTemplate` 或切换为统一 HTTP client。
4. 统一文档和源码编码。

### 8.3 P2 演进能力

1. 引入采集后处理 pipeline。
2. 引入设备和连接状态机。
3. 引入历史写入和上报背压。
4. 引入按设备/协议维度的熔断、限流和隔离。
