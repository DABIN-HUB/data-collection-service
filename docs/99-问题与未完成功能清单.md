# 问题与未完成功能清单（截至 2026-07-14）

## 1. 文档说明

这份清单基于当前仓库代码重新梳理，目标不是回顾历史，而是明确三件事：

1. 旧文档里哪些“未完成”其实已经完成。
2. 当前版本真正还没做完的功能有哪些。
3. 如果目标是按当前配置方式准备开源，应该先处理哪些问题。

因此，本文档分为三层：

- 已完成但旧文档未同步的内容
- 当前仍未完成的功能与实现边界
- 面向开源准备的优先级清单（`P0 / P1 / P2`）

在其他文档尚未完全修正前，可以把本文档视为当前版本的较高优先级事实清单。

## 2. 已完成但旧文档未同步的内容

以下内容在当前代码中已经落地，不能再归类为“未实现”。

### 2.1 MQTT 下行里的属性设置、服务调用、配置推送已打通

当前 `MqttDownlinkService` 已经支持：

- `thing.property.set`
- `thing.service.invoke`
- `thing.config.push`

现状说明：

- `thing.property.set` 已能解析下行点位并路由到 `CollectionManager.writePoints(...)`
- `thing.service.invoke` 已能路由到 `CollectionManager.executeCommand(...)`
- `thing.config.push` 已能复用 `ConfigSyncService -> ConfigManager -> CollectionScheduler` 触发配置刷新与运行中设备重载
- 对应测试 `MqttDownlinkServiceTest` 已覆盖成功路径

结论：

- MQTT 下行链路不是“完全未实现”
- 真正还没完成的是 OTA 升级、OTA 进度主流程和服务名映射深化，见第 3 节

### 2.2 设备影子的 Redis CAS、版本冲突处理、TTL 与历史能力已落地

当前 `ShadowManager` 已具备：

- 基于 Lua 的 Redis CAS 更新
- 本地版本与远端版本冲突检测
- 自动合并与重试策略
- 影子 TTL 管理
- 脏设备集合维护
- 历史版本留存与过期时间控制

对应配置已存在于 `ReportProperties.Shadow` 中，例如：

- `casEnabled`
- `autoMergeEnabled`
- `ttlSeconds`
- `historyEnabled`
- `historyTtlSeconds`

结论：

- 旧文档里“设备影子 Redis CAS / 一致性 / 过期清理暂未实现”的说法已经过时
- 更准确的表述应是：设备影子已经具备 Redis CAS 与版本治理基础能力

### 2.3 BACnet/IP 已不是占位能力

当前 `BacnetIpCollector` 已具备较完整的数据面能力，包括：

- 读点
- 批量读点
- 写点
- 批量写点
- COV 订阅
- `who_is`
- `read_property`
- `read_property_multiple`
- `discover_objects`
- `device_info`
- `diagnostic / status`

仓库内也已经存在多组 `BACNET_IP` 相关测试，不应再把它归类为“只有框架没有真实实现”。

结论：

- `BACNET_IP` 已属于真实可用能力范围
- 真正仍应谨慎表述的是 `BACNET_SC`，见第 4.1 节

### 2.4 BACnet COV 重连后恢复订阅的基础闭环已存在

当前 `BacnetIpCollector` 已具备以下机制：

- 连接适配器重连后回调采集器
- 根据 `resubscribeOnReconnect` 决定是否自动恢复订阅
- 重连后重新执行 `doSubscribe(...)`

结论：

- `docs/protocols/BACNET_IP.md` 中“未实现重连并恢复 COV 订阅闭环”的表述已经落后于代码
- 更准确的说法应是：基础重连恢复能力已存在，但现场稳定性仍需按设备类型继续验证

## 3. 当前仍未完成的核心能力

这部分才是当前版本真正还没做完、或者只做到一半的内容。

### 3.1 MQTT 配置推送已实现最小闭环，OTA 升级仍未实现

当前 `MqttDownlinkService` 已支持 `thing.config.push`，并复用现有配置治理链路：

- 默认按单设备 `collection` 类型触发配置刷新
- 支持 `device`、`points`、`connection`、`collection`、`all`
- `type=all` 且未显式带设备时，会触发异步全量同步
- `type=all` 且显式带设备时，会顺序刷新设备、点位和连接配置
- 当前实现更偏向“触发配置同步/重载”，不是按 MQTT 消息体直接写入本地完整配置

当前仍返回 `501` 的只剩：

- `thing.ota.upgrade`

当前影响：

- 云端已可通过统一 MQTT 下行协议直接触发采集配置刷新
- 云端仍无法通过统一 MQTT 下行协议触发 OTA 升级流程

### 3.2 `thing.ota.progress` 只有消息构造能力，没有真实进度生产链路

当前 `IoTProtocolService` 已经可以构造 `thing.ota.progress` 消息，但仓库内并没有真实 OTA 主流程去持续产出升级进度。

这意味着：

- “OTA 进度上报”只有消息格式能力
- 还没有升级任务、下载、校验、安装、回滚、状态推进与进度回传闭环

### 3.3 MQTT 服务调用还缺“平台服务名 -> 协议命令”配置化映射

当前 `MqttDownlinkService` 会从以下字段中直接取命令名：

- `command`
- `service`
- `identifier`
- `serviceId`

但更复杂的“平台服务名映射为协议命令名”的规则当前还没有配置化实现。

这意味着：

- 简单服务调用已可用
- 复杂平台模型、多协议异构命令映射仍需要业务层自行约束

### 3.4 TCP 下行控制链路仍未打通

从当前代码与文档状态看，真正完成的下行入口主要还是 MQTT。TCP 方向目前缺少完整的反向控制链路，尤其包括：

- TCP JSON 下行消息解析与命令路由
- TCP 二进制下行协议解码
- 与 `writePoints(...)` / `executeCommand(...)` 的统一接线

结论：

- 如果后续要强调“多链路双向控制”，TCP 下行仍是明确未完成项

### 3.5 `CUSTOM_TCP` / `CUSTOM_UDP` 仍是占位实现

当前 `CustomProtocolCollector` 只完成了生命周期骨架，典型现状包括：

- 可以初始化、连接、断开
- 读点、批量读点、写点、批量写点、订阅、取消订阅、执行命令等核心方法仍直接抛出未支持异常

结论：

- `CUSTOM_TCP` / `CUSTOM_UDP` 目前不能作为真实采集协议对外承诺
- 适合在文档里明确标注为“扩展占位协议”

### 3.6 监控报表调度器仍是骨架代码

`monitor/metrics/ReportScheduler` 当前仍然只有调度骨架，核心报送逻辑尚未落地，代码中保留了明确的 `TODO`。

这意味着：

- 监控指标采集、缓存、健康检查等能力是存在的
- 但“定时报表输出 / 趋势报表任务”还不能按完整能力对外承诺

### 3.7 监控 README 对报表能力存在过度承诺

当前 `src/main/java/com/wangbin/collector/monitor/README.md` 中，把 `ReportScheduler` 描述成已经支持：

- 实时大盘
- 历史趋势
- 设备效率排行
- 定期报表

但代码真实状态仍是调度骨架。

结论：

- 这不只是“功能未完成”问题
- 还是“文档口径超过代码事实”的问题，开源前必须收敛

### 3.8 `ReportManager` 的压缩上报模式还没有真正分化实现

当前 `ReportManager` 虽然保留了压缩上报入口，但压缩分支本质上仍回落到普通批量上报逻辑，没有形成独立的数据压缩与发送路径。

这意味着：

- “支持压缩上报模式”从配置结构上成立
- 但从执行效果看，还不应把它描述成完整能力

### 3.9 处理器链管理仍未真正接入主采集链路

`ProcessorChainManager` 目前更像一个预留框架，存在两个明显现状：

- 代码中仍保留“从数据库或配置动态加载处理器链”的 `TODO`
- 主采集闭环里没有形成一个明确、稳定、默认启用的处理器链编排入口

结论：

- 当前项目的主处理链仍以 `BaseCollector` + `DataQualityProcessor` + 缓存/上报切面为主
- `ProcessorChainManager` 还不应视为已经完整投入主流程

### 3.10 `collector.mqtt` 本地配置兜底仍未完全收敛

当前配置中仍同时存在两套相关入口：

- `collector.report.mqtt`
- `collector.mqtt`

其中 `collector.mqtt` 仍被部分采集逻辑使用，说明项目还没有完全收敛到单一的 MQTT 配置模型。

这会带来两个问题：

- 配置理解成本偏高
- 开源使用者容易误判到底该维护哪一套配置

### 3.11 编码与乱码问题仍需要系统清理

当前仓库里仍有部分文档和源码注释、日志文案存在编码不统一、终端查看乱码或历史残留注释异常的问题。

这类问题已经不只是文档观感问题，还会直接影响：

- 协议说明可读性
- 日志排障效率
- 异常文案可理解性
- 开源仓库的整体可信度

### 3.12 控制台页面仍有占位区域

当前 `static/admin/index.html` 中仍保留明显的预留面板，例如：

- 事件告警面板预留
- 通讯日志面板预留

结论：

- 当前控制台可以作为运行观察入口
- 但还不能把它描述成完整的一体化运维控制台

## 4. 协议层仍然存在的能力边界

以下内容不一定属于“缺陷”，但从开源表述上应该明确写成能力边界，避免使用者误解为全部协议都同等完整。

### 4.1 `BACNET_SC` 仍属于实验性能力

`BacnetScCollector` 当前定位仍是安全 WebSocket 通道方向的实验性实现，还不能视为完整的 BACnet/SC 标准 Hub/Node 体系落地。

### 4.2 `OMRON_FINS` 不支持原生订阅，高风险命令未开放

当前 `OmronFinsCollector` 的边界较明确：

- 不支持原生订阅
- `executeCommand(...)` 已按白名单支持控制器信息、CPU 状态和时钟读取
- RUN/STOP 等高风险控制命令仍未开放

更准确的说法应是：

- `OMRON_FINS` 以轮询采集为主
- 不适合对外描述为“完整读写订阅命令全支持”

### 4.3 `MITSUBISHI_MC` 当前仍以轮询为主，并存在帧型边界

当前 `McCollector` 已具备真实读写能力，但仍存在以下边界：

- 不支持原生订阅，当前明确为 `P0 only supports polling`
- 当前帧型只覆盖 `3E_BINARY`、`3E_ASCII`、`4E_BINARY`
- 其他帧型会进入 `UnsupportedMcFrameCodec`
- 远程 `RUN/STOP/RESET` 与 `UDP` 传输仍未纳入当前常规交付范围

### 4.4 `SIEMENS_S7` 的符号化与数组能力仍有限制

当前 `S7Collector` 的主要边界包括：

- 不支持符号化浏览与自动导入
- 数组点位只支持整数组读写
- 数组点位上不支持缩放、偏移、精度、上下限、告警等处理规则
- 订阅能力依赖底层 PLC4X 运行时元数据，不适合无条件承诺

### 4.5 `ETHERNET_IP` 的订阅与数组处理仍有边界

当前 `EtherNetIpCollector` 的主要边界包括：

- 订阅能力依赖底层驱动元数据，不保证所有环境可用
- 数组点位不支持缩放、偏移、精度、上下限、告警等规则

### 4.6 `ADS` 数组订阅仍未开放

当前 `AdsCollector` 的主要边界包括：

- 一维同构数组轮询读写已经支持，并严格校验元素数量
- 数组订阅暂不支持
- 订阅能力同样依赖底层驱动元数据

### 4.7 `KNXNET_IP` 的读写订阅能力依赖驱动元数据

当前 `KnxNetIpCollector` 对读、写、订阅的支持需要底层 PLC4X 驱动在运行时声明能力，因此：

- 不能简单写成“默认全部支持”
- 更准确的说法是“支持能力受底层驱动实现约束”

### 4.8 `OPC_UA` 仍有数组订阅、浏览与双驱动验收边界

当前 `Plc4xOpcUaCollector` 的主要边界包括：

- PLC4X 路径已支持一维数组轮询读写，数组订阅暂不开放
- 浏览能力依赖底层驱动元数据
- 订阅能力依赖底层驱动元数据
- `OPC_UA_MILO` 已作为独立实验协议接入，但尚未完成与 PLC4X 的同服契约验收

注意：

- 这不等于项目完全不支持 `OPC_UA`
- 这里说的是 PLC4X 路径下的能力边界

### 4.9 `MODBUS_RTU` 原生诊断命令仍未实现

PLC4X 串口路径不支持的功能码 07、08、11、12 已改为明确抛出“不支持”，不再返回假成功。后续若确有需求，
仍需实现独占串口的 Native 驱动和标准异常码处理。

当前 `Plc4xModbusRtuCollector` 中，以下能力仍偏占位：

- `read_exception_status`
- `diagnostics`
- `get_comm_event_counter`
- `get_comm_event_log`

这些命令入口存在，但目前仍以占位响应为主，不适合写成完整诊断能力。

## 5. 按优先级处理建议

如果目标是“按当前配置方式准备开源，不做大改造”，建议按下面顺序处理。

### 5.1 P0：开源前必须先处理

#### 1. 统一文档口径，修正文档互相冲突

当前至少有以下文档仍与代码现实冲突：

- `docs/02-采集协议支持与实现方式.md`
- `docs/protocols/README.md`
- `docs/protocols/MQTT.md`
- `docs/protocols/BACNET_IP.md`
- `src/main/java/com/wangbin/collector/monitor/README.md`

这些冲突会直接导致使用者对以下事实判断错误：

- `BACNET_IP` 是否已具备真实数据面
- MQTT `thing.property.set` / `thing.service.invoke` 是否已打通
- BACnet 诊断命令、COV 重连恢复是否存在
- 监控报表能力是否真的已经完成

#### 2. 统一编码，清理乱码

建议把开源面向的文档和关键源码说明统一为 `UTF-8`，并重点清理：

- README
- `docs/*`
- 协议文档
- 监控 README
- 关键连接适配器和异常信息中的乱码日志文案

原因很简单：这类问题会直接影响第一印象、问题定位和维护效率。

#### 3. 收敛“过度承诺”的描述

当前最典型的过度承诺点是：

- 报表调度器还是骨架，但文档写得像完整能力
- 控制台还有占位区块，但容易被误解为完整运维台
- 部分协议能力边界没有在文档里清楚写明

### 5.2 P1：建议尽快处理或明确标注

#### 1. 明确 MQTT 下行剩余缺口

至少要在 README 和协议文档里写清楚：

- `thing.config.push` 已实现最小闭环，但要在文档里写清楚它是“触发配置刷新”，不是“直接落地完整配置载荷”
- `thing.ota.upgrade` 暂未实现
- `thing.ota.progress` 只有消息构造能力，没有真实生产链路
- 服务名到协议命令名已支持全局映射，但设备级/协议级差异化映射仍待补齐

#### 2. 明确 TCP 下行仍未支持

如果暂时不做实现，就应直接写成“当前不支持 TCP 下行反控”。

#### 3. 明确 `CUSTOM_TCP` / `CUSTOM_UDP` 为占位协议

如果暂时不补协议帧解析与读写逻辑，就不要在任何对外文档中写成“已支持真实采集”。

#### 4. 说明两套 MQTT 配置入口的用途

在不改代码结构的前提下，至少要写清楚：

- `collector.report.mqtt` 用在哪里
- `collector.mqtt` 用在哪里
- 如果同时配置，谁优先、谁兜底

#### 5. 报表与处理器链相关能力要么补齐，要么降级表述

优先处理：

- `ReportScheduler`
- `ReportManager` 压缩模式
- `ProcessorChainManager`

如果短期不做实现，就应在文档中明确写成“预留框架”或“部分实现”。

### 5.3 P2：可按业务需要继续完善

#### 1. 协议细项持续补强

例如：

- `OMRON_FINS` 的命令执行
- `MITSUBISHI_MC` 的更多帧型或更深控制能力
- `S7` / `ETHERNET_IP` / `ADS` / `KNXNET_IP` / `PLC4X OPC_UA` 的边界补齐
- `MODBUS_RTU` 的诊断命令补实

#### 2. 控制台占位区域补齐

如果后续有计划继续做管理台，可再补：

- 事件告警列表
- 通讯日志面板
- 更完整的反控与链路调试入口

## 6. 当前未完成总览

截至目前，仍建议视为未完成或仅部分完成的重点项如下：

- 文档体系口径仍未统一，且多处与代码事实冲突
- 仓库内仍存在编码不统一与乱码问题
- MQTT 的 `thing.config.push` 已实现最小闭环，`thing.ota.upgrade` 仍未实现
- `thing.ota.progress` 只有消息构造能力，没有真实进度链路
- MQTT 服务名到协议命令名已支持全局映射，但设备级/协议级差异化映射仍待补齐
- TCP 下行控制链路仍未打通
- `CUSTOM_TCP` / `CUSTOM_UDP` 仍是占位协议
- 报表调度器仍是骨架代码
- 监控 README 对报表能力存在过度承诺
- 压缩上报模式没有独立实现
- 处理器链仍未真正接入主采集闭环
- MQTT 双配置入口仍未完全收敛
- 控制台仍有占位面板
- 多个协议仍存在明确能力边界，不能按“全功能统一支持”对外承诺

以上清单更适合作为当前版本的真实“未完成功能与实现边界”说明。

## 8. 2026-07-16 协议能力收口实施计划

本节以 `ProtocolDescriptorRegistry`、实际采集器方法和现有测试为依据，说明协议能力缺口的代码落点。
实施时不得绕开 `ConnectionFactory`、`BaseCollector`、`TelemetryIngressService` 另建独立采集链路。

截至 2026-07-17，能力状态模型、假成功清理、订阅降级、CUSTOM TCP/UDP 数据面、FINS 只读命令、
ADS/OPC UA 一维数组、OPC UA 显式双驱动、BACnet/SC TLS 基线和边缘遥测入口已经完成代码与定向测试。
以下条目保留作为后续真实设备、协议栈和硬件在环验收清单。

### 8.1 协议能力元数据

当前 `ProtocolDescriptor` 只使用 `implemented/writable/subscribable` 三个布尔值，无法表达“运行时依赖驱动”
和“实验性”状态，并且已经与代码产生偏差：IEC104、IEC61850、SNMP 已实现写入，CoAP 已实现 Observe，
但注册表仍按只读或不可订阅返回。

调整方案：

1. 新增 `ProtocolCapabilityState` 枚举，至少包含 `SUPPORTED`、`UNSUPPORTED`、`RUNTIME_DEPENDENT`、
   `EXPERIMENTAL`。
2. 将 `ProtocolDescriptor` 的静态能力改为能力对象；现有布尔字段由能力状态派生，避免前端契约重复判断。
3. 在 `ProtocolSchemaService` 返回静态能力，在设备运行态接口返回连接建立后的实际能力。
4. 增加协议能力矩阵测试，覆盖 IEC104、IEC61850、SNMP、CoAP、S7、ADS、KNXnet/IP、OPC UA。

### 8.2 CUSTOM_TCP 与 CUSTOM_UDP

当前 `CustomProtocolCollector` 的读写订阅方法全部抛出未支持异常；`CUSTOM_UDP` 只是 `CUSTOM_TCP` 的别名，
注册表甚至会把它解析为 TCP。当前测试只验证协议名称，没有数据面测试。

调整方案：

1. 将 `CUSTOM_TCP` 和 `CUSTOM_UDP` 注册为两个独立 descriptor，分别创建 TCP 和 UDP 连接适配器。
2. 新增 `CustomFrameCodec`、`CustomRequestEncoder`、`CustomResponseDecoder`、
   `CustomCorrelationStrategy` 接口，通过受控插件注册表选择实现，不允许执行数据库下发的任意脚本。
3. 第一阶段只支持固定长度、分隔符、长度字段三种帧边界，以及字节偏移、位偏移和 JSONPath 三种解析方式。
4. `CustomProtocolCollector` 负责请求关联、超时、批量读取和调用 `ingestPushedValue`，不得直接写缓存或上报。
5. 增加 TCP 粘包/半包、UDP 乱序/丢包、请求序号关联、非法帧和断线恢复集成测试。

### 8.3 BACNET_SC

当前 `BacnetScCollector` 复用 `BacnetIpCollector`，`BacnetScClient` 仍按 BACnet/IP 的 `BVLC 0x81` 编解码，
只是由 `BacnetScConnectionAdapter` 将帧放入安全 WebSocket，因此属于安全隧道实现，而不是完整 BACnet/SC。

调整方案：

1. 新增 SC 专用 BVLL 编解码，覆盖 VMAC、地址解析、Connect/Accept/Disconnect、Heartbeat 和 Result 消息。
2. 新增 `BacnetScSession` 状态机，管理 Node 到 Hub 的连接、重连、心跳、VMAC 冲突和会话关闭。
3. 上层 APDU、分段响应、WriteProperty 和 COV 继续复用现有 BACnet 服务代码，不复制属性层实现。
4. 强制校验证书链、主机名和客户端证书，生产配置禁止信任全部证书。
5. 增加内存 Hub 测试桩和真实 BACnet/SC Hub 互操作测试，通过后再把能力从 `EXPERIMENTAL` 调整为 `SUPPORTED`。

当前进度：已完成 WebSocket 默认信任链修正、客户端密钥库/服务端信任库加载、`wss` 与双向 TLS 强校验，
并新增 `BacnetScSessionState` 公开 `SECURE_TUNNEL_ACTIVE` 状态。SC 专用 BVLL、VMAC 与标准 Hub 会话仍未完成。

### 8.4 OMRON_FINS

当前 `FinsFrameCodec` 只实现内存区读 `01/01` 和写 `01/02`，所以 `executeCommand` 没有可复用的通用命令帧。
FINS/UDP 本身没有与当前点位模型对应的原生值变更订阅，现有 `doSubscribe` 只是记录日志。

调整方案：

1. 抽取通用 FINS 命令帧构建和响应解析，保留 SID、命令回显和 End Code 校验。
2. 按明确白名单增加 CPU 状态、控制器信息、时钟读取等只读命令，再单独评审 RUN/STOP 等高风险命令。
3. 高风险命令必须复用控制接口鉴权、审计和设备级开关，不得仅凭命令字符串执行。
4. 不伪造原生订阅；协议保持 `subscribable=UNSUPPORTED`。如果用户要求订阅体验，由调度器明确降级为轮询并返回降级原因。
5. 扩展现有 FINS UDP 测试桩，验证命令 End Code、SID 不匹配、超时重试和权限拒绝。

当前进度：通用命令帧、SID/命令回显/End Code 校验以及控制器信息、CPU 状态、时钟读取白名单已完成；
原生订阅继续明确拒绝，可通过统一策略显式降级轮询。

### 8.5 MITSUBISHI_MC

当前已实现 3E Binary、3E ASCII、4E Binary 和 TCP 轮询读写，其他帧型进入 `UnsupportedMcFrameCodec`；
`executeCommand` 仅支持点位读写和状态，订阅直接拒绝。

调整方案：

1. 仅在现场设备明确需要时增加 `Mc4eAsciiFrameCodec` 或旧系列帧型，不做无设备验证的全帧型堆叠。
2. 若需要 UDP，先抽取 MC 请求响应传输接口，再新增 UDP 适配器；TCP 默认路径保持不变。
3. RUN/STOP/RESET 使用独立命令 codec、设备白名单、二次确认、操作审计和执行后状态回读。
4. MC 没有当前模型可直接使用的原生点位订阅，保持轮询；不要用空订阅方法伪装成功。
5. 每个新增帧型必须扩展 `FakeMcServer`、序列号/End Code/长度异常测试及至少一次真实 PLC 长稳验证。

### 8.6 SIEMENS_S7

当前 `S7Collector` 已实现绝对地址读写、整段一维数组和 PLC4X 支持时的循环/事件订阅，明确不支持符号浏览；
数组路径直接透传，拒绝缩放、偏移、精度、上下限和告警规则。

调整方案：

1. 不把 S7comm 绝对地址协议包装成在线符号浏览。新增离线 TIA 导出文件导入服务，将符号映射为可验证的绝对地址；
   优化 DB 无绝对偏移时应明确拒绝，建议改走 OPC UA。
2. 抽取通用数组处理器，第一阶段逐元素支持缩放、偏移、精度和上下限，并在 `ProcessResult` 保存元素级质量。
3. 数组告警需要生成稳定的 `pointId[index]` 告警身份和独立状态机，不能把整个数组共用一个告警状态。
4. 对 PLC4X 不支持订阅的连接增加显式 `FAIL_FAST` 或 `FALLBACK_TO_POLLING` 策略，并在运行状态显示实际模式。
5. 增加 TIA 文件导入、数组元素质量、订阅降级和真实 S7-1200/1500 验证。

### 8.7 ETHERNET_IP

当前 `EtherNetIpCollector` 已实现 Logix Tag 标量和数组读写，但数组只允许透传；`doSubscribe` 明确抛出不支持，
运行状态也返回 `subscribable=false`。

调整方案：

1. 数组处理复用 S7 的通用数组处理器，不在两个采集器中继续复制规则判断。
2. 普通实时需求优先使用轮询降级策略。若必须支持 CIP 隐式 I/O，需要单独实现 Forward Open/Close、连接 ID、
   RPI、UDP I/O 数据包和连接超时状态机，不能将普通 Tag 轮询命名为订阅。
3. 隐式 I/O 应作为独立能力开关和独立连接服务，数据仍通过 `TelemetryIngressService` 进入统一链路。
4. 使用 Logix 模拟器或真实 PLC 验证数组、UDT 边界、Forward Open 恢复和长稳运行。

### 8.8 ADS

`AdsAddressParser` 已能解析数组长度，`AdsCollector` 现已通过通用 PLC4X 数组工具完成一维同构数组轮询读写；
剩余缺口是数组订阅与 TwinCAT 实服验证，不再是地址模型或基础值编解码。

调整方案：

1. 复用 PLC4X 数组值读取、写入转换和 `ProcessResult` 构建工具，先支持一维同构数组整段读写。
2. 明确数组长度、元素类型和字符串元素长度，写入前严格校验数量。
3. 第一阶段数组订阅可拒绝，标量订阅保持现状；驱动验证通过后再开放数组循环订阅。
4. 增加直接地址、符号地址、数组读写、长度不匹配和订阅重连测试，并使用 TwinCAT 实服验收。

当前进度：一维同构数组轮询读写和严格长度校验已完成，数组订阅保持拒绝；TwinCAT 实服验收未完成。

### 8.9 KNXNET_IP

当前 KNX 读写订阅实现已经存在，但是否可用由 PLC4X 连接元数据决定；缺口是能力发现、配置反馈和现场验证，
不是再写一套重复的组地址协议。

调整方案：

1. 连接成功后把 read/write/subscribe 实际能力写入设备运行态，前端根据运行态而不是静态 descriptor 展示操作。
2. 增加订阅不可用时的显式轮询降级，并记录 `requestedMode/actualMode/degradedReason`。
3. 对无 DPT 且无 KNX project 的点位继续强校验，避免按错误类型解析总线值。
4. 使用 KNX/IP Router、Tunnel 和项目文件分别做读写、事件订阅、重连和 DPT 互操作测试。

### 8.10 OPC_UA 与 OPC_UA_PLC4X

`OPC_UA` 与 `OPC_UA_PLC4X` 路由到 `Plc4xOpcUaCollector`，支持标量和一维同构数组轮询读写；
数组订阅仍明确拒绝，浏览和标量订阅依赖驱动元数据。`OPC_UA_MILO` 已显式路由到独立的 Eclipse Milo
`OpcUaCollector`，不会与 PLC4X 连接混用，但仍属于实验能力。

调整方案：

1. 已通过独立协议标识 `OPC_UA` / `OPC_UA_MILO` 固定驱动，同一设备生命周期内只创建一个采集器，禁止按操作混用连接。
2. Milo 采集器已接入 `CollectorFactory`、`ConnectionFactory`、配置校验和运行状态；完成实服验收前不切换生产默认驱动。
3. PLC4X 路径已复用通用数组处理器支持一维数组；Milo 路径继续补批量写、订阅重建、会话恢复和证书生命周期。
4. 浏览结果统一为稳定 DTO，包含 NodeId、BrowseName、NodeClass、DataType、AccessLevel 和数组维度，可直接生成点位草稿。
5. 建立同一 OPC UA 测试服务器上的双驱动契约测试，读写、浏览、订阅、数组、安全策略全部通过后才能切换默认值。

当前进度：PLC4X 一维数组轮询读写已完成；`OPC_UA_MILO` 已作为独立实验协议接入 `CollectorFactory`、
`ConnectionFactory` 和校验器，并从表单中排除仅供 PLC4X 使用的原始连接串。默认 `OPC_UA` 路由未改变，
同服双驱动契约和默认驱动切换尚未完成。

### 8.11 MODBUS_RTU 诊断命令

当前 PLC4X 串口适配器只暴露 Tag 读写，异常状态、Diagnostics、通信事件计数和事件日志只构造请求字节或返回占位结果。
同一串口不能同时由 PLC4X 和另一个串口客户端占用。

调整方案：

1. 默认 PLC4X 采集路径保持不变，先从对外能力列表移除占位诊断命令，避免返回假成功。
2. 确有业务需求时新增 `PLC4X/NATIVE` 串口驱动选择；Native 模式由单一请求队列独占串口并实现 CRC、帧间隔、
   功能码、异常码和超时关联，采集与诊断都走同一个客户端。
3. 补齐功能码 07、08、11、12 的响应模型和设备支持性判断；从站不支持时返回标准协议异常，不返回成功占位。
4. 使用虚拟串口和真实从站验证正常响应、CRC 错误、静默间隔、广播地址和并发串行化。

### 8.12 IEC104、IEC61850、SNMP 与 COAP

这四项的主要缺口不是数据面，而是注册元数据。IEC104 已实现命令和自发上送，IEC61850 已实现写入和报告，
SNMP 已实现 SET/WALK/Trap，CoAP 已实现 Observe。

调整方案：

1. 先修正 descriptor 能力状态和前端展示，不重复开发已经存在的读写订阅代码。
2. 为每项增加“descriptor 静态能力 + collector 实际方法 + 集成测试”一致性用例。
3. IEC 和 SNMP 写操作继续受点位 `readWrite`、控制接口权限和审计约束；不能因为修正元数据而放开未授权写入。

### 8.13 PROFINET 与 EtherCAT

当前工程没有这两个协议的 descriptor、连接适配器、采集器、地址模型或依赖。两者都不适合直接在普通 Spring
业务线程中实现确定性循环通信。

调整方案：

1. `PROFINET` 先明确范围：只做 DCP/非循环 Record Data，还是需要 PROFINET IO 周期数据。前者可以做普通适配器，
   后者应使用经过验证的协议栈或独立边缘进程。
2. `EtherCAT` 必须使用具备原始网卡访问和实时调度能力的 Master 进程，负责 ENI/ESI、PDO、SDO、状态机和分布式时钟；
   Java 服务不直接承担微秒级循环。
3. 两个边缘进程通过受鉴权的本地网关协议上送 `deviceId/pointId/value/quality/timestamp/sequence`，
   Java 侧新增网关型 collector 并通过 `TelemetryIngressService` 接入现有缓存、处理、告警和上报链路。
4. 增加进程心跳、序号去重、时间同步、断线降级和配置版本握手，不允许把网关在线误判为现场总线健康。
5. 只有完成硬件在环、周期抖动、断网恢复和 8 小时长稳测试后，才能注册为 `SUPPORTED`。

当前进度：已提供受 HMAC/Token 鉴权和 `EDGE_INGEST` 权限保护的 `/api/edge/telemetry`，实现已配置点位映射、
质量/时间戳透传和 `gatewayId + deviceId` 递增序号去重，并接入统一处理与后处理链路。边缘进程心跳、持久化序号、
配置版本握手确认、PROFINET/EtherCAT 主站实现和硬件在环测试仍未完成，因此未注册为可用现场协议。

### 8.14 建议执行优先级

1. `P0`：协议能力元数据一致性、移除假成功占位、订阅降级状态可观测。
2. `P1`：OPC UA 双驱动收口、ADS 数组、FINS 运维命令、S7/EtherNet-IP 通用数组处理。
3. `P1`：有明确 BACnet/SC 项目时完成标准 Hub/Node 状态机。
4. `P2`：按现场需求扩展 MC 帧型、UDP 和高风险控制命令。
5. `项目制预研`：CUSTOM 协议插件、PROFINET、EtherCAT；没有设备、协议样本和验收环境时不进入主干实现。
