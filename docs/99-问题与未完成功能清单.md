# 问题与未完成功能清单（截至 2026-07-07）

## 1. 文档说明

这份清单基于当前仓库代码重新梳理，目标不是罗列历史问题，而是回答两个更实际的问题：

1. 以前文档里写“未完成”的内容，现在到底还有没有未完成。
2. 当前版本真正还没有做完、或者能力边界还比较明确的部分有哪些。

因此，本文档分成两类内容：

- 已经完成，但旧文档没有及时同步的内容
- 目前代码里仍然存在的未完成功能、占位实现或能力边界

## 2. 已完成但旧文档未同步的内容

以下内容在当前代码中已经落地，不能再归类为“未实现”。

### 2.1 MQTT 下行里的属性设置与服务调用已打通

当前 `MqttDownlinkService` 已经支持以下两类消息：

- `thing.property.set`
- `thing.service.invoke`

现状说明：

- `thing.property.set` 已经可以把下行点位写入请求路由到 `CollectionManager.writePoints(...)`
- `thing.service.invoke` 已经可以把命令调用路由到 `CollectionManager.executeCommand(...)`
- 对应测试 `MqttDownlinkServiceTest` 已覆盖成功路径

结论：

- MQTT 下行链路不是“完全未实现”
- 真正还没完成的只剩配置推送和 OTA，见下文第 3.1 节

### 2.2 设备影子的 Redis CAS、版本冲突处理、TTL 与历史能力已落地

当前 `ShadowManager` 已经具备以下能力：

- 基于 Lua 的 Redis CAS 更新
- 本地版本与远端版本冲突检测
- 自动合并与重试策略
- 影子 TTL 管理
- 脏设备集合维护
- 历史版本留存与过期时间控制

对应配置已经存在于 `ReportProperties.Shadow` 中，例如：

- `casEnabled`
- `autoMergeEnabled`
- `ttlSeconds`
- `historyEnabled`
- `historyTtlSeconds`

结论：

- 旧文档里“设备影子 Redis CAS / 一致性 / 过期清理暂未实现”的说法已经过时
- 当前更准确的表述应该是：设备影子已经具备 Redis CAS 与版本治理能力，后续是否继续增强一致性策略，要按业务要求再评估

### 2.3 BACnet/IP 已不是占位能力

当前 `BacnetIpCollector` 已经具备较完整的数据面能力，包括：

- 读点
- 批量读点
- 写点
- 批量写点
- COV 订阅
- `who_is`
- `discover_objects`
- `device_info`
- `diagnostic`
- 运行状态查询

仓库内也已经存在多组 `BACNET_IP` 相关测试，不应再把它归类为“只有框架没有真实实现”。

结论：

- `BACNET_IP` 已经属于真实可用能力范围
- 真正仍应谨慎表述的是 `BACNET_SC`，见第 4.1 节

## 3. 当前仍未完成的核心能力

这部分才是当前版本真正还没做完、或者只做到一半的内容。

### 3.1 MQTT 配置推送与 OTA 仍未实现

当前 `MqttDownlinkService` 对以下消息类型仍返回 `501`：

- `thing.config.push`
- `thing.ota.upgrade`

这说明目前 MQTT 下行只完成了“控制类”能力的一部分，还没有完成“配置治理类”和“升级类”能力。

当前影响：

- 云端无法通过统一 MQTT 下行协议直接下发采集配置变更
- 云端无法通过统一 MQTT 下行协议触发 OTA 升级流程

建议：

- 如果准备开源，README 和协议文档应明确写成“属性设置、服务调用已支持；配置推送、OTA 升级暂未实现”

### 3.2 TCP 下行控制链路仍未打通

从当前代码与文档实现状态看，真正完成的下行入口主要还是 MQTT。TCP 方向目前缺少完整的反向控制链路，尤其包括：

- TCP JSON 下行消息解析与命令路由
- TCP 二进制下行协议解码
- 与 `writePoints(...)` / `executeCommand(...)` 的统一接线

结论：

- 如果后续要强调“多链路双向控制”，TCP 下行仍是明确未完成项

### 3.3 `CUSTOM_TCP` / 自定义协议采集器仍是占位实现

当前 `CustomProtocolCollector` 只完成了生命周期骨架，典型现状包括：

- 可以初始化、连接、断开
- 读点、批量读点、写点、批量写点、订阅、取消订阅、执行命令等核心方法仍直接抛出未支持异常

结论：

- `CUSTOM_TCP` 目前不能作为真实采集协议对外承诺
- 适合在文档里明确标注为“扩展占位协议”

### 3.4 监控报表调度器仍是骨架代码

`monitor/metrics/ReportScheduler` 当前仍然只有调度骨架，核心报送逻辑尚未落地，代码中保留了明确的 `TODO`。

这意味着：

- 监控指标采集、缓存、健康检查等能力是存在的
- 但如果文档宣称已经形成完整的“定时报表输出 / 趋势报表任务”，则会超过代码实际状态

结论：

- 报表调度能力应视为未完成，不应在开源说明中写成已完整交付

### 3.5 `ReportManager` 的压缩上报模式还没有真正分化实现

当前 `ReportManager` 虽然保留了压缩上报入口，但压缩分支本质上仍回落到普通批量上报逻辑，没有形成独立的数据压缩与发送路径。

这意味着：

- “支持压缩上报模式”从配置结构上成立
- 但从执行效果看，还不应当把它描述成完整能力

### 3.6 处理器链管理仍未真正接入主采集链路

`ProcessorChainManager` 目前更像一个预留框架，存在两个明显现状：

- 代码中仍保留“从数据库或配置动态加载处理器链”的 `TODO`
- 主采集闭环里没有形成一个明确、稳定、默认启用的处理器链编排入口

结论：

- 当前项目的主处理链仍以 `BaseCollector` + `DataQualityProcessor` + 缓存/上报切面为主
- `ProcessorChainManager` 还不应视为已经完整投入主流程

### 3.7 `collector.mqtt` 本地配置兜底仍未完全收敛

当前配置中仍同时存在两套相关入口：

- `collector.report.mqtt`
- `collector.mqtt`

其中 `collector.mqtt` 仍被部分采集逻辑使用，说明项目还没有完全收敛到单一的 MQTT 配置模型。

这会带来两个问题：

- 配置理解成本偏高
- 开源使用者容易误判到底该维护哪一套配置

建议：

- 如果暂时不做结构调整，至少要在 README 或配置说明里把两者用途说清楚

### 3.8 编码与乱码问题仍需要系统清理

当前仓库里仍有部分文档和源码注释存在编码不统一、终端查看乱码或历史残留注释异常的问题。

这类问题虽然不一定影响运行，但会直接影响开源观感与维护效率，尤其体现在：

- 协议说明文档可读性下降
- 新贡献者难以判断注释原意
- README、协议文档、监控说明之间容易出现表达不一致

结论：

- 编码统一仍然是开源前应优先处理的工程化问题

### 3.9 控制台页面仍有占位区域

当前 `static/admin/index.html` 中仍保留明显的预留面板，例如：

- 事件告警面板预留
- 通讯日志面板预留

结论：

- 当前控制台可以作为运行观察入口
- 但还不能把它描述成完整的一体化运维控制台

## 4. 协议层仍然存在的能力边界

以下内容不一定属于“缺陷”，但从开源表述上应该明确写成能力边界，避免使用者误解为全部协议都同等完整。

### 4.1 `BACNET_SC` 仍属于实验性能力

`BacnetScCollector` 当前定位仍是安全 WebSocket 通道方向的实验性实现，还不能视为完整的 BACnet/SC 标准 Hub/Node 体系落地。

结论：

- 可以保留在协议列表中
- 但应明确标注为实验性支持

### 4.2 `OMRON_FINS` 暂不支持订阅与命令执行

当前 `OmronFinsCollector` 的边界较明确：

- 不支持原生订阅
- `executeCommand(...)` 仍未实现

更准确的说法应是：

- `OMRON_FINS` 以轮询采集为主
- 不适合对外描述为“完整读写订阅命令全支持”

### 4.3 `MITSUBISHI_MC` 当前仍以轮询为主

当前 `McCollector` 已经具备真实读写能力，但订阅能力仍明确不支持，代码中直接说明 `P0 only supports polling`。

结论：

- `MITSUBISHI_MC` 适合写成“支持轮询读写，不支持订阅”

### 4.4 `SIEMENS_S7` 的符号化与数组能力仍有限制

当前 `S7Collector` 的主要边界包括：

- 不支持符号化浏览与自动导入
- 数组点位只支持整数组读写
- 数组点位上不支持缩放、偏移、精度、上下限、告警等处理规则
- 订阅能力依赖底层 PLC4X 运行时元数据，不适合无条件承诺

结论：

- `SIEMENS_S7` 已可用，但不应写成“全功能透明支持”

### 4.5 `ETHERNET_IP` 的订阅与数组处理仍有边界

当前 `EtherNetIpCollector` 的主要边界包括：

- 订阅能力依赖底层驱动元数据，不保证所有环境可用
- 数组点位不支持缩放、偏移、精度、上下限、告警等规则

### 4.6 `ADS` 暂不支持数组点位

当前 `AdsCollector` 的主要边界包括：

- 数组点位暂不支持
- 订阅能力同样依赖底层驱动元数据

### 4.7 `KNXNET_IP` 的读写订阅能力依赖驱动元数据

当前 `KnxNetIpCollector` 对读、写、订阅的支持需要底层 PLC4X 驱动在运行时声明能力，因此：

- 不能简单写成“默认全部支持”
- 更准确的说法是“支持能力受底层驱动实现约束”

### 4.8 PLC4X 版 `OPC_UA` 仍有数组与浏览边界

当前 `Plc4xOpcUaCollector` 的主要边界包括：

- 数组点位暂不支持
- 浏览能力依赖底层驱动元数据
- 订阅能力依赖底层驱动元数据

注意：

- 这不等于项目完全不支持 `OPC_UA`
- 这里说的是 PLC4X 路径下的能力边界

### 4.9 `MODBUS_RTU` 的部分诊断命令仍是占位返回

当前 `Plc4xModbusRtuCollector` 中，以下能力仍偏占位：

- `read_exception_status`
- `diagnostics`
- `get_comm_event_counter`
- `get_comm_event_log`

这些命令入口存在，但目前仍以占位响应为主，不适合写成完整诊断能力。

## 5. 建议优先级

如果目标是“按当前配置方式准备开源，不做大改造”，建议按下面顺序处理：

1. 先统一文档口径：把 README、协议文档、`docs/99` 里的过时描述全部修正。
2. 处理编码问题：优先清理 README、协议文档、监控文档中的乱码与历史编码残留。
3. 明确能力边界：对 `CUSTOM_TCP`、`BACNET_SC`、TCP 下行、MQTT OTA 等未完成项做显式标注。
4. 统一配置说明：在不改代码结构的前提下，把 `collector.report.mqtt` 和 `collector.mqtt` 的用途写清楚。
5. 收敛“过度承诺”的描述：报表调度、压缩上报、控制台能力都应按真实状态表述。

## 6. 当前未完成总览

截至目前，仍建议视为未完成或仅部分完成的重点项如下：

- MQTT 的 `thing.config.push` 与 `thing.ota.upgrade`
- TCP 下行控制链路
- `CUSTOM_TCP` 协议真实采集实现
- 报表调度器实际报送逻辑
- 压缩上报模式的独立实现
- 处理器链的动态加载与主链路接入
- MQTT 双配置入口的说明与收敛
- 仓库内编码与乱码清理
- 控制台预留面板补齐

以上清单更适合作为当前版本的真实“未完成功能与实现边界”说明。
