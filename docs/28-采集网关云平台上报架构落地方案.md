# 采集网关云平台上报架构落地方案

## 1. 结论

当前采集系统定位是“采集网关”，本地采集设备不应各自建立云平台连接。云平台连接只由网关侧 MQTT 通道维护一次，采集点位进入影子和上报流水线后，由系统按云设备身份和云属性字段组装上报消息。

本轮落地规则如下：

1. 点位云端属性字段只使用 `additionalConfig.reportField`。
2. `pointAlias` 只作为本地显示别名，不参与云上报、下行属性匹配、字段唯一性校验。
3. 缺少 `reportField` 的点位，即使 `reportEnabled=true`，也不进入云属性上报链路。
4. 普通点位上报只走设备级 `DeviceInfo.cloudTarget`，不再从点位推导云设备身份。
5. 子设备上报不新建 MQTT 连接，仍复用网关连接，但发布 topic 必须使用子设备自己的 `{productKey}/{deviceName}`。
6. 网关批量包只在满足批量策略时使用 `/sys/{gatewayProductKey}/{gatewayDeviceName}/thing/event/property/pack/post`。

## 2. 配置模型

### 2.1 设备级云目标

云目标已经提升到设备配置层，字段如下：

```json
{
  "cloudTarget": {
    "enabled": true,
    "deviceType": "SUB_DEVICE",
    "productKey": "pk-sub",
    "deviceName": "sub-001",
    "topologyEnabled": true
  }
}
```

字段含义：

1. `enabled`：是否启用该采集设备的云端上报。
2. `deviceType`：`GATEWAY` 表示网关自身，`SUB_DEVICE` 表示网关子设备，`DIRECT` 预留给直连设备。
2. `productKey/deviceName`：云平台设备身份，必须来自云端设备模型。
3. `topologyEnabled`：子设备是否参与网关拓扑注册。

运行时只读取 `DeviceInfo.cloudTarget` 作为普通上报云身份。点位级 `reportProductKey/reportDeviceName/productKey/cloudBindings` 会被清理，不再参与上报。

### 2.2 点位字段映射

点位只维护一个云属性字段：

```json
{
  "pointCode": "AI_TEMP_01",
  "pointAlias": "1号温度展示名",
  "additionalConfig": {
    "reportEnabled": true,
    "reportField": "temperature"
  }
}
```

约束：

1. `reportField` 必须等于云端物模型属性标识。
2. 同一云设备下，启用上报的 `reportField` 必须唯一。
3. `pointAlias` 不再作为 `reportField` 的兜底值。
4. 点位导入时可以默认把 `pointCode` 填入 `reportField`，但运行时不能隐式兜底。

### 2.3 已删除的点位级云身份

普通上报不再支持以下点位级身份配置：

1. `additionalConfig.reportDeviceName`
2. `additionalConfig.reportProductKey`
3. `additionalConfig.productKey`
4. `additionalConfig.cloudBindings`

如果未来需要一对多、聚合目标、特殊事件路由，应单独设计 `CloudRouteRule` 或 `CloudAggregateTarget`，不能再把普通上报身份塞回点位。

## 3. 连接流程

1. 系统启动后读取 `collector.report.mqtt` 配置。
2. 每个本地网关只创建一个 MQTT 连接，连接身份使用网关云设备三元组。
3. 建连后订阅平台下行 topic 和 ACK topic。
4. ACK 订阅使用 `+/+` 通配云设备身份，保证子设备 topic 的 `_reply` 也能被网关连接接收。
5. 采集线程不直接连接云平台，只写缓存、影子和上报队列。

## 4. 上报流程

### 4.1 普通属性上报

采集数据进入缓存后流程如下：

```text
Collector
  -> ProcessResult
  -> ShadowManager.apply(reportField)
  -> CacheReportService.flushDirtyDevices()
  -> ReportData(properties)
  -> AlinkCloudProtocolAdapter.buildPublishTopic()
  -> MqttReportHandler.reportAsync()
```

子设备普通属性 topic：

```text
/sys/{subProductKey}/{subDeviceName}/thing/property/post
```

payload：

```json
{
  "id": "uuid",
  "version": "1.0",
  "method": "thing.property.post",
  "params": {
    "temperature": 36.5,
    "humidity": 60
  }
}
```

### 4.2 网关批量包

批量包只由网关 topic 发送：

```text
/sys/{gatewayProductKey}/{gatewayDeviceName}/thing/event/property/pack/post
```

payload 必须符合阿里云网关批量包结构：

```json
{
  "id": "uuid",
  "version": "1.0",
  "method": "thing.event.property.pack.post",
  "params": {
    "properties": {},
    "events": {},
    "subDevices": [
      {
        "identity": {
          "productKey": "pk-sub",
          "deviceName": "sub-001"
        },
        "properties": {
          "temperature": 36.5
        },
        "events": {}
      }
    ]
  }
}
```

## 5. 下发流程

平台下发只处理真实下行：

1. `thing.property.set`
2. `thing.service.invoke`
3. `thing.config.push`
4. `thing.ota.upgrade`
5. `thing.topo.change`
6. `thing.auth.register.sub_reply`

`thing.topo.add/delete/get` 和 `thing.auth.register.sub` 是网关主动上行，不应作为平台下行处理。

属性设置匹配规则：

1. 从 topic 或 payload 定位云设备。
2. 映射到本地设备。
3. 使用 `params` 中的属性名匹配本地 `DataPoint.additionalConfig.reportField`。
4. 写入设备影子 desired。
5. 调用 `CollectionManager.writePoints(...)` 下发到采集协议。
6. 发布 `_reply` 响应。

## 6. 告警与事件

告警本质是事件上报，应遵循同一身份规则：

1. 告警所属点位必须能解析到云设备身份。
2. 告警事件标识应来自规则配置或标准事件标识，不应使用 `pointAlias`。
3. 事件 payload 可以携带 `eventType/eventLevel/ruleId/ruleName` 等诊断字段。
4. 高优先级告警可绕过普通批量窗口，但仍复用同一 MQTT 连接。

## 7. 性能策略

1. MQTT 连接按网关复用，避免每个子设备单独建连。
2. 采集写影子，定时或变化触发 flush，避免采集线程被云端 ACK 阻塞。
3. ACK 异步确认，超时重试，不阻塞主采集链路。
4. 相同网关下多个子设备可合并为 property pack。
5. 单包属性数、包大小、并发 pending 数必须有上限。
6. 失败重试使用指数退避和抖动，避免云端或网络恢复时雪崩。

## 8. 本轮代码修改范围

1. `DataPoint.getReportField()` 去掉 `pointAlias` 兜底。
2. 删除 `CloudPointMappingResolver`，普通上报不再从点位 `cloudBindings` 推导云设备身份。
3. `ReportData` 构造属性时只使用 `reportField`。
4. `MqttDownlinkService` 属性下发只按 `reportField` 匹配。
5. `AlinkCloudProtocolAdapter` 下行订阅只暴露真实平台下行。
6. `MqttReportHandler` ACK 订阅改为支持子设备身份的通配 topic。
7. `CloudPackReportAssembler` 和 `AlinkPayloadEncoder` 按阿里云 property pack 结构输出。
8. `CloudTopologyService` 修正 `thing.topo.change` 中 `status=0` 创建、`status=1` 删除。
9. 新增设备级 `DeviceInfo.cloudTarget`，普通上报只从设备级读取 `{productKey}/{deviceName}`。
10. 新增 `CloudDeviceIdentityService`，维护本地设备 ID 与云设备身份的双向索引。
11. 删除旧 `ReportIdentityResolver`，不再读取 `reportDeviceName/reportProductKey/productKey` 点位级身份字段。
12. 前端控制台新增设备级 `cloudTarget` 配置区，点位页只保留 `reportField`。

## 9. 已落地的主链路

当前已把云身份收敛到设备级 `cloudTarget`，形成以下主链路：

```text
DeviceInfo.cloudTarget
  -> DataPoint.additionalConfig.reportField
  -> Shadow
  -> ReportData
  -> CloudProtocolAdapter
  -> MQTT Gateway Connection
```

运行时会清理点位 `reportDeviceName/reportProductKey/productKey/cloudBindings` 旧身份字段。启用上报的点位如果所属设备没有有效 `cloudTarget`，不会进入云端上报。

## 10. 设备级 cloudTarget 最终落地方案

### 10.1 核心结论

采集系统按采集网关设计，云端 MQTT 物理连接只由网关设备建立一次。普通数据上报不能再从点位配置推导 `{productKey}/{deviceName}`，必须由采集设备的设备级 `cloudTarget` 决定。

最终规则：

1. 采集设备决定“上报到哪个云设备”。
2. 点位决定“上报成哪个云属性”。
3. `pointAlias` 只用于本地展示。
4. `cloudBindings` 不再作为普通上报身份配置。
5. 没有有效 `cloudTarget` 的设备不上云，不回退到本地 `deviceId`。

### 10.2 配置结构

网关 MQTT 连接仍来自全局上报配置：

```json
{
  "gatewayProductKey": "pk_gateway",
  "gatewayDeviceName": "collector_gateway_001",
  "gatewayDeviceSecret": "secret"
}
```

每个采集设备维护自己的云端身份：

```json
{
  "id": "local-motor-1",
  "deviceName": "电机采集设备 1",
  "cloudTarget": {
    "enabled": true,
    "deviceType": "SUB_DEVICE",
    "productKey": "pk_motor",
    "deviceName": "motor_001",
    "topologyEnabled": true
  }
}
```

网关自身系统点位也作为一个采集设备维护，只是设备类型为 `GATEWAY`：

```json
{
  "id": "gateway-system",
  "deviceName": "采集网关系统点位",
  "cloudTarget": {
    "enabled": true,
    "deviceType": "GATEWAY",
    "productKey": "pk_gateway",
    "deviceName": "collector_gateway_001",
    "topologyEnabled": false
  }
}
```

点位只维护上报字段：

```json
{
  "pointCode": "temperature_raw",
  "additionalConfig": {
    "reportEnabled": true,
    "reportField": "temperature"
  }
}
```

### 10.3 必须删除的旧逻辑

运行时不再读取以下点位级字段作为云设备身份：

1. `additionalConfig.reportDeviceName`
2. `additionalConfig.reportProductKey`
3. `additionalConfig.productKey`
4. `cloudBindings[].productKey`
5. `cloudBindings[].deviceName`

普通上报也不再保留这些回退：

1. 无云身份时回退到本地 `deviceId`。
2. 无云字段时回退到 `pointCode`。
3. 下发时按 `deviceName/deviceAlias/deviceId` 模糊匹配云设备。

### 10.4 上报流程

采集到点位数据后按以下流程处理：

1. 根据本地 `deviceId` 读取 `DeviceInfo.cloudTarget`。
2. `cloudTarget.enabled=false` 或缺少 `productKey/deviceName` 时跳过云上报。
3. 点位未开启 `reportEnabled` 或缺少 `reportField` 时跳过云属性上报。
4. 将纵向点位数据转换成当前云设备的横向属性快照。
5. `deviceType=GATEWAY` 时发布到 `/sys/{gatewayProductKey}/{gatewayDeviceName}/thing/property/post`。
6. `deviceType=SUB_DEVICE` 时复用网关 MQTT 连接，发布到 `/sys/{subProductKey}/{subDeviceName}/thing/property/post`。
7. 批量属性包按云设备身份分桶，不允许不同子设备被合并成普通属性上报。

### 10.5 下发流程

云端下发 topic 中的 `{productKey}/{deviceName}` 是唯一设备路由依据：

```text
/sys/{productKey}/{deviceName}/thing/property/set
```

处理流程：

1. 从 topic 或 payload 解出云设备身份。
2. 用 `productKey/deviceName` 反查本地采集设备。
3. 找不到本地设备时拒绝处理，不做模糊匹配。
4. 在该设备点位列表里按 `reportField` 找点位。
5. 找到可写点位后调用采集协议写入。

### 10.6 拓扑流程

拓扑关系来自设备级 `cloudTarget`：

1. `deviceType=SUB_DEVICE` 且 `topologyEnabled=true` 的设备参与拓扑注册。
2. 拓扑注册内容使用 `cloudTarget.productKey/deviceName`。
3. 网关身份使用全局 MQTT 网关配置。
4. 点位配置不参与拓扑关系声明。

### 10.7 控制台要求

设备编辑页新增“云平台身份”区：

1. 是否启用云上报。
2. 云设备类型：网关设备 / 子设备 / 不上云。
3. 云 `productKey`。
4. 云 `deviceName`。
5. 是否启用拓扑注册。
6. 当前上报 topic 示例。

点位编辑页只保留：

1. 是否上报。
2. `reportField`。
3. 缓存、变化阈值、事件、告警配置。

点位页删除：

1. 点位级云设备身份。
2. `cloudBindings` 普通配置入口。
3. “点位云目标”概念。

### 10.8 性能原则

1. 本地设备 ID 到云身份使用内存索引。
2. 云身份到本地设备 ID 使用内存索引。
3. 配置变更时清理索引，不在每条数据上报时遍历设备。
4. 上报缓存和影子缓存按云身份隔离，避免不同产品下同名设备冲突。
5. 批量上报只在同一网关连接内聚合，单条普通上报仍按目标云设备构造 topic。
