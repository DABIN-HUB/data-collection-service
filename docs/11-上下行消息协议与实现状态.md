# 上下行消息协议与实现状态

## 1. 文档定位

本文整理平台与采集服务之间的上行/下行消息约定，并对照当前代码说明实现状态。

当前工程已经具备：

- 采集数据统一后处理：`ProcessResult -> 缓存 -> 上报聚合 -> MQTT/HTTP/TCP 上报`。
- 协议写入统一入口：`CollectionManager.writePoint(...)`、`CollectionManager.writePoints(...)`、`CollectionManager.executeCommand(...)`。
- MQTT 上报 ACK 接收：`MqttReportHandler` 可订阅 ACK topic 并完成上报确认。

当前工程已经补齐：

- MQTT 下行属性设置消息解析与路由。
- MQTT 下行服务调用消息解析与路由。
- 云端下行消息执行后的统一响应发布链路。

当前工程暂未具备：

- MQTT 下行 OTA 升级的实际执行链路。
- `thing.ota.progress` 的真实进度生产链路。

## 3. 当前 MQTT 上报链路

核心入口：

- `CollectorDataPostProcessor`
- `CacheReportService`
- `ReportManager`
- `MqttReportHandler`

链路说明：

1. 协议采集器读取点位并生成 `ProcessResult`。
2. 缓存后处理把结果写入缓存、Redis Stream、历史存储，并调用上报聚合。
3. `CacheReportService` 将点位变化写入设备影子。
4. 影子 flush 时构造 `ReportData`。
5. `MqttReportHandler` 按配置发布 MQTT 消息。

默认 MQTT topic 模板：

```text
iot/device/{productKey}/{deviceName}/{method}
```

代码会把 method 中的点号转换成 topic 路径，例如：

```text
thing.property.post -> thing/property/post
```

因此默认属性上报 topic 形态为：

```text
iot/device/{productKey}/{deviceName}/thing/property/post
```

MQTT JSON 上报消息体当前由 `MqttReportHandler.buildJsonPayload(...)` 生成，主要字段为：

```json
{
  "id": "message-id",
  "version": "1.0",
  "method": "thing.property.post",
  "deviceId": "device-1",
  "timestamp": 1710000000000,
  "params": {
    "sqs": 25
  },
  "quality": {
    "sqs": "GOOD"
  },
  "propertyTs": {
    "sqs": 1710000000000
  },
  "metadata": {
    "pointId": "p1",
    "pointCode": "sqs"
  }
}
```

## 4. 当前 MQTT 接收能力

工程里有两套 MQTT 接收逻辑，需要区分：

| 位置 | 用途 | 当前行为 |
| --- | --- | --- |
| `core/report/handler/MqttReportHandler` | 统一数据上报通道 | 订阅 ACK 和下行 topic；ACK 消息进入确认逻辑，非 ACK 消息转给 `MqttDownlinkService`。 |
| `core/collector/protocol/mqtt/MqttCollector` | MQTT 作为一种采集协议 | 订阅点位 topic，收到消息后更新 MQTT 点位最新值，并调用 `ingestPushedValue(...)` 进入统一后处理链。 |

结论：

- MQTT 采集协议自身的入站采集是已实现的。
- 平台通过 MQTT 下发控制指令，再转成 Modbus/OPC/SNMP/IEC 等协议写入，这条链路已支持 `thing.property.set` 和 `thing.service.invoke`。

## 5. 下行属性设置目标约定

建议沿用现有消息结构，将 `method` 作为业务类型，`params` 作为待写属性集合。

示例：

```json
{
  "id": "123456789",
  "version": "1.0",
  "method": "thing.property.set",
  "deviceId": "device-1",
  "timestamp": 1710000000000,
  "params": {
    "sqs": 25
  }
}
```

目标处理语义：

1. 根据 topic 或 payload 解析 `productKey`、`deviceName`、`deviceId`。
2. 根据 `params` 的属性名匹配 `DataPoint.pointCode` 或 `DataPoint.reportField`。
3. 找到内部设备 `deviceId` 和点位 `DataPoint`。
4. 调用 `CollectionManager.writePoints(deviceId, Map<DataPoint, Object>)`。
5. 按每个点位写入结果发布响应消息。

当前状态：

- 第 1 步到第 5 步已实现。
- `MqttDownlinkService` 支持从 payload 或 topic 解析设备。
- 点位匹配顺序覆盖 `reportField`、`pointAlias`、`pointCode`、`pointId`、`pointName`。
- `CollectionManager.writePoints(...)` 已接入具体协议写入逻辑。
- 写入成功后不直接伪造 reported，仍等待采集回读确认。

## 6. 下行服务调用目标约定

示例：

```json
{
  "id": "123456789",
  "version": "1.0",
  "method": "thing.service.invoke",
  "deviceId": "device-1",
  "timestamp": 1710000000000,
  "params": {
    "service": "reset",
    "args": {
      "mode": "soft"
    }
  }
}
```

目标处理语义：

1. 解析目标设备。
2. 将 `params.service` 映射为协议命令名。
3. 调用 `CollectionManager.executeCommand(deviceId, command, params)`。
4. 发布服务调用响应。

当前状态：

- MQTT 下行解析已实现。
- `command/service/identifier/serviceId` 会作为命令名候选。
- 已路由到 `CollectionManager.executeCommand(...)`。
- 已支持通过 `collector.report.mqtt.service-command-mappings` 做全局服务名映射；未配置时回退原字段值。

## 7. 配置推送与 OTA

### 7.1 配置推送

示例：

```json
{
  "id": "123456789",
  "version": "1.0",
  "method": "thing.config.push",
  "deviceId": "device-1",
  "timestamp": 1710000000000,
  "params": {
    "configVersion": "v2",
    "reload": true
  }
}
```

当前状态：

- MQTT 下行 method 已能被 `MqttDownlinkService` 识别并执行。
- 默认会按单设备 `collection` 类型触发配置刷新。
- 支持通过 `configType/type/scope/syncType` 指定 `device/points/connection/collection/all`。
- `type=all` 且未显式带设备时，会触发 `ConfigSyncService.triggerManualSync()` 做异步全量同步。
- 配置事件会继续复用 `ConfigManager` 和 `CollectionScheduler`，对运行中设备做缓存刷新与重载。

## 10. TCP Binary 认证与消息体

示例业务体：

```json
{
  "messageId": "123456789",
  "version": "1.0",
  "method": "auth",
  "productKey": "efCs2ruTcmchWF61",
  "deviceName": "fjb_001",
  "clientId": "efCs2ruTcmchWF61.fjb_001",
  "username": "fjb_001&efCs2ruTcmchWF61",
  "password": "9815d27ebedb262a71a074a726156b9516339a7419272bb8dcff0017370fbaec"
}
```

```json
{
  "messageId": "123456789",
  "version": "1.0",
  "method": "thing.property.post",
  "params": {
    "sqs": 25
  }
}
```

当前实现：

- `BinaryProtocolAdapter` 是 TCP 上报侧编码器。
- 实际二进制帧格式为：
  - `magic`：1 字节，固定 `0x7E`
  - `protocolVersion`：1 字节，固定 `0x01`
  - `messageType`：1 字节，固定 `0x01`
  - `totalLength`：4 字节
  - `messageIdLength`：2 字节
  - `messageId`：UTF-8 字节
  - `methodLength`：2 字节
  - `method`：UTF-8 字节
  - `body`：JSON 编码后的完整 `IoTMessage`
- TCP Binary 下行解码暂未实现。

## 11. 字段说明

| 字段 | 说明 | 当前代码来源 |
| --- | --- | --- |
| `id` / `messageId` | 消息唯一标识 | MQTT 上报使用 `id`；TCP IoTMessage 使用 `messageId`，JSON 编码时输出 `id`。 |
| `version` | 协议版本号 | 默认 `1.0`。 |
| `method` | 消息方法类型 | 见第 2 节。 |
| `productKey` | 产品密钥 | 上报时来自 `collector.report.mqtt.gateway-product-key` 或 `ReportIdentityResolver`。 |
| `deviceName` | 云端设备名 | 上报时来自 `gatewayDeviceName`、设备映射或原始设备标识。 |
| `clientId` | 客户端 ID | TCP 认证消息使用 `productKey.deviceName`。 |
| `username` | 用户名 | TCP 认证消息使用 `deviceName&productKey`。 |
| `password` | 密码 | 来自上报配置，代码不负责生成 SHA-256。 |
| `params` | 业务参数 | 上行属性为点位字段和值；下行属性设置也建议使用同一结构。 |
| `quality` | 质量信息 | 上报时可携带点位质量。 |
| `propertyTs` | 属性时间戳 | 上报时可携带点位时间戳。 |
| `metadata` | 扩展元数据 | 上报时携带点位 ID、地址、单位、数据类型等。 |

## 12. 后续实现建议

已新增独立的 `MqttDownlinkService`，`MqttReportHandler` 只负责 MQTT 收包、ACK 处理和响应发布。

后续建议继续拆分和补齐：

1. 将 `MqttDownlinkService` 内部的 method 分派拆成独立 router，便于继续扩展 OTA 和更多下行能力。
2. 将点位匹配逻辑抽成 `DevicePointResolver`，统一复用到 HTTP/API 反控场景。
3. 为影子历史补长期审计存储，降低 Redis list 只做短期留存的限制。
4. 为 `thing.config.push` 补充内联配置载荷模型，并为 `thing.ota.upgrade` 接入真实执行链路。
