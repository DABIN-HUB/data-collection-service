# 物联网云平台对接最优架构方案

## 1. 最终结论

本项目对接 `qqqqq/` 中物联网云平台的最优方案是：

```text
工业现场采集网关 + 云平台 Alink 网关适配层
```

而不是：

```text
普通 MQTT 直连设备
```

也不是：

```text
在 MqttReportHandler 里继续堆 topic 模板、payload 分支、拓扑、注册、OTA
```

最终架构必须把四类模型彻底分开：

1. 采集域模型：`ProcessResult`、`DataPoint`、`ReportData`、缓存、历史、Redis Stream、影子。
2. 云端身份模型：`productKey`、`deviceName`、`deviceSecret`、网关设备、子设备、逻辑聚合设备。
3. 云平台协议模型：`thing.property.post`、`thing.event.post`、`thing.topo.add`、`thing.auth.register.sub`、`thing.event.property.pack.post`、`thing.ota.*`。
4. 传输模型：MQTT 连接、订阅、发布、ACK、重连、QoS、限流。

当前仓库已经具备一条可用的采集到上报闭环，但云平台适配还没有独立成层。由于本次目标是追求架构最优，而不是低成本兼容旧实现，所以重构时允许直接清理、删除、替换此前不合理的上报和 MQTT 相关代码；不要求保留旧 topic、旧配置、旧上报绑定输入或旧 handler 入口的兼容能力。前提只有一个：必须保证与云平台 Alink 契约对接无误，并把数据上报链路做成职责清晰、模型稳定、可观测、可扩展、可长期维护的优秀链路。

### 1.1 本次重构硬约束

1. 架构最优优先于旧代码兼容。
2. 之前代码里职责混乱、阻碍分层、只为历史兼容存在的部分，可以直接删除后重构。
3. 不做旧 `iot/device` topic、旧 `collector.report.mqtt` 配置、旧上报绑定输入、旧 `MqttReportHandler` 业务入口的兼容保留。
4. 在保证云平台 `/sys/{productKey}/{deviceName}/{method_path}`、`method/params`、`_reply`、网关/子设备语义完全正确的前提下，优先把数据上报链路做到最优。
5. 验收标准不是“旧用法还能跑”，而是“云平台契约正确、上报链路优秀、职责边界清楚、后续拓扑/注册/批量/OTA 扩展不返工”。
6. 明确原则：因为追求架构最优，所以之前的代码需要清理的可以直接删除，然后重构；不要做兼容；在保证和云平台对接无误的情况下，要保证数据上报这块链路优秀。

## 2. 云平台契约基线

`qqqqq/` 中的文档整体是 Alink 风格协议模型，本项目必须按这个契约建模。

### 2.1 设备身份

云平台设备身份是三元组：

```text
productKey
deviceName
deviceSecret
```

它不同于本项目内部的：

```text
deviceId
pointId
pointCode
collector instance id
```

网关场景下必须明确三类云端设备：

1. 直连设备
2. 网关设备
3. 网关子设备

对本项目来说，最佳形态是：

1. 采集服务实例在云平台上表现为一个网关设备。
2. 现场 PLC、仪表、控制器、机组、产线段在云平台上表现为子设备或逻辑聚合子设备。
3. 网关代理子设备进行属性上报、事件上报、下行反控、拓扑管理、动态注册和批量上报。

### 2.2 MQTT Topic

统一 Topic 格式：

```text
/sys/{productKey}/{deviceName}/{method_path}
```

`method_path` 是 method 的点号转斜杠：

```text
thing.property.post -> thing/property/post
thing.event.post -> thing/event/post
thing.service.invoke -> thing/service/invoke
```

回复主题：

```text
原主题 + _reply
```

例如：

```text
/sys/{productKey}/{deviceName}/thing/property/post_reply
```

### 2.3 消息体

通用消息结构：

```json
{
  "id": "message-id",
  "version": "1.0",
  "method": "thing.property.post",
  "params": {
    "temperature": 25.6
  }
}
```

最优实现里，`method` 必须枚举化，不能散落为字符串。

必须支持的一等 method：

```text
thing.state.update
thing.property.post
thing.property.set
thing.event.post
thing.service.invoke
thing.config.push
thing.ota.upgrade
thing.ota.progress
thing.topo.add
thing.topo.delete
thing.topo.get
thing.topo.change
thing.auth.register
thing.auth.register.sub
thing.event.property.pack.post
```

### 2.4 网关子设备语义

`qqqqq/设备网关与子设备.md` 里最关键的约束是：

1. 子设备属性上报、事件上报、服务调用使用和直连设备相同的 topic 与消息体。
2. 网关设备独有能力包括拓扑、子设备动态注册、批量上报。
3. 拓扑关系可以后台绑定，也可以协议绑定。
4. 网关批量上报使用 `thing.event.property.pack.post`。

因此本项目不能只做“一个 MQTT client 往云端发点位”。它必须成为云平台语义上的网关设备。

## 3. 当前项目真实状态

以下判断基于当前代码和文档状态。

### 3.1 已具备能力

当前项目已具备：

1. 多协议采集与统一后处理。
   - 入口：`CollectorDataPostProcessor`
   - 结果模型：`ProcessResult`
   - 后处理管线：`TelemetryPostProcessPipeline`

2. 实时流、历史存储、上报后处理阶段化。
   - Redis Stream：`StreamTelemetryPostProcessStage`
   - TDengine 历史：`HistoryTelemetryPostProcessStage`
   - 云端上报：`ReportTelemetryPostProcessStage`

3. 点位纵转横的雏形。
   - `CacheReportService.reportPoint(...)` 将点位写入影子。
   - `ShadowManager` 聚合最新属性。
   - flush 时构造 `ReportData.properties`。

4. 多本地点位映射到同一云端设备的雏形。
   - `CloudPointMappingResolver` 支持 `additionalConfig.cloudBindings`。
   - 多个点位可配置相同 `productKey/deviceName`。

5. MQTT 上行。
   - `ReportManager`
   - `MqttReportHandler`
   - ACK 等待和回复处理

6. MQTT 下行基础能力。
   - `thing.property.set`
   - `thing.service.invoke`
   - `thing.config.push`
   - 执行结果通过 `_reply` 回复

7. 设备影子基础能力。
   - `reported`
   - `desired`
   - `delta`
   - Redis CAS
   - TTL
   - desired 历史审计

### 3.2 当前不足

当前不足不是“能不能连”，而是架构边界还不够干净：

1. `MqttReportHandler` 仍然过重。
   - 它同时负责 MQTT 连接、发布、订阅、ACK、下行转发、topic 变量替换、JSON payload 构造。
   - 长期继续加拓扑、注册、批量、OTA 会不可维护。

2. `MqttDownlinkService` 仍然是单类分支处理。
   - 当前能支撑 property/set、service/invoke、config/push。
   - 加上 `thing.topo.change`、`thing.auth.register.sub_reply`、`thing.ota.upgrade` 后会失控。

3. 云平台协议没有独立 DTO 和 codec。
   - `ReportData` 当前被直接编码成 MQTT payload。
   - 这会把采集快照模型和云平台协议模型绑死。

4. 云端身份模型不清晰。
   - 当前 `deviceId`、`gatewayDeviceName`、`cloudDeviceId`、`rawDeviceId`、`productKey` 主要依赖 metadata 和 topic 模板传递。
   - 下行路由和拓扑同步会因此变脆。

5. 聚合能力是隐式能力。
   - “纵转横”依赖影子。
   - “多本地设备 -> 一个云端子设备”依赖多个点位写同一 `cloudBindings.aggregateTargetId`。
   - 缺少显式聚合目标、字段冲突策略、窗口策略和来源追踪。

6. 网关拓扑域缺失。
   - 还没有正式 `CloudTopologyService`。
   - 还没有 `thing.topo.add/delete/get/change` 的完整链路。

7. 子设备动态注册域缺失。
   - 还没有正式 `CloudSubDeviceRegisterService`。
   - 还没有 `thing.auth.register.sub` 的标准生命周期。

8. OTA 域缺失。
   - `thing.ota.upgrade` 当前不能执行真实升级。
   - `thing.ota.progress` 只有消息构造能力，没有真实进度生产链路。

9. 可靠投递还不完整。
   - 当前有 ACK 和重试，但没有持久化发送队列、ACK 状态机、死信队列和重放工具。

## 4. 最优目标架构

最终目标架构：

```text
现场协议采集层
  Modbus / S7 / OPC UA / BACnet / SNMP / IEC / MQTT ...
    -> ProcessResult
    -> TelemetryPostProcessPipeline
    -> CloudAggregationService
    -> CloudTelemetryService
    -> CloudTelemetryMessage
    -> AlinkTopicBuilder + AlinkPayloadEncoder
    -> CloudMqttTransport
    -> 物联网云平台
```

下行目标架构：

```text
物联网云平台
  -> CloudMqttTransport
  -> AlinkTopicParser + AlinkPayloadDecoder
  -> CloudDownlinkMessage
  -> CloudDownlinkDispatcher
  -> PropertySetHandler / ServiceInvokeHandler / ConfigPushHandler
  -> TopologyHandler / RegisterHandler / OtaHandler
  -> CollectionManager / ConfigSyncService / ShadowManager / CloudOtaService
```

核心原则：

1. 采集运行时不关心 `/sys/{pk}/{dn}/...`。
2. MQTT 传输层不关心 `thing.property.post` 的业务语义。
3. Alink codec 只负责编解码 topic 和 payload，不执行采集写入。
4. 云平台集成域负责身份、映射、聚合、拓扑、注册、OTA。
5. 影子继续保留，但从“隐式聚合实现”升级为“云端 reported/desired 同步基础设施”。

## 5. 最优模块拆分

建议新增：

```text
src/main/java/com/wangbin/collector/core/cloud/
  model/
  mapping/
  aggregation/
  service/
  topology/
  register/
  shadow/
  ota/
  protocol/
    alink/
      dto/
      codec/
      topic/
  transport/
    mqtt/
```

### 5.1 `core/cloud/model`

定义云平台一等模型。

建议模型：

```text
CloudGatewayIdentity
CloudDeviceIdentity
CloudSubDeviceBinding
CloudDeviceType
CloudTelemetryMessage
CloudPropertyPost
CloudEventPost
CloudStateUpdate
CloudPropertySet
CloudServiceInvoke
CloudConfigPush
CloudOtaUpgrade
CloudOtaProgress
CloudTopoAdd
CloudTopoDelete
CloudTopoGet
CloudTopoChange
CloudSubDeviceRegister
CloudPackReport
```

关键点：

1. `CloudDeviceIdentity` 只表达云端身份。
2. 本地 `deviceId` 不应混进 `productKey/deviceName`。
3. 凭据使用 `secretRef`，避免后续把 `deviceSecret` 明文散落在配置和日志里。

### 5.2 `core/cloud/protocol/alink`

这是最优方案的第一刀。

建议类：

```text
AlinkMethod
AlinkTopicBuilder
AlinkTopicParser
AlinkPayloadEncoder
AlinkPayloadDecoder
AlinkMessageEnvelope
AlinkReply
```

要求：

1. `AlinkMethod` 枚举化全部 method。
2. Topic builder 只做 topic。
3. Payload encoder 只做 JSON。
4. Decoder 返回强类型 `CloudDownlinkMessage`，不要返回裸 `JsonNode` 给业务类继续猜。
5. 只支持云平台标准 `/sys/{pk}/{dn}`。旧 `iot/device/{pk}/{dn}` 不再作为兼容目标，相关代码可直接删除。

### 5.3 `core/cloud/mapping`

负责内部设备、点位、云端设备之间的映射。

建议类：

```text
CloudIdentityResolver
CloudPointMappingResolver
CloudDeviceRegistry
CloudRouteResolver
CloudFieldMapper
```

职责：

1. `local deviceId -> gateway identity`
2. `DataPoint -> cloud device identity`
3. `cloud field -> local DataPoint`
4. `cloud productKey/deviceName -> local route`
5. `service identifier -> protocol command`

当前 `ReportIdentityResolver` 可以演进为 `CloudIdentityResolver`，但不要继续承担 payload 或 transport 责任。

### 5.4 `core/cloud/aggregation`

这是必须显式新增的一层。

它负责两件事：

1. 纵向点位流转横向属性 JSON。
2. 多个本地采集设备聚合为一个云端逻辑子设备。

建议类：

```text
CloudAggregateTarget
CloudAggregateKey
CloudAggregateSnapshot
CloudAggregationPolicy
CloudAggregationService
CloudFieldConflictResolver
CloudSourceTrace
```

显式聚合目标示例：

```json
{
  "aggregateTargetId": "line-1-energy-summary",
  "cloudIdentity": {
    "productKey": "pk_energy",
    "deviceName": "line1_summary"
  },
  "sources": [
    {
      "localDeviceId": "meter-a",
      "pointId": "voltage_a",
      "field": "voltageA"
    },
    {
      "localDeviceId": "meter-b",
      "pointId": "current_total",
      "field": "currentTotal"
    }
  ],
  "policy": {
    "flushMode": "WINDOW",
    "windowMs": 1000,
    "conflictPolicy": "LATEST_WINS"
  }
}
```

必须支持的策略：

```text
flushMode:
  IMMEDIATE
  WINDOW
  PERIODIC

conflictPolicy:
  LATEST_WINS
  SOURCE_PRIORITY
  REJECT_CONFLICT

reportMode:
  SINGLE
  PACK
  HYBRID
```

不要继续依赖弱结构隐式实现跨设备聚合。运行时不保留旧绑定输入兼容，重构后统一收敛到 `cloudBindings` 和 `CloudAggregateTarget`。

### 5.5 `core/cloud/service`

编排层。

建议类：

```text
CloudTelemetryService
CloudTelemetryAssembler
CloudCommandService
CloudDownlinkDispatcher
CloudShadowSyncService
CloudTopologyService
CloudRegisterService
CloudOtaService
CloudReliableReportService
```

职责：

1. 把采集结果变成云平台消息。
2. 把云平台下行变成本地动作。
3. 组织影子、拓扑、注册、OTA 和可靠投递。

### 5.6 `core/cloud/transport/mqtt`

MQTT 只做传输。

建议类：

```text
CloudMqttClient
CloudMqttPublisher
CloudMqttSubscriber
CloudMqttAckTracker
CloudMqttConnectionManager
CloudMqttTransportProperties
```

它只接收：

```text
topic
payload
qos
retained
```

它不应该知道：

```text
thing.property.post
thing.topo.add
DataPoint
CollectionManager
ShadowManager
```

## 6. 设备建模最优方案

### 6.1 云平台侧

云端应看到：

1. 一个采集网关设备。
2. 多个被代理的子设备。
3. 子设备可以是现场物理设备，也可以是逻辑聚合设备。
4. 每个子设备有独立属性、事件、影子、服务和控制入口。

### 6.2 本项目侧

本地要区分三类对象：

```text
LocalDevice
  当前采集系统里的实际采集设备，例如 PLC、仪表、OPC UA Server。

CloudDevice
  云平台上的 productKey/deviceName 设备。

CloudAggregateTarget
  多点位、多本地设备汇成的云端逻辑设备。
```

### 6.3 设备级配置

建议新增结构化云端配置，先可落在扩展配置中，后续再独立表或配置模型：

```json
{
  "cloud": {
    "enabled": true,
    "deviceType": "GATEWAY",
    "productKey": "pk_gateway",
    "deviceName": "collector-1",
    "secretRef": "secret://collector-1"
  }
}
```

子设备：

```json
{
  "cloud": {
    "enabled": true,
    "deviceType": "SUB_DEVICE",
    "productKey": "pk_motor",
    "deviceName": "motor-001",
    "secretRef": "secret://motor-001",
    "gateway": {
      "productKey": "pk_gateway",
      "deviceName": "collector-1"
    }
  }
}
```

### 6.4 点位级配置

点位级云端映射统一使用结构明确的 `cloudBindings`：

```json
{
  "cloudBindings": [
    {
      "aggregateTargetId": "motor-001",
      "productKey": "pk_motor",
      "deviceName": "motor-001",
      "field": "temperature",
      "messageType": "PROPERTY"
    }
  ]
}
```

存量配置处理原则：

```text
一次性配置迁移脚本 / 人工整理 -> cloudBindings -> CloudAggregateTarget
```

不在运行时代码里保留旧绑定结构兼容解析。

### 6.5 字段治理

云端字段名以物模型 identifier 为准。

本地点位字段解析优先级：

```text
cloudBindings.field
reportField
pointAlias
pointCode
pointId
pointName
```

但最终应收敛到显式 `cloudBindings.field`，不要长期依赖模糊匹配。

## 7. 上行链路最优方案

### 7.1 单设备属性上报

```text
ProcessResult
-> CloudAggregationService.apply(...)
-> CloudAggregateSnapshot
-> CloudTelemetryAssembler.propertyPost(...)
-> CloudPropertyPost
-> AlinkPayloadEncoder
-> AlinkTopicBuilder
-> CloudMqttTransport.publish(...)
```

payload：

```json
{
  "id": "message-id",
  "version": "1.0",
  "method": "thing.property.post",
  "params": {
    "temperature": 25.6,
    "humidity": 60
  }
}
```

topic：

```text
/sys/{productKey}/{deviceName}/thing/property/post
```

### 7.2 事件上报

事件不应混在属性绑定里。

建议独立事件绑定：

```json
{
  "cloudEvents": [
    {
      "identifier": "over_temperature",
      "triggerField": "temperature",
      "condition": ">",
      "threshold": 80
    }
  ]
}
```

payload：

```json
{
  "id": "message-id",
  "version": "1.0",
  "method": "thing.event.post",
  "params": {
    "identifier": "over_temperature",
    "value": {
      "temperature": 86.5
    },
    "time": 1739265600000
  }
}
```

### 7.3 网关批量上报

`thing.event.property.pack.post` 是网关场景的推荐高阶能力。

链路：

```text
CloudAggregateSnapshot[]
-> CloudPackReportAssembler
-> CloudPackReport
-> AlinkPayloadEncoder
-> /sys/{gatewayPk}/{gatewayDn}/thing/event/property/pack/post
```

payload：

```json
{
  "id": "message-id",
  "version": "1.0",
  "method": "thing.event.property.pack.post",
  "params": {
    "properties": {
      "cpuUsage": 45.2
    },
    "events": {},
    "subDevices": [
      {
        "identity": {
          "productKey": "pk_motor",
          "deviceName": "motor-001"
        },
        "properties": {
          "temperature": 36.5
        },
        "events": {}
      }
    ]
  }
}
```

推荐策略：

```text
SINGLE:
  每个云端设备单独上报，便于调试。

PACK:
  网关按窗口打包上报，适合生产高吞吐。

HYBRID:
  普通属性打包，告警事件和控制回执单独上报。
```

默认建议：

```text
开发 / 联调阶段：SINGLE
生产稳定阶段：HYBRID
高吞吐现场：PACK
```

## 8. 下行链路最优方案

### 8.1 总链路

```text
MQTT message
-> CloudMqttSubscriber
-> AlinkTopicParser
-> AlinkPayloadDecoder
-> CloudDownlinkMessage
-> CloudDownlinkDispatcher
-> method handler
```

### 8.2 属性设置

`thing.property.set` 的最优语义：

1. 解析云端身份。
2. 根据 `CloudRouteResolver` 找到本地设备和点位。
3. 写入影子 `desired`。
4. 调用 `CollectionManager.writePoints(...)`。
5. 返回字段级响应。
6. 不伪造 `reported`，等待采集回读后清理 `delta`。

这与当前实现一致，应保留。

需要优化的是：

1. 设备解析从 `topic contains + payload 猜测` 改为 `AlinkTopicParser + CloudRouteResolver`。
2. 点位解析从多字段模糊匹配逐步收敛到显式 `CloudFieldMapper`。

### 8.3 服务调用

`thing.service.invoke` 的最优语义：

1. 平台服务 identifier 映射为本地协议命令。
2. 调用 `CollectionManager.executeCommand(...)`。
3. 记录请求状态和审计。
4. 返回 `_reply`。

建议映射模型：

```json
{
  "serviceMappings": [
    {
      "productKey": "pk_motor",
      "deviceName": "motor-001",
      "service": "reset",
      "localDeviceId": "plc-1",
      "command": "soft_reset",
      "timeoutMs": 5000
    }
  ]
}
```

### 8.4 配置推送

当前 `thing.config.push` 已能触发配置刷新，这是合理的最小闭环。

最优演进：

1. 保留“触发刷新”语义。
2. 新增“内联配置载荷”语义。
3. 引入配置版本号、幂等 key 和审计记录。
4. 明确 configType：

```text
device
points
connection
collection
cloud-mapping
cloud-topology
all
```

### 8.5 拓扑变更

`thing.topo.change` 只应由 `CloudTopologyHandler` 处理。

职责：

1. 解析平台下发的子设备绑定/解绑。
2. 更新 `CloudDeviceRegistry`。
3. 更新本地拓扑缓存。
4. 必要时触发订阅、路由和聚合目标刷新。

### 8.6 OTA 升级

`thing.ota.upgrade` 不能放在普通下行类中临时执行。

必须进入 `CloudOtaService`：

```text
CloudOtaTask
CloudOtaTaskRepository
CloudOtaDownloadService
CloudOtaVerifier
CloudOtaExecutor
CloudOtaProgressReporter
```

状态机：

```text
CREATED
DOWNLOADING
DOWNLOADED
VERIFYING
INSTALLING
SUCCESS
FAILED
ROLLING_BACK
ROLLED_BACK
CANCELLED
```

进度通过 `thing.ota.progress` 上报。

## 9. 影子最优方案

当前 `ShadowManager` 是重要基础能力，应保留并上移语义。

最优定位：

```text
本地采集 reported 聚合
云端 desired 接收
delta 计算
下行反控状态协同
上行属性快照来源
```

属性设置语义：

1. 平台下发 `thing.property.set`。
2. 本地写入 `desired`。
3. 协议写入现场设备。
4. 等采集回读产生 `reported`。
5. `reported == desired` 后自动清理 `delta`。

不要做：

```text
下行写入成功后立即伪造 reported
```

需要新增：

```text
CloudShadowFieldMapper
CloudShadowConflictPolicy
CloudShadowSyncService
```

## 10. 拓扑与注册最优方案

### 10.1 CloudDeviceRegistry

新增 `CloudDeviceRegistry`，统一维护：

```text
gateway identity
sub-device identity
logical aggregate device identity
local route
secretRef
topology status
registration status
```

建议状态：

```text
LOCAL_ONLY
REGISTER_REQUIRED
REGISTERED
TOPOLOGY_BOUND
TOPOLOGY_UNBOUND
DISABLED
ERROR
```

### 10.2 CloudTopologyService

支持：

```text
thing.topo.add
thing.topo.delete
thing.topo.get
thing.topo.change
```

拓扑关系不能只靠点位级云端绑定推导。必须有设备级或聚合目标级显式关系。

### 10.3 CloudSubDeviceRegisterService

支持：

```text
thing.auth.register.sub
```

注意：

1. 子设备动态注册不会创建设备。
2. 子设备必须在平台预创建。
3. 注册用于获取 `deviceSecret`。
4. 注册成功后应持久化 `secretRef` 并驱动拓扑绑定。

### 10.4 直连动态注册

本项目作为采集网关，直连设备动态注册不是优先项。

优先级：

```text
子设备动态注册 > 网关拓扑 > 直连设备动态注册
```

## 11. 可靠投递最优方案

当前 ACK 能力只能算基础确认，不是完整可靠投递。

完整线上能力需要：

```text
CloudOutboxMessage
CloudOutboxRepository
CloudAckStateMachine
CloudDeadLetterQueue
CloudReplayService
CloudReportMetrics
```

状态机：

```text
CREATED
QUEUED
SENDING
SENT
ACKED
TIMEOUT
RETRYING
FAILED
DEAD
```

关键要求：

1. Broker 不可达时消息不能只在内存里。
2. 重连后能恢复未确认消息。
3. 消息 ID 稳定，支持幂等去重。
4. 多次失败进入死信。
5. 提供人工重放入口。

可靠投递不应阻塞第一阶段抽层，但必须进入产品化路线。

## 12. 配置模型最优方案

当前配置：

```yaml
collector:
  report:
    mqtt:
      broker-url:
      topic-prefix:
      gateway-product-key:
      gateway-device-name:
```

问题：

1. 传输配置和云平台协议配置混在一起。
2. `collector.report.mqtt` 与 `collector.mqtt` 容易混淆。
3. topic prefix 默认仍偏旧格式。

最优配置应拆成两层。

### 12.1 传输层

```yaml
collector:
  cloud:
    transport:
      mqtt:
        broker-url: tcp://127.0.0.1:1883
        client-id: collector-1
        username:
        password:
        qos: 1
        clean-session: true
        keep-alive-interval: 60
        ack-timeout-seconds: 5
```

### 12.2 云平台协议层

```yaml
collector:
  cloud:
    provider: alink
    gateway:
      product-key: pk_gateway
      device-name: collector-1
      secret-ref: secret://collector-1
    topics:
      prefix: /sys
      reply-suffix: _reply
    report:
      mode: hybrid
      pack-enabled: true
      aggregation-window-ms: 1000
    downlink:
      property-set-enabled: true
      service-invoke-enabled: true
      config-push-enabled: true
      topology-enabled: true
      register-enabled: true
      ota-enabled: false
```

### 12.3 配置收敛策略

重构后只保留清晰配置边界：

```text
collector.cloud.* 负责云平台接入
collector.mqtt.* 仅负责 MQTT 作为采集协议
collector.report.mqtt 删除，不做 deprecated 兼容
```

如果现场已有旧配置，应通过一次性迁移脚本或人工配置治理迁入 `collector.cloud.*`，不要在运行时代码里保留双配置读取逻辑。

## 13. 与现有代码的重构关系

### 13.1 `ReportData`

保留为采集域快照。

它适合表达：

```text
deviceId
pointCode
properties
quality
propertyTs
metadata
```

它不应决定：

```text
Alink topic
Alink method DTO
topo payload
register payload
OTA payload
```

### 13.2 `CacheReportService`

可以作为实现参考，但不要求短期保留旧类形态。

中期拆分：

```text
CacheReportService 当前职责
  -> CloudAggregationService
  -> CloudTelemetryService
  -> CloudReportFlushService
```

其中“影子聚合 + dirty flush”的正确语义可以复用；如果旧实现阻碍上报链路最优分层，可以直接拆除并重写为 `CloudAggregationService`。

### 13.3 `ReportIdentityResolver`

升级为：

```text
CloudIdentityResolver
CloudPointMappingResolver
```

它只负责身份和映射，不负责编码、发布、ACK。

### 13.4 `MqttReportHandler`

从：

```text
MQTT 连接 + 发布 + 订阅 + ACK + 下行转发 + Topic 拼装 + Payload 构造
```

收缩为：

```text
CloudMqttTransport
```

### 13.5 `MqttDownlinkService`

从单类分支：

```text
handlePropertySet
handleServiceInvoke
handleConfigPush
OTA 501
```

拆成：

```text
CloudDownlinkDispatcher
CloudPropertySetHandler
CloudServiceInvokeHandler
CloudConfigPushHandler
CloudTopologyHandler
CloudSubDeviceRegisterReplyHandler
CloudOtaUpgradeHandler
```

### 13.6 `IoTProtocolService`

当前偏通用消息构造，后续应被 `core/cloud/protocol/alink` 替代或收敛。

Alink 编码不能散在 `IoTProtocolService`、`MqttReportHandler`、`MqttDownlinkService` 多个地方。

## 14. 推荐实施顺序

### Phase 0：固化现有行为

目标：

1. 不保留旧架构兼容，只固化云平台正确性和核心上报语义。
2. 补齐关键测试，作为重构保护网。

验收：

1. `thing.property.post` 仍能上报。
2. `thing.property.set` 仍能写 desired 并调用 `writePoints`。
3. `thing.service.invoke` 仍能调用 `executeCommand`。
4. `thing.config.push` 仍能触发配置刷新。
5. 影子 CAS 测试仍通过。

### Phase 1：抽 Alink 协议层

新增：

```text
core/cloud/protocol/alink/AlinkMethod
core/cloud/protocol/alink/topic/AlinkTopicBuilder
core/cloud/protocol/alink/topic/AlinkTopicParser
core/cloud/protocol/alink/codec/AlinkPayloadEncoder
core/cloud/protocol/alink/codec/AlinkPayloadDecoder
```

改造：

1. `MqttReportHandler.buildJsonPayload(...)` 迁移到 encoder。
2. `MqttReportHandler.replaceTopicVariables(...)` 迁移到 topic builder。
3. `MqttDownlinkService.resolveMethod(...)` 迁移到 topic parser + decoder。

验收：

1. 现有功能不变。
2. Topic 和 payload 构造不再散落在 MQTT handler。
3. 支持 `/sys/{pk}/{dn}`。
4. 不兼容旧 `iot/device/{pk}/{dn}`，统一验证标准 `/sys/{pk}/{dn}`。

### Phase 2：抽身份、映射、聚合层

新增：

```text
CloudDeviceIdentity
CloudGatewayIdentity
CloudIdentityResolver
CloudPointMappingResolver
CloudAggregateTarget
CloudAggregationService
CloudDeviceRegistry
```

改造：

1. `ReportIdentityResolver` 迁移到云端映射层。
2. 点位云端映射转换为 `CloudAggregateTarget`。
3. `CacheReportService` 调用 `CloudAggregationService`。

验收：

1. “多个点位 -> 一个云端子设备”有显式聚合目标。
2. “多个本地设备 -> 一个云端逻辑设备”有显式来源追踪。
3. 字段冲突策略可配置。

### Phase 3：拆 MQTT 传输和下行分发

1. `MqttReportHandler` 退化为 transport 或被新 transport 替换。

验收：

1. 每个 method 独立 handler。
2. handler 不直接解析 topic 字符串。
3. MQTT 传输层不知道业务 method。

### Phase 4：补网关拓扑与子设备动态注册

```text

CloudTopologyHandler

```

支持：

```text

thing.topo.delete
thing.topo.get
thing.topo.change

```

验收：

1. 网关可主动同步拓扑。
2. 平台下发拓扑变更后本地 registry 更新。
3. 子设备动态注册成功后能保存 secretRef。

## 15. 第一阶段开工任务

不要从“把 topic-prefix 改成 `/sys`”开始。

第一阶段建议直接做协议层抽离：

1. 新增 `AlinkMethod`。
2. 新增 `AlinkTopicBuilder`。
3. 新增 `AlinkTopicParser`。
4. 新增 `AlinkPayloadEncoder`。
5. 新增 `AlinkPayloadDecoder`。
6. 给 property/post、property/set、service/invoke、config/push 建最小 DTO。
7. 改 `MqttReportHandler` 使用 builder + encoder。
8. 改 `MqttDownlinkService` 使用 parser + decoder。
9. 保持现有测试全部通过。
10. 新增 topic/parser/encoder/decoder 单元测试。

这一阶段完成后，旧上报架构可以被新链路替换；验收重点是云平台对接正确和数据上报链路优秀，而不是旧行为完全兼容。

## 16. 明确不推荐方案

以下方案不推荐：

1. 只改 `topic-prefix=/sys` 就上线。
2. 继续在 `MqttReportHandler` 里加 `if method == topo`。
3. 继续在 `MqttDownlinkService` 里堆 OTA、topo、register。
4. 继续通过 `metadata.rawDeviceId` 传核心身份。
5. 把整个采集服务映射成一个普通直连设备。
6. 把 `ReportData` 直接当云平台协议 DTO。
7. 把子设备注册、拓扑、OTA 当普通 MQTT 消息临时处理。

## 17. 最终工程形态

最终工程应形成以下边界：

```text
core/collector
  只管现场协议采集、写入、命令执行。

core/cache
  只管缓存、实时流、历史后处理管线。

core/report
  只保留仍然合理的通用上报抽象；旧 MQTT handler 职责混乱时直接删除并由 core/cloud 接管。

core/cloud
  负责云平台身份、协议、聚合、拓扑、注册、OTA、可靠投递。

core/cloud/protocol/alink
  负责 Alink topic 和 payload 编解码。

core/cloud/transport/mqtt
  负责 MQTT 连接、订阅、发布、ACK、重连。
```

云端最终看到：

1. 一个采集网关设备。
2. 多个网关子设备。
3. 多个逻辑聚合子设备。
4. 每个子设备独立属性、事件、服务、影子。
5. 网关能维护拓扑、动态注册子设备、批量上报和执行 OTA。

这才是技术最优、架构最优、职责最清晰、长期维护成本最低的方案。
