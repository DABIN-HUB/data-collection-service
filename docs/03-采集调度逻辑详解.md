# 采集调度逻辑详解

## 1. 调度核心职责

核心类：`core/collector/scheduler/CollectionScheduler`

调度器负责：

- 设备采集任务启动/停止/重载
- 点位批次切分与时间片分配
- 并发采集与异步处理
- 性能统计与动态调优

## 2. 线程池分工

由 `ThreadPoolConfig` 提供、调度器注入使用：

- `timeSliceScheduler`：时间片触发器
- `batchDispatcherExecutor`：批次任务分发
- `asyncCollectorExecutor`：采集 IO 线程池
- `dataProcessorExecutor`：数据处理线程池

## 3. 时间片调度模型

初始化流程（`@PostConstruct`）：

1. 读取 `collector.scheduler` 配置，标准化时间片数量和间隔。
2. 初始化 `timeSliceTasks`（每个时间片对应任务列表）。
3. `startTimeSliceScheduling()`：为每个时间片注册固定频率任务。
4. 启动动态时间片调整任务。
5. 启动性能监控日志任务。
6. 延迟自动启动所有设备。

执行逻辑（每个时间片）：

1. 读取本时间片的 `DeviceBatchTask` 列表。
2. 对每个批次异步提交 `processDeviceBatch(...)`。
3. 以“当前时间片间隔 - 10ms”为等待上限做 `allOf().get(...)`。
4. 记录时间片执行时长，若超时则告警。

## 4. 设备启动到批次执行

### 4.1 `startDevice(deviceId)` 关键步骤

1. 读取设备与点位配置。
2. 初始化点位自适应采集参数（配置开启时）。
3. 注册采集器 + 建立连接。
4. `scheduleDevicePoints(...)` 生成批次并分配时间片。
5. 调用 `collectionManager.rebuildReadPlans(...)` 构建协议级读计划。
6. 更新运行状态与统计。

### 4.2 批次规划（`DeviceBatchPlanner`）

流程：

1. 先按 `dataType` 分组。
2. 组内按地址数字近似排序。
3. 结合历史性能算“最优批次大小”。
4. 地址跨度过大时切分，避免低效跨段。
5. 小批次合并，超大批次按 100 点切块。
6. 通过哈希+批次索引分配到时间片，尽量均匀。

协议默认批次上限（代码内）：

- `MODBUS_TCP/MODBUS_RTU`：125
- `OPC_UA`：100（默认）
- `MQTT`：30（默认）
- `SNMP`：20（默认）

## 5. 批次采集执行（`processDeviceBatch`）

执行路径：

1. 连接检查，不通则重连。
2. 在 `asyncCollectorPool` 提交 `collectionManager.readPoints(...)`。
3. 使用 `collectTimeoutMs` 做超时保护。
4. 非空结果交给 `dataProcessorPool` 异步处理。
5. 更新成功/失败统计。
6. 按耗时动态调小或调大批次（性能反馈）。

## 6. 采集后处理（`CollectedDataProcessor`）

对每个返回点位值：

1. 记录处理统计。
2. 若设备之前有连续失败，重置点位自适应状态。
3. 启用自适应时，调用 `AdaptiveCollectionUtil.adjustCollectionFrequency(...)` 调整该点位采样间隔。

## 7. 动态时间片调整

入口：`startDynamicTimeSliceAdjustment()`

每个调整周期：

1. 估算系统负载（活跃线程数 / 最大线程数）。
2. 结合活跃设备数和任务数计算目标时间片数。
3. 用 `TimeSliceTuner` 结合平均执行时长/超时标记调节时间片间隔。
4. 配置变化时重建时间片队列并 `rescheduleAllDevices()`。

## 8. 配置更新联动

`handleConfigUpdate(ConfigUpdateEvent)`：

- 设备运行中且配置更新时，触发防抖重启（默认 1 秒）。
- 防止短时间多次配置变更导致频繁启停。

## 9. 调度相关配置

```yaml
collector:
  scheduler:
    initial-time-slice-count: 4
    max-time-slice-count: 12
    min-time-slice-interval-ms: 300
    default-time-slice-interval-ms: 1500
    initial-time-slice-interval-ms: 1500
    dynamic-adjust-interval-ms: 60000
    collect-timeout-ms: 800
  adaptive-collection:
    enabled: true
    adjust-window-ms: 60000
```

## 10. 调度验证建议

1. 启动多个设备并观察 `/monitor/performance`。
2. 人为注入慢设备，观察时间片超时日志和动态调节结果。
3. 修改设备配置，验证防抖重启生效。
4. 对比开启/关闭 `adaptive-collection` 后的任务耗时与失败率。

## 11. 计划调整后的调度契约

详细任务见《16-P0_P1实施任务单与改造方案》的 `SCH-P0-01`，调度实现后续必须遵守：

1. 周期调度定义与单次采集执行分离，单次超时不能永久取消周期任务。
2. 设备停止、配置删除和服务关闭才允许永久取消任务。
3. 超时只影响当前设备当前执行，不得取消同时间片其他设备。
4. 同一设备默认不允许采集重入；上一轮未结束时记录跳过并进入退避判断。
5. 连续失败进入 `DEGRADED` 或 `SUSPENDED`，成功后允许自动恢复。
6. 配置重载和时间片重建必须递增调度代次，旧代次结果不得进入后处理。
7. 设备运行状态以最后成功采集时间、连续失败和调度状态共同计算。

新增回归场景必须包括慢设备隔离、单次超时恢复、停机在途任务隔离、重配不重复采集以及动态时间片切换不丢任务。正常路径的批次规划、采集周期和协议调用次数必须与改造前基线一致。
