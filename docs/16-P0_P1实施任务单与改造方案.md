## 3.1 调度器在途任务取消与设备停机隔离【已完成】

### 3.1.1 问题

当前 `CollectionScheduler` 已经对单批次采集使用 `collectFuture.get(timeout)` 和 `collectFuture.cancel(true)`，但还存在两类缺口：

1. 时间片级超时只会告警，不会取消已经派发到 `batchDispatcher` 的任务。
2. `stopDevice()`、配置重启后，已提交但尚未完成的采集和后处理任务仍可能继续执行。

### 3.1.2 改造目标

目标是实现“任务代际隔离 + 统一取消入口”。

要求：

1. 设备被停机或重启后，旧代际任务结果不能继续落缓存、上报和影子。
2. 时间片超时后，属于该时间片的批次任务必须进入取消态。
3. 动态时间片重建后，旧时间片里的任务即使晚到，也不能污染新调度状态。

### 3.1.3 代码落点

优先修改以下类：

1. `src/main/java/com/wangbin/collector/core/collector/scheduler/CollectionScheduler.java`
2. `src/main/java/com/wangbin/collector/core/collector/scheduler/DeviceBatchTask.java`
3. `src/main/java/com/wangbin/collector/core/collector/scheduler/DeviceScheduleInfo.java`
4. `src/main/java/com/wangbin/collector/core/collector/scheduler/CollectedDataProcessor.java`

### 3.1.4 改造方案

建议新增以下结构：

```java
class DeviceScheduleInfo {
    String deviceId;
    long generation;
    boolean running;
}

class DeviceBatchTask {
    String deviceId;
    long generation;
    int timeSliceIndex;
    AtomicBoolean cancelled;
}
```

在 `CollectionScheduler` 中新增：

1. `ConcurrentMap<String, Long> deviceGenerations`
2. `ConcurrentMap<String, Set<Future<?>>> deviceInFlightCollectFutures`
3. `ConcurrentMap<String, Set<CompletableFuture<?>>> deviceInFlightProcessFutures`

核心动作：

1. `startDevice()` 时为设备生成新的 `generation`。
2. `scheduleDevicePoints()` 生成的 `DeviceBatchTask` 带上当前 `generation`。
3. `processDeviceBatch()` 开始前检查：
   - 设备是否仍在运行。
   - task generation 是否等于当前 generation。
   - task 是否已取消。
4. `collectFuture`、数据处理 future 都注册到 in-flight registry。
5. `stopDevice()`、配置重启、时间片级取消时统一：
   - 标记设备 generation 失效
   - 取消 in-flight future
   - 清理旧批次
6. `processCollectedData()` 前再次检查 generation，防止旧结果落地。

### 3.1.5 测试建议

新增测试：

1. `CollectionSchedulerShouldCancelCollectFutureOnCollectTimeout`
2. `CollectionSchedulerShouldNotProcessStoppedDeviceInflightResults`
3. `CollectionSchedulerShouldIgnoreStaleGenerationBatchResult`

### 3.1.6 验收标准

1. 批次采集超时后，不再继续进入 `processCollectedData()`。
2. `stopDevice()` 后，旧批次即使晚完成，也不会继续写缓存或上报。
3. 配置重启后，仅新 generation 的任务有效。

## 3.2 动态时间片重配安全切换【已完成】

### 3.2.1 问题

当前 `applyTimeSliceConfigUpdate()` 已能更新时间片数量和间隔，并调用 `rebuildTimeSliceAssignments()`，但切换过程仍偏“立即替换”。

主要风险：

1. 旧时间片任务尚在运行时，新时间片已开始派发。
2. 同一设备批次可能短时重复执行。

### 3.2.2 改造目标

实现“可重建，但不重跑”的安全时间片切换。

### 3.2.3 代码落点

1. `src/main/java/com/wangbin/collector/core/collector/scheduler/CollectionScheduler.java`
2. `src/main/java/com/wangbin/collector/core/collector/scheduler/TimeSliceTuner.java`

### 3.2.4 改造方案

建议把时间片配置抽成一个不可变快照：

```java
record TimeSliceRuntimeConfig(
    long revision,
    int sliceCount,
    int sliceIntervalMs
) {}
```

核心调整：

1. `TIME_SLICE_COUNT` 和 `TIME_SLICE_INTERVAL` 继续保留，但新增 `timeSliceRevision`。
2. 每次 `applyTimeSliceConfigUpdate()`：
   - 先生成新 revision
   - 重建 `timeSliceTasks`
   - 重新注册定时 future
3. 每个 `DeviceBatchTask` 带 `timeSliceRevision`。
4. `executeTimeSlice()` 执行时只处理当前 revision 任务。
5. 如果 `CompletableFuture.allOf(...).get(...)` 超时：
   - 记录 overload
   - 取消本片已注册的在途 future
   - 标记该轮 slice execution failed

### 3.2.5 测试建议

新增测试：

1. `CollectionSchedulerShouldRebuildAssignmentsOnSliceCountChange`
2. `CollectionSchedulerShouldSkipStaleRevisionTasks`
3. `CollectionSchedulerShouldCancelSliceTasksWhenSliceExecutionTimeout`

### 3.2.6 验收标准

1. 切片数量变化后没有重复调度。
2. 旧 revision 的任务不会污染新 revision。
3. 时间片超时后，在途任务会被取消或结果被丢弃。

## 3.3 上报 flush 背压与失败重试收口【已完成】

### 3.3.1 问题

当前 `CacheReportService` 已有：

1. `flushDirtyDevices()`
2. `FlushTracker`
3. 分片重试
4. `ReportManager.reportAsync(...)`

但仍存在：

1. 普通失败的重试是立即递归 `dispatch(...)`。
2. 没有显式退避策略。
3. 没有设备级积压上限。

### 3.3.2 改造目标

目标是让 flush 在目标端抖动、线程池 reject 或链路慢时不会放大拥塞。

### 3.3.3 代码落点

1. `src/main/java/com/wangbin/collector/core/report/service/CacheReportService.java`
2. `src/main/java/com/wangbin/collector/core/report/service/ReportManager.java`
3. `src/main/java/com/wangbin/collector/core/report/config/ReportProperties.java`

### 3.3.4 改造方案

建议增加：

1. 每设备 `maxPendingChunks`
2. `retryBackoffMs`
3. `maxRetryBackoffMs`
4. `retryJitterEnabled`

将当前：

```java
dispatch(data, config, highPriority, tracker);
```

改为：

```java
scheduleChunkRetry(data, config, highPriority, tracker, attempt);
```

具体规则：

1. reject、网络失败、handler 返回失败都统一走异步退避重试。
2. 对单设备同时处于 pending 的 chunk 数设置上限。
3. 超过上限时：
   - 保留 dirty
   - 不清 shadow
   - 记录 dropped/deferred 指标
4. `ReportManager.reportAsync()` 的 reject 结果保留明确错误码或 metadata。

### 3.3.5 测试建议

新增测试：

1. `CacheReportServiceShouldRetryWithBackoffWhenExecutorRejected`
2. `CacheReportServiceShouldKeepDirtyDeviceWhenPartialChunkFails`
3. `CacheReportServiceShouldLimitPendingChunksPerDevice`

### 3.3.6 验收标准

1. 失败不会同步递归重试。
2. 同一设备的积压数量可控。
3. 部分失败后 dirty 状态保留，后续可补 flush。

## 3.4 flush 互斥与影子提交一致性【已完成】

### 3.4.1 问题

当前 `ShadowManager` 在 `desired` 路径已经有 CAS，但 `flush` 仍主要是单实例内存互斥：

1. `flushingDevices` 只在本 JVM 生效。
2. `markReportedValues()` 是按 chunk 部分提交，不是整次 flush 原子提交。

### 3.4.2 改造目标

目标是保证：

1. 多实例下同一设备不会并发 flush。
2. chunk 部分成功时，影子状态变化有清晰语义。

### 3.4.3 代码落点

1. `src/main/java/com/wangbin/collector/core/report/service/CacheReportService.java`
2. `src/main/java/com/wangbin/collector/core/report/shadow/ShadowManager.java`
3. 如需要，可补：
   - `src/main/java/com/wangbin/collector/common/config/DistributedLock.java`
   - `src/main/java/com/wangbin/collector/common/config/RedisDistributedLock.java`

### 3.4.4 改造方案

建议拆成两个层次：

#### 层次一：flush 分布式互斥

1. `flushDevice(deviceId)` 入口加设备级锁：
   - key 类似 `collector:report:flush:deviceId`
2. 获取不到锁时直接跳过，由后续周期 flush 接管。

#### 层次二：reported 提交语义

定义两类提交：

1. `markReportedValuesChunk(deviceId, properties)`
   - 表示某 chunk 成功
   - 仅更新对应字段的 lastReportedValue
2. `markReportedWindowCommitted(deviceId, windowStart, windowEnd)`
   - 表示整次 flush 成功完成
   - 清 dirty
   - 更新 lastReportAt / window

必要时在 `DeviceShadow` 中增加：

1. `lastFlushBatchId`
2. `lastFlushRevision`

用于追踪当前 flush 的窗口和提交状态。

### 3.4.5 测试建议

新增测试：

1. `CacheReportServiceShouldAvoidDuplicateFlushAcrossInstances`
2. `ShadowManagerShouldKeepReportedStateConsistentAcrossChunkedFlush`
3. `ShadowManagerShouldCasReportedUpdatesInMultiInstanceMode`

### 3.4.6 验收标准

1. 同一设备同一时刻仅一个实例 flush。
2. chunk 局部成功时，dirty 不会被误清。
3. flush 全成功后，`lastReportAt` 和 `reported` 语义一致。

## 4.3 线程池来源与拒绝策略统一【已完成】

### 4.3.1 问题

### 4.3.2 改造目标

主流程线程池来源统一，避免：

1. 监控不可见。
2. 停机不可控。
3. 回退策略不一致。

### 4.3.3 代码落点

1. `src/main/java/com/wangbin/collector/common/config/ThreadPoolConfig.java`
2. `src/main/java/com/wangbin/collector/core/cache/config/CacheAsyncConfig.java`
3. `src/main/java/com/wangbin/collector/core/connection/adapter/HttpConnectionAdapter.java`
4. `src/main/java/com/wangbin/collector/core/connection/adapter/WebSocketConnectionAdapter.java`
5. `src/main/java/com/wangbin/collector/core/collector/protocol/modbus/base/AbstractModbusCollector.java`
6. `src/main/java/com/wangbin/collector/core/collector/protocol/iec/base/AbstractIce104Collector.java`
7. `src/main/java/com/wangbin/collector/core/report/handler/MqttReportHandler.java`
8. `src/main/java/com/wangbin/collector/core/report/handler/TcpReportHandler.java`

### 4.3.4 改造方案

建议：

1. 明确三类共享资源：
   - `ioIntensiveExecutor`
   - `cpuIntensiveExecutor`
   - `timeSliceScheduler`
2. 主流程 bean 优先强制注入共享线程池。
3. 仅在非 Spring、手工 new 场景下允许 fallback。
4. 给 fallback 加显式日志，便于发现。
5. `CacheAsyncConfig` 如无必要，可并入统一 `ioIntensiveExecutor` 或单独定义但统一 reject 策略。
6. 明确 reject 策略：
   - 调度与关键采集：`AbortPolicy` + 上层显式处理
   - 非关键异步回填：`CallerRunsPolicy` 或有界 reject 计数

### 4.3.5 测试建议

新增测试：

1. `ThreadPoolFallbackShouldPreferInjectedExecutorOverCommonPool`
2. `HttpConnectionAdapterShouldUseInjectedExecutorWhenPresent`
3. `AbstractModbusCollectorShouldUseInjectedExecutorWhenPresent`

### 4.3.6 验收标准

1. 主流程不再依赖 `ForkJoinPool.commonPool()`。
2. 自建 executor 数量明显下降。
3. 各线程池拒绝策略可解释且一致。

## 4.4 Redis 扫描和批量读取路径优化【已完成】

### 4.4.1 问题

当前 `RedisCacheManager` 已经使用 `SCAN`，优于 `KEYS`，但仍有两个问题：

1. `scanKeys()` 会把所有 key 收集到内存。
2. `MultiLevelCacheManager.getAll()` 仍是逐 key 读取。

### 4.4.2 改造目标

减少大 keyspace 下的内存峰值和 Redis 往返次数。

### 4.4.3 代码落点

1. `src/main/java/com/wangbin/collector/core/cache/manager/RedisCacheManager.java`
2. `src/main/java/com/wangbin/collector/core/cache/manager/MultiLevelCacheManager.java`

### 4.4.4 改造方案

建议分两步：

#### 第一步：扫描分批消费

1. 抽一个 `scanKeysBatch(pattern, batchConsumer)`。
2. `deleteByPattern()`、`clear()`、`size()`、`keys()` 按批消费，不一次性缓存全量 key。

#### 第二步：bulk 读取

1. `MultiLevelCacheManager.getAll()` 对二级缓存优先走 `pipelineGet()`。
2. 命中后再按需回填一级缓存。
3. 批量 miss 场景下减少逐 key round-trip。

### 4.4.5 测试建议

新增测试：

1. `RedisCacheManagerShouldScanAndDeleteInBatches`
2. `RedisCacheManagerShouldReturnKeysWithoutMaterializingHugeSetWhenDeleting`
3. `MultiLevelCacheManagerShouldUsePipelineForBulkReads`

### 4.4.6 验收标准

1. pattern 删除和 clear 不再一次性聚合超大 key 集。
2. bulk 读取 Redis 往返次数下降。

## 9. 2026-07-14 架构整改计划

### 9.1 定位与原则

本轮目标不是重写采集框架，而是消除可能导致停采、丢数据、错误上报、安全绕过和控制台误判的系统性风险，使工程从“功能完整的预生产版本”进入“具备生产准入条件的工业采集网关”。

1. 不改变各协议的寄存器地址解释、帧编解码、连接参数、批量读取和数值转换规则。
2. P0 阶段不直接改动协议采集器的业务实现。
3. 配置、调度、采集结果、后处理、告警和上报分批调整，禁止一次性重写整条链路。
4. 不保留“配置读取异常等于空配置”和“时间片超时等于永久取消任务”等错误语义。
5. 每项修改必须有自动化测试、运行指标、失败日志、回滚边界和验收标准。
6. 本地 `deviceId` 是控制台、配置和采集任务的唯一标识；`productKey + deviceName` 只用于云端身份和云消息路由。
7. 新增源码和文档使用 UTF-8，新增注释使用中文，并遵循《阿里巴巴 Java 开发手册（嵩山版）》。

### 9.2 `BASE-00` 采集基线

代码整改前必须固定以下基线：

1. 每种已交付协议保留正常读取、批量读取、失败重试和断线重连用例。
2. 固化原始值、缩放值、质量、时间戳和告警元数据的转换结果。
3. 固化启动、停止、重启、配置变更和关闭时的连接次数与任务数量。
4. 固化控制台通过本地 `deviceId` 查询设备、点位、实时值和状态的契约。
5. 固化云端 topic、属性字段、消息 ID、ACK 和重试报文。
6. 记录采集周期偏差、线程池队列、Redis、TDengine 和上报延迟。

基线完成条件是全量 Maven 测试、前端 JavaScript 语法检查和新增链路回归全部通过。后续任务均以“采集数量、点位值、质量和协议请求次数无非预期变化”为合并门禁。

### 9.3 第一阶段：P0 正确性与安全整改

#### 9.3.1 `CFG-P0-01` 配置失败语义与最后有效快照

**现状**：`RemoteConfigLoader` 捕获异常后返回空集合，后续可能构造合法空快照，把配置中心故障识别为全部设备删除。

**调整步骤**：

1. `ConfigLoader` 返回 `SUCCESS/NOT_MODIFIED/FAILED` 状态、候选快照、来源版本、加载时间和错误原因。
2. 网络异常、超时、反序列化失败和远端错误统一返回 `FAILED`，禁止使用空集合表达失败。
3. 只有远端明确成功且设备列表为空时，才能生成合法空快照。
4. `ConfigSyncService` 先完整加载、校验候选快照，再计算差异和提交。
5. 候选快照校验成功后一次性替换当前快照；失败时保留最后有效快照，不发布删除事件，不停止设备。
6. 真正删除设备只能来自权威快照、版本变更或明确删除接口。
7. 暴露连续失败、最后成功时间、配置版本和设备数量指标。

**采集保护与测试**：不修改协议连接和点位读取；运行任务继续使用最后有效配置。覆盖 HTTP 超时、非法 JSON、明确空列表、失败恢复和并发同步。验收标准是配置中心故障不能误删设备或停采。

#### 9.3.2 `SCH-P0-01` 调度超时与生命周期解耦

**现状**：时间片超时可能永久取消其中全部任务，一个慢设备可以影响其他设备，控制台也未必反映真实停采。

**调整步骤**：

1. 永久 `cancelled` 只用于设备停止、配置删除和服务关闭。
2. 时间片超时只取消本次 `Future` 或标记本次执行超时，不删除下一周期调度。
3. 为每个设备增加非重入保护，上一轮未结束时只跳过该设备下一次触发。
4. 连续超时达到阈值后进入 `DEGRADED` 并按设备退避，成功后恢复正常周期。
5. 慢设备不能取消同时间片其他设备。
6. 停止设备仍须隔离在途任务，旧调度代次结果不得写入。
7. 动态时间片重建采用新旧代次安全切换。

**采集保护与测试**：不改变正常周期、批次、协议调用次数和 `DeviceBatchPlanner` 结果。覆盖单次超时恢复、慢设备隔离、同设备不重入、停机代次隔离和动态重建。

#### 9.3.3 `SHADOW-P0-01` dirty 影子恢复与可靠上报

**现状**：dirty 集合可以从 Redis 恢复，但本地设备到云身份的映射存在进程内 Map；重启后找不到映射时可能清除 dirty。

**调整步骤**：

1. 抽取 `CloudDeviceIdentityService`，以本地 `deviceId` 从正式配置解析 `cloudTarget`。
2. `flushDevice()` 不再依赖临时内存映射。
3. 上报记录保存本地设备 ID、`productKey`、`deviceName`、影子版本、消息 ID 和创建时间。
4. 引入版本化持久化 Outbox；配置缺失时进入 `WAITING_CONFIG`，保留 dirty 并重试。
5. 超过重试阈值进入隔离集合，不得静默删除。
6. ACK 成功后按影子版本提交 `reported` 并清理对应 Outbox。
7. ACK 超时、重复、乱序和版本冲突都按消息 ID 与影子版本幂等处理。

**身份规则**：本地查询、配置、缓存和采集任务使用 `deviceId`；云 topic 使用 `productKey + deviceName`；禁止云身份缺失时回退本地 ID；禁止下行模糊匹配。

**测试**：覆盖服务重启、配置暂不可用、ACK 丢失/重复/乱序、云身份变更和多实例 flush。验收标准是未确认数据在任何暂时故障下都不会被清除。

#### 9.3.4 `SEC-P0-01` 密钥、可信代理与防重放

1. 轮换仓库中出现过的数据库、Redis、MQTT 和运维凭据。
2. 基础配置只保留环境变量占位符和无权限示例值。
3. 生产 profile 发现默认令牌、空密码和示例凭据时拒绝启动。
4. 控制台不预填或公开令牌；日志不得记录完整令牌、密码和设备密钥。
5. 配置可信代理范围；非可信代理请求忽略转发 IP 头。
6. HMAC 加入请求体 SHA-256、nonce、时间戳、方法、路径和规范化查询参数。
7. Redis 保存短期 nonce，重复请求直接拒绝。
8. 分别统计 Token、签名和 IP 白名单的认证结果，后续拆分查看、控制、配置和安全权限。

该任务只作用于 HTTP 管理面和云服务调用，不改变现场协议采集。验收必须证明伪造代理头、篡改请求体和请求重放均不能通过认证。

### 9.4 第二阶段：P1 数据一致性与资源隔离

#### 9.4.1 `PIPE-P1-01` 不可变采集快照

同步采集返回值与异步线程读取的最新 `ProcessResult` 可能来自不同周期，调整如下：

1. 保留协议采集器的原始读取方法和协议处理逻辑。
2. 在 `BaseCollector` 统一出口构造不可变 `TelemetrySample`。
3. 样本包含设备 ID、点位 ID、原始值、处理值、质量、采集时间、设备代次和元数据。
4. 批量读取构造不可变 `CollectionBatchResult`，异步任务不得回查 collector 的可变最新状态。
5. AOP 只把已完成快照交给 `TelemetryIngressService`。
6. `lastValue` 只作为查询缓存，不再作为本次处理的事实来源。
7. 推送型和轮询型协议使用同一份样本契约。

测试必须构造两轮采集与异步阻塞交错，证明每轮值、质量、原始值和时间戳保持配对；设备重启后的旧代次样本必须被拒绝。

#### 9.4.2 `EXEC-P1-01` 后处理隔离与背压

| 通道 | 投递目标 | 队列满时策略 |
|---|---|---|
| 最新值缓存 | 保留最新值 | 同点位合并，不阻塞采集 |
| Redis Stream | 按配置保留实时流 | 有界等待或明确记录丢弃 |
| TDengine 历史 | 至少一次、允许幂等重放 | 本地缓冲、批量写入、重试 |
| 告警状态 | 状态转换不可丢 | 持久化事件或可靠重试 |
| 云端上报 | 至少一次、云端幂等 | 持久化 Outbox，不静默丢弃 |

1. 拆分缓存、Stream、历史、告警和云上报执行器。
2. 每个执行器使用有界队列、独立线程名和拒绝策略。
3. TDengine 按设备或时间窗口批量写入，建表检查移出单条热路径。
4. Redis 暂不可用时，本地最新值仍可更新。
5. 云端上报从 Outbox 消费，不占用采集后处理线程等待 ACK。
6. 告警历史不与最新值缓存共享容易阻塞的线程池。
7. 暴露队列长度、拒绝数、最老任务年龄、吞吐和失败次数。
8. 关闭顺序为停止新采集、等待在途、排空处理队列、提交 Outbox、断开连接。

验收必须覆盖 Redis、TDengine 和云平台分别中断，单一下游故障不得扩散为全局停采。

#### 9.4.3 `ALARM-P1-01` 告警状态机与单一出口

以 `{deviceId, pointId, ruleId}` 为唯一键，建立 `NORMAL -> PENDING -> ACTIVE -> ACKED -> RECOVERED -> NORMAL` 状态机。

1. `duration` 表示首次满足条件到进入 `ACTIVE` 的持续时间。
2. 增加迟滞或恢复阈值，避免阈值附近反复告警。
3. 只在状态转换时创建 `AlarmEvent`，持续采样只更新状态。
4. 生成稳定 `eventId`，供历史、通知和云上报幂等。
5. 删除同一事件的双重云出口，统一由事件 Outbox 上报。
6. ACK 只改变确认状态，不代表恢复。
7. 恢复事件关联原告警 ID，并携带开始、恢复时间和持续时长。

验收标准是持续越限只产生一次激活事件，短时尖峰不触发，ACK、恢复和再次触发符合定义，云端不存在重复告警事件。

### 9.5 第三阶段：P1 配置、接口与运行治理

#### 9.5.1 `CONFIG-P1-01` 原子配置包

1. 设备基础信息、连接参数、点位和云身份组成版本化 `DeviceConfigBundle`。
2. 编辑和导入先完成协议 schema、唯一性、云身份和引用完整性校验。
3. 校验成功后一次提交，失败时不得出现部分更新。
4. 每次提交只发布一个包含新旧版本的配置事件，调度器只执行一次防抖重启。
5. `ConfigManager` 对外返回不可变快照或防御性副本。
6. `lastValue`、稳定次数和自适应周期迁移到独立 `PointRuntimeState`。
7. 配置事件在释放写锁后发布。

验收必须证明导入任意一步失败时原配置完整保留，一次保存最多触发一次重启，运行状态不污染持久化配置。

#### 9.5.2 `API-P1-01` API、秘密字段和权限

1. 统一成功和错误结构，错误返回正确 HTTP 状态码。
2. 请求使用 Bean Validation DTO，不直接暴露内部实体。
3. 密码、设备密钥和令牌采用只写字段，查询脱敏。
4. 配置导出默认排除秘密，敏感导出使用专用权限和加密文件。
5. 拆分查看、设备控制、配置管理和安全管理权限。
6. 生成 OpenAPI，增加后端契约测试和控制台接口回归。
7. 前端 API 客户端统一处理非 JSON 错误、HTTP 状态和认证过期。

#### 9.5.3 `CACHE-P1-01` 缓存模式与 Redis 序列化

1. 修正 `collector.cache.type` 与 Spring `CacheManager` 条件疑似反向的问题。
2. 明确定义 `local`、`redis` 和 `multi-level` 三种模式。
3. `local` 模式不得在主路径强制访问 Redis。
4. 多级模式明确读写、回填、失效和 Redis 降级规则。
5. 禁止无约束多态反序列化，改为固定 DTO 或类型白名单。
6. Redis key 增加业务前缀、结构版本和环境隔离。
7. 为三种模式分别增加 Spring 上下文和读写测试。

#### 9.5.4 `OPS-P1-01` 真实健康、启动与停机

设备状态统一为 `STOPPED`、`STARTING`、`RUNNING`、`DEGRADED`、`SUSPENDED` 和 `FAILED`，依据最后成功采集时间、连续失败、调度状态和退避状态计算。

1. 控制台不使用静态“运行中”或配置态代替运行态。
2. 健康接口增加采集延迟、连续失败、调度代次和配置新鲜度。
3. 线程池展示 active、pool、queue、completed 和 rejected，零值区分“空闲”和“未接入”。
4. 增加 Outbox 最老消息、ACK 超时、Redis 和 TDengine 状态。
5. `Application.main()` 启动失败必须返回非零退出码。
6. 优雅停机接入真实 Spring 生命周期，依次停止入口、采集、后处理和连接。
7. 删除或标注控制台中的站点、用户、事件和通讯日志占位数据。

### 9.6 第四阶段：`ENG-P2-01` 工程治理

1. 按配置、调度、协议采集、遥测、告警、云上行和运维边界拆分超大类。
2. 协议类只保留协议差异，不复制缓存、告警和上报逻辑。
3. 字段注入逐步改为构造器注入。
4. 统一 Jackson，禁止业务类自行创建未配置的 `ObjectMapper`。
5. 清理乱码源码、英文页面残留和不符合要求的注释。
6. 引入格式化、静态检查、依赖漏洞扫描、密钥扫描和架构约束测试。
7. 前端拆分 API、状态、设备编辑、点位编辑和监控模块，并补关键端到端测试。
8. 文档链接、标题和关键配置一致性检查进入 CI。

该阶段在 P0 和主链路 P1 稳定后实施，禁止为了减少类长度而机械拆分类。

### 9.7 交付顺序与验收

| 顺序 | 任务 | 进入下一阶段的条件 |
|---|---|---|
| 1 | `BASE-00` | 基线测试和指标固定 |
| 2 | `CFG-P0-01` | 配置故障不误删设备 |
| 3 | `SCH-P0-01` | 慢设备隔离且正常设备不停采 |
| 4 | `SHADOW-P0-01` | 重启和断网不丢 dirty 数据 |
| 5 | `SEC-P0-01` | 默认秘密清理且防重放通过 |
| 6 | `PIPE-P1-01` | 样本跨线程保持一致 |
| 7 | `EXEC-P1-01` | 下游故障不阻塞采集 |
| 8 | `ALARM-P1-01` | 告警状态和事件唯一 |
| 9 | `CONFIG-P1-01` | 配置原子提交 |
| 10 | `API-P1-01` | API 契约和权限统一 |
| 11 | `CACHE-P1-01` | 三种缓存模式行为明确 |
| 12 | `OPS-P1-01` | 状态、启动和停机真实可靠 |
| 13 | `ENG-P2-01` | 工程约束进入 CI |

P0 可按配置、调度和安全分支并行开发，但影子任务必须在配置身份规则稳定后合并。不可变快照与执行器拆分不允许并行修改同一段异步提交代码。

每个任务只包含一个领域变化；数据结构变化先支持读取旧版本再写新版本；回滚不得删除 Redis dirty、Outbox、告警状态和配置快照；上报验证使用测试 topic，禁止双重正式上报。

总体验收必须覆盖配置中心断开、单设备超时、服务重启、Redis/TDengine/云平台故障、ACK 重复乱序、告警越限、配置导入失败、代理头伪造、请求重放、启动失败和正常停机。P0 全部完成、全量测试通过、采集基线无非预期变化、单一下游故障不扩散且专题文档与代码一致后，本轮才能标记完成。
