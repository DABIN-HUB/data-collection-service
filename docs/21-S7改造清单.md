# S7 改造清单

本文档用于把当前 `SIEMENS_S7` 实现从“可用的基础 PLC4X 绝对地址采集”推进到“工程可用的 S7 采集能力”。
重点不是泛泛列问题，而是把任务拆到具体类、接口、配置项和验收口径。

## 1. 当前基线

当前 `SIEMENS_S7` 已具备：

1. 真实 PLC4X S7 连接。
2. 标量点单点读写和按 `maxFieldsPerRequest` 分片批读批写。
3. 周期订阅 `addCyclicTagAddress(...)`。
4. 统一类型解析、统一 `ProcessResult`、统一缓存/上报后处理链路。
5. `executeCommand(read/write/status/diagnostic)` 薄封装。

当前明确缺口：

1. 只适合绝对地址路径，没有符号浏览、符号导入、优化块访问治理。
2. 数组地址解析层已部分具备，但采集层仍拒绝数组。
3. `diagnostic` 只有基础连接状态，没有 CPU / SZL / 系统诊断信息。
4. 订阅只有 cyclic，没有 `MODE / SYS / USR / ALM` 事件订阅。
5. 没有 S7 专项批读计划，当前批量策略仍是“按点位拼 request”。
6. 对 `S7-1200/1500` 的上线前提没有显式校验和错误引导。
7. 连接参数和运维指标还偏基础。

## 2. 边界和原则

### 2.1 本轮边界

本清单只覆盖当前 `SIEMENS_S7` raw S7 路线，不把 `OPC_UA` 路线混入同一实现。

### 2.2 优先级定义

1. `P0`：会直接影响当前项目能否稳定采集、能否上线、能否定位问题。
2. `P1`：不立刻阻断主链路，但会持续影响性能、可观测性和扩展成本。
3. `P2`：更偏产品增强或第二条技术路线，不建议和当前 P0/P1 主线混做。

### 2.3 设计原则

1. 保持 `SIEMENS_S7` 作为“绝对地址驱动”主路径，不在 P0 阶段强行混入复杂符号浏览逻辑。
2. 能复用现有协议模式的优先复用，尤其参考 `EtherNetIpCollector` 的“标量/数组分路”实现。
3. 配置 schema、连接校验、运行时 collector、控制接口和文档必须一起改，不做半套能力。

## 3. P0 清单

## 3.1 P0-1：补齐 S7-1200/1500 上线前置校验和部署诊断

### 3.1.1 目标

把当前“连接能建起来但业务读不到”的隐性失败，前移为显式校验或显式诊断结果。

1. `S7-1200/1500` 场景下全局 DB / optimized block / PUT/GET 等常见前置条件。
2. 地址格式和控制器类型的组合校验。

### 3.1.3 涉及接口和入口

### 3.1.4 具体改造项

1. 在 `ProtocolConnectionValidator` 新增 `validateS7(...)`，校验以下内容：

   - `deploymentHints`
3. 在 `ProtocolDescriptorRegistry` 的 S7 连接字段说明中补充：
   - `controllerType` 的含义。
   - `plc4xConnectionString` 与普通 host/port/rack/slot 的优先级。
   - `subscriptionEnabled` 只是启用 cyclic subscription，不代表 PLC 原生事件订阅。

## 4. P1 清单

## 4.1 P1-1：支持 `MODE / SYS / USR / ALM` 事件订阅

Status: implemented on 2026-06-25. `S7Collector` 已支持 `CYCLIC` 和 `MODE / SYS / USR / ALM` 两类订阅路径；协议 schema 和管理端动态表单会暴露 `additionalConfig.subscriptionMode`、`additionalConfig.subscriptionAddress`。

### 4.1.1 目标

在现有 cyclic subscription 之外，补齐 PLC4X S7 驱动支持的系统事件订阅能力。

### 4.1.2 代码落点

1. `src/main/java/com/wangbin/collector/core/collector/protocol/s7/S7Collector.java`
   - 扩展 `doSubscribe(...)`、`handleSubscriptionEvent(...)`、`ingestEventPayload(...)`。
   - `readPoint(...)` / `readPoints(...)` 对订阅点优先返回本地缓存的最新结果，不再额外主动轮询。
2. `src/main/java/com/wangbin/collector/core/config/protocol/ProtocolDescriptorRegistry.java`
   - 为 S7 点位补 `additionalConfig.subscriptionMode`、`additionalConfig.subscriptionAddress`。
3. `docs/protocols/SIEMENS_S7.md`
   - 同步说明 cyclic / event 两类订阅配置方式。

### 4.1.3 涉及接口和入口

1. Java 接口：`SubscribableCollector.subscribe/unsubscribe`。
2. 前端协议字段接口：`GET /api/protocols/SIEMENS_S7/fields`。
3. 管理命令入口：`POST /api/control/device/{deviceId}/command`，可配合 `status` / `diagnostic` 查看订阅运行状态。
4. 使用方式：
   - `collectionMode=SUBSCRIPTION` 且 `additionalConfig.subscriptionMode=CYCLIC`：走 `addCyclicTagAddress(...)`，地址使用点位绝对地址。
   - `collectionMode=EVENT`，或 `collectionMode=SUBSCRIPTION` 且 `subscriptionMode=MODE / SYS / USR / ALM`：走 `addEventTagAddress(...)`。
   - `subscriptionAddress` 为空时，事件订阅优先复用 `additionalConfig.subscriptionAddress` / `s7SubscriptionAddress`，再退回点位 `address`，最后退回 mode token 本身。

### 4.1.4 具体改造项

1. 订阅模式区分：`CYCLIC`、`MODE`、`SYS`、`USR`、`ALM`，并兼容 `SYSTEM -> SYS`、`USER -> USR`、`ALARM -> ALM` 别名归一化。
2. 对事件型点位，`ProcessResult` metadata 统一补充：`eventTriggered`、`eventType`、`eventLevel`、`eventMessage`、`subscriptionMode`、`subscriptionAddress`、`eventPayload`、`responseCode`、`eventTimestamp`。
3. 事件和 cyclic 推送都继续复用现有 `lastProcessResults`、`telemetryIngressService`、缓存 / 上报 / 实时流主链路，不单独造第二套后处理逻辑。
4. `status` / `diagnostic` 会补充 `activeSubscriptions`、`supportedSubscriptionModes`、`subscriptionModeCounts`、`lastSubscriptionEventTs`、`lastSubscriptionPointId`、`lastSubscriptionPointCode`、`lastSubscriptionError` 等运行信息。

### 4.1.5 测试

1. `S7CollectorTest`：订阅模式分路、事件 payload 缓存回读、事件 metadata。
2. 后续真实设备联调：`MODE / SYS / USR / ALM` 事件落库、落流、上报链路验证。

### 4.1.6 验收标准

1. cyclic 和事件订阅可以共存。
2. 事件点位不会被误当作普通标量轮询点处理。
3. 运维侧能够直接从 `status` / `diagnostic` 看见订阅数、最近事件和最近订阅错误。

## 4.2 P1-2：补 S7 专项批读计划

Status: implemented on 2026-06-25. 轮询标量点现在会先构建 S7 专项读计划；满足条件的计划优先走连续块读，再在本地切片解码；块读失败会自动回退到原 PLC4X multi-tag 批读。

### 4.2.1 目标

把当前“按点拼 readRequest”升级为“按 DB / area / offset 连续区合并”，降低请求数量和 PLC 压力。

### 4.2.2 代码落点

1. `src/main/java/com/wangbin/collector/core/collector/protocol/s7/S7Collector.java`
   - 改造 `buildReadPlans(...)`、`doReadPoints(...)`、计划执行和 fallback 分路。
   - 新增块读字节切片、本地 PLC4X `DataItem.staticParse(...)` 解码和计划快照输出。
2. 新增：
   - `src/main/java/com/wangbin/collector/core/collector/protocol/s7/plan/S7ReadPlan.java`
   - `src/main/java/com/wangbin/collector/core/collector/protocol/s7/plan/S7ReadPlanItem.java`
   - `src/main/java/com/wangbin/collector/core/collector/protocol/s7/plan/S7ReadPlanBuilder.java`
3. 调度接入点：
   - `ReadPlanCapable.rebuildReadPlans(...)`
   - `CollectionManager.rebuildReadPlans(...)`

### 4.2.3 涉及接口和入口

1. Java 接口：`ReadPlanCapable.rebuildReadPlans(...)`。
2. 调度调用链：`CollectionScheduler -> CollectionManager -> S7Collector`。
3. 使用方式：
   - 不需要新增开关字段；设备启动、重载或配置刷新后，`rebuildReadPlans(...)` 会自动重建计划。
   - 当前只作用于轮询标量点；数组点、订阅点、事件点仍走各自已有路径，不参与块读计划。
   - `maxFieldsPerRequest` 仍然是计划切分上限；当前连续窗口上限是固定 `256 bytes`。
   - 要看计划是否命中块读，可通过 `diagnostic` 的 `summary.plannedReadBatches[*]` 查看 `blockOptimizable`、`blockReadEnabled`、`blockReadAddress`。

### 4.2.4 具体改造项

1. 按 `DB / INPUT / OUTPUT / MERKER` 分组，并按 byte/bit offset 排序。
2. 计划同时按 `maxFieldsPerRequest`、固定 `256 bytes` span、以及“是否允许块读”分段，避免把不兼容点位混进同一块。
3. 只有满足以下条件的计划才会触发真实块读：
   - 同一段计划内点位数大于 1。
   - 地址属于 `DB / INPUT / OUTPUT / MERKER` 且是 byte-addressable。
   - 点位为标量、非 bit 级 `BOOL`、非 `STRING / WSTRING`。
4. 典型命中示例：`DB1.DBW0`、`DB1.DBW2`、`DB1.DBD4` 会被规划为一次 `DB1:0:BYTE[8]` 读取。
5. 块读返回后，collector 会按 `S7ReadPlanItem.byteOffset/byteLength` 切片，并复用 PLC4X `DataItem.staticParse(...)` 做本地子值解码，避免自己手写类型解析。
6. 任一块读请求失败、payload 长度不足、切片越界或本地解码失败，都会自动回退到原来的 PLC4X multi-tag 批读；不会影响同一批点位的正确性。
7. 当前实现还没有根据 `pduSize` / `controllerType` 做动态 span 估算，仍是固定 `256 bytes` 窗口。这个缺口需要保留在后续 P1-2 续做项里。

### 4.2.5 测试

1. `S7ReadPlanBuilderTest`：分组、排序、切片、块读地址生成、`BOOL` 点分路。
2. `S7CollectorTest`：块读命中、块读失败 fallback、结果切片解码。
3. 回归测试：`ProtocolConnectionValidatorTest`、`ProtocolSchemaServiceTest`、`AdsCollectorTest`、`EtherNetIpCollectorTest`、`KnxNetIpCollectorTest`、`Plc4xOpcUaCollectorTest`、`ConnectionBackedCollectorPointIdentityTest`。

### 4.2.6 验收标准

1. 同规模轮询标量点下，S7 请求次数显著下降。
2. 失败时不会影响现有采集正确性。
3. 运维侧可通过 `plannedReadBatches` 明确看到哪些批次会命中块读、具体块地址是什么。

## 4.3 P1-3：补齐连接参数和冗余配置

### 4.3.1 目标

### 4.3.2 代码落点

### 4.3.3 具体改造项

1. 已接出的连接字段：`host`、`port`、`rack`、`slot`、`controllerType`、`pduSize`、`maxFieldsPerRequest`、`subscriptionEnabled`、`readTimeout`、`timeout`。

   - 一旦设置 `plc4xConnectionString`，`host/port/rack/slot/controllerType` 不再是运行时真值来源。
   - `controllerType`、`localDeviceGroup`、`remoteDeviceGroup` 会在 adapter 内做横杠/下划线归一化后写入 PLC4X 连接串。
   - `maxFieldsPerRequest` 不只影响普通 PLC4X tag batch，也会影响 S7 读计划切分。
5. 前端协议配置页会通过 `GET /api/protocols/SIEMENS_S7/fields` 动态展示这些字段；管理端不需要单独硬编码 S7 表单。
6. 当前尚未接出的字段：`tcpKeepAlive`、`tcpNoDelay`、`tcpDefaultTimeout`、`s7Mode`。若后续现场需要，继续放在 P1-3 续做项。

### 4.3.4 验收标准

1. 管理端能通过 schema 配置上述已接出的参数。
2. adapter 构造出的连接串可稳定反映配置结果。
3. `connection_info` / `diagnostic` 能直接回显当前连接参数，便于排查“配置写了但没生效”的问题。

### 4.4.3 具体改造项

## 5. P2 清单

## 5.1 P2-1：符号浏览、符号导入、优化块访问

### 5.1.3 涉及类

2. 新的 schema descriptor。
3. 新的 browse API。

## 5.2 P2-2：安全连接和凭据治理

### 5.2.1 结论

如果 PLC4X raw S7 本身不提供足够的安全连接能力，这部分不应在当前 collector 里做表面封装。

### 5.2.2 推荐实现方式

1. 优先评估 PLC / 网关侧是否已提供安全协议出口。
2. 对高安全场景优先采用 `OPC_UA`、专用网关或安全通道方案。

## 5.3 P2-3：TIA Portal 工程导入和点位自动生成
