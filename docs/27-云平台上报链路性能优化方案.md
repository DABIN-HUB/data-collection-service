# 云平台上报链路性能优化方案

## 1. 目标

本方案用于在现有云平台适配器架构上继续优化上报链路，目标是：

1. 网关级批量属性包，减少 MQTT 消息数量。
2. ACK 异步化，避免发送线程被云端响应阻塞。
3. Payload 精简配置，降低序列化成本和带宽占用。
4. 协议适配器选择缓存，避免每条消息重复解析云厂商协议。
5. 保持主链路和云厂商协议解耦，后续接入华为云只新增 adapter，不改采集、影子聚合、重试和 MQTT 连接主流程。

## 2. 最优链路

```text
CacheReportService
  -> ShadowManager 纵向点位转横向设备快照
  -> CloudBatchAccumulator 网关级批量聚合
  -> CloudProtocolAdapter 云厂商协议编码
  -> MqttReportHandler 异步发布
  -> MqttReportHandler.AckManager 异步 ACK 状态机
```

## 3. 核心设计

### 3.1 协议上下文缓存

新增 `CloudReportTargetContext`，按上报目标缓存：

```text
targetId
cloudProvider
CloudProtocolAdapter
CloudPayloadOptions
CloudBatchFlushPolicy
CloudAckOptions
```

`ReportConfigProvider` 构建 `ReportConfig` 时只解析一次 `cloudProvider`。后续上报只读取上下文，不再按字符串反复查 registry。

### 3.2 Payload 精简

新增三种 profile：

1. `compact`：只保留 `id/version/method/params`，用于高吞吐生产链路。
2. `standard`：额外允许质量、属性时间戳。
3. `diagnostic`：携带 metadata，用于联调和排障。

配置：

```yaml
collector:
  report:
    cloud:
      payload:
        profile: compact
        include-quality: on_error
        include-property-ts: false
        include-metadata: false
        include-message-id: true
```

### 3.3 ACK 异步化

发布线程只负责投递：

```text
register ack ticket -> mqtt publish -> return accepted
```

ACK 到达后由 `MqttReportHandler.AckManager` 更新状态。超时扫描独立执行，不阻塞发送线程。

配置：

```yaml
collector:
  report:
    cloud:
      ack:
        mode: async
        timeout-ms: 5000
        max-pending: 10000
        timeout-scan-ms: 500
        commit-on: publish-success
```

说明：`commit-on=publish-success` 适合最高吞吐；如果后续需要强一致提交，可以扩展为 `ack-success` 并把影子提交挂到 ACK 回调。

### 3.4 网关级批量属性包

新增 `CloudBatchAccumulator`，按 `gatewayProductKey + gatewayDeviceName + cloudProvider` 分桶，把多个子设备横向快照合并成 `thing.event.property.pack.post`。

配置：

```yaml
collector:
  report:
    cloud:
      batch:
        enabled: true
        max-devices-per-pack: 50
        max-properties-per-pack: 500
        max-payload-bytes: 131072
        max-delay-ms: 1000
        high-priority-bypass: true
```

批量包示例：

```json
{
  "id": "uuid",
  "version": "1.0",
  "method": "thing.event.property.pack.post",
  "params": {
    "properties": [
      {
        "productKey": "pk1",
        "deviceName": "sub1",
        "properties": {
          "temperature": 26.5,
          "humidity": 60
        }
      }
    ]
  }
}
```

## 4. 阿里巴巴规范约束

1. 类保持单一职责，禁止继续扩大 `MqttReportHandler` 的业务职责。
2. 云厂商差异只能进入 `CloudProtocolAdapter` 实现。
3. 配置使用强类型对象，不在核心逻辑中长期传递裸 `Map<String,Object>`。
4. 异步队列、ACK pending map 必须有容量上限。
5. 异步任务必须捕获异常并记录日志。
6. 日志使用占位符，不拼接字符串。
7. DTO 暴露集合时做防御性复制。
8. 编码统一 UTF-8，无 BOM。

## 5. 华为云接入方式

后续新增：

```text
HuaweiCloudProtocolAdapter implements CloudProtocolAdapter
```

实现：

1. `provider()` 返回 `huawei`。
2. `buildPublishTopic(...)` 生成华为云 topic。
3. `encodeReportData(...)` 输出华为云属性/事件/批量包 payload。
4. `decode(...)` 解析华为云下行命令。
5. `downlinkTopicPaths()` 返回华为云订阅 topic path。

配置切换：

```yaml
collector:
  report:
    mqtt:
      cloud-provider: huawei
```

主上报链路不需要修改。

## 6. 落地原则

1. 追求架构最优，历史临时代码如果阻碍主链路质量，可以直接清理后重构，不做低价值兼容。
2. 在保证和云平台协议对接无误的前提下，优先保证数据上报链路优秀：少消息、少字段、少阻塞、少重复解析。
3. 原有能力不能丢失：纵向点位转横向属性、影子提交、事件/告警、下行命令、拓扑/子设备注册/OTA 能力继续保留。
4. 华为云等新平台只新增 `CloudProtocolAdapter` 实现，不修改采集、影子、重试、MQTT 发布主流程。
