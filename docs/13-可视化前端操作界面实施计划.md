# 可视化前端操作界面实施计划

## 1. 目标

本计划用于在当前 `data-collection-service` 工程上新增一个面向运维、实施和调试人员的可视化管理端。

前端不是独立于后端的展示页，而是围绕当前已经落地的完整链路设计：

1. 协议连接配置。
2. 设备与点位配置治理。
3. 数据采集启停与运行状态观测。
4. 实时数据、缓存数据、历史数据查询。
5. 设备影子、数据上报、下行反控。
6. 缓存、调度、连接、系统资源、异常监控。
7. 配置同步、导入导出、差异诊断与访问审计。

## 2. 当前可复用后端能力

4. `/api/config/device/{deviceId}/points`：点位列表。
5. `/api/config/device/{deviceId}/connection`：连接配置。
6. `/api/config/device/{deviceId}/diff`：本地与远端差异。

8. `/api/config/device/{deviceId}/clear`：清空设备配置缓存。
9. `/api/config/sync*`：触发配置同步与查看同步状态。

前端页面：

4. 点位配置表格。

2. 缓存命中率。

### 2.6 上报与下行能力

已有代码能力：

1. `CollectorDataPostProcessor`：采集后处理入口。
2. `CacheReportService`：影子聚合和上报入口。
3. `ReportManager`：上报分发。
4. `MqttReportHandler`、`HttpReportHandler`、`TcpReportHandler`：上报处理器。
5. `MqttDownlinkService`：MQTT 下行属性设置和服务调用。
6. `CollectionManager.writePoint/writePoints/executeCommand`：协议写入与命令入口。

当前缺口：

1. 没有上报配置管理 Controller。
2. 没有 HTTP 形式的手动写点位/执行命令 Controller。
3. Redis Stream 已写入，但没有浏览器消费用的 SSE/WebSocket 接口。

前端落地策略：

1. 第一版展示上报配置摘要、影子和实时数据。
2. 第二阶段补 `ReportController` 和 `ControlController` 后开放上报配置、测试上报、手动反控。
3. 第三阶段补 Redis Stream SSE 或 WebSocket 后替换实时数据轮询。

## 3. 页面信息架构

### 3.1 总览 Dashboard

功能：

1. 服务健康状态。
2. 设备数、点位数、连接数、运行设备数。
3. 协议分布。
4. 缓存命中率。
5. 最近异常。
6. 线程池负载。
7. 最近同步时间和下次同步时间。

接口：

1. `GET /health`
2. `GET /api/config/summary`
3. `GET /api/device/running`
4. `GET /monitor/cache`
5. `GET /monitor/devices`
6. `GET /monitor/system`
7. `GET /monitor/errors`

### 3.2 设备管理

功能：

1. 设备列表。
2. 设备新增、编辑、清空配置。
3. 设备启动、停止、状态查询。
4. 设备配置刷新。
5. 设备配置 diff。
6. 设备导入导出。

接口：

1. `GET /api/config/devices`
2. `PUT /api/config/device/{deviceId}`
3. `POST /api/config/device/{deviceId}/refresh`
4. `POST /api/config/device/{deviceId}/clear`
5. `GET /api/config/device/{deviceId}/diff`
6. `POST /api/device/{deviceId}/start`
7. `POST /api/device/{deviceId}/stop`
8. `GET /api/device/{deviceId}/status`
9. `GET /api/config/export`
10. `POST /api/config/import`

需要补充：

1. `POST /api/config/local/devices`：新增本地临时设备完整配置包。
2. `PUT /api/config/local/device/{deviceId}`：修改本地临时设备完整配置包。
3. `GET /api/config/local/device/{deviceId}`：读取本地临时设备配置包。
4. `DELETE /api/config/local/device/{deviceId}`：仅允许删除 `configSource=local` 且 `temporaryConfig=true` 的设备。
5. `POST /api/device/{deviceId}/start-local`：跳过远端刷新，直接基于本地内存配置启动。

本地临时设备约束：

1. 设备、连接和点位都必须显式标记为 `local` 本地临时配置。
2. 本地临时设备只写入当前采集服务内存，不写远端配置源。
3. 本地接口不得覆盖或删除远端/同步来源设备。
4. 前端必须显示“本地临时设备”标签。
5. 普通 `POST /api/device/{deviceId}/start` 保持原逻辑，仍会先刷新远端配置。
6. 全量远端同步时运行期保留本地临时设备；如果远端出现同 ID 设备，则跳过本地临时恢复。
7. 所有协议设备都需要配置采集自适应参数：`baseCollectionInterval`、`minCollectionInterval`、`maxCollectionInterval`，单位 ms；`pointChangeThreshold` 默认 `1`。

### 3.4 点位管理

## 4. 前端工程方案

### 4.1 第一阶段方案

为了不引入额外构建链路，第一阶段先使用 Spring Boot 静态资源：

```text
src/main/resources/static/admin/index.html
src/main/resources/static/admin/styles.css
src/main/resources/static/admin/app.js
```

访问路径：

```text
/collector/admin/index.html
```

说明：当前 `server.servlet.context-path=/collector`，因此本地默认完整地址为：

```text
http://127.0.0.1:9090/collector/admin/index.html
```

开发环境默认接口令牌：

```text
123456789
```

页面左侧的“接口令牌 X-Collector-Token”输入框保存后，会自动附加到后续 `/api/**` 请求头中。

特点：

1. 不依赖 npm 安装。
2. 可直接随 jar 包部署。
3. 适合先验证信息架构、接口闭环和运维流程。

### 4.2 第二阶段方案

当页面复杂度上升后，再迁移到：

```text
frontend/
  package.json
  src/
  vite.config.ts
```

建议技术栈：

1. Vite
2. React
3. TypeScript
4. TanStack Query
5. ECharts
6. Zod

构建产物输出到：

```text
src/main/resources/static/admin
```

## 7. 风险与边界

1. 当前 `CUSTOM_TCP` 仍是占位实现，前端必须标记“未实现真实采集”。
2. 点位更新接口目前是整表覆盖，前端必须做二次确认。
3. 上报配置当前主要来自 `application.yml`，在线修改需要补持久化策略。
4. 实时数据第一版轮询可能增加后端压力，需要限制刷新频率和当前设备范围。
5. 鉴权开启后，前端必须携带 `X-Collector-Token` 或服务签名。
6. 本地临时设备只存在于当前服务内存，重启后会丢失；前端必须显式提示。
7. 配置同步不应把本地临时配置写回远端，也不允许本地接口覆盖远端/同步设备。
8. 如果远端同步后出现同 ID 设备，本地临时设备不能继续覆盖该远端设备。
