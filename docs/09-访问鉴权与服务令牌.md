# 访问鉴权与服务令牌

## 1. 设计目标

1. 对 `/api/**` 管理接口做“最小侵入”的访问控制；不影响健康检查、Actuator 等自检路径。
2. 支持两类调用主体：
   - **运维/调试**：人工或 CLI 工具，适合使用静态 Token。
   - **云端配置服务**：机器调用，要求具备密钥轮换与重放保护能力。
3. 降低自动化推送成本——同一过滤器兼容 Token、签名和 IP 白名单三种姿势。
4. 任意失败都直接返回 `401`，并在 `LogFilter` 中标记 `risk=HIGH`，方便排障。

实现入口：`src/main/java/com/wangbin/collector/api/filter/AuthFilter.java`

> ⚠️ 鉴权过滤器优先级高于访问日志，因此未通过鉴权的请求不会进入业务层，但仍会写入告警日志。

## 2. 鉴权流程概览

1. `permit-all-paths` 中的 URL（默认 `/health`、`/actuator/**`）直接放行。
2. 请求若携带 `X-Collector-Service` 视为“服务到服务”调用：进入签名校验流程。
3. 否则检查 `X-Collector-Token`，匹配 `ops-tokens` 后放行。
4. 若仍未命中，但请求 IP 在全局或特定服务的 `allow-ips` 中，并且配置了 `allow-ip-fallback=true`，则可降级放行。
5. 以上都不满足时，返回 `401 {"status":"error","message":"missing credential"}`。
6. 通过鉴权的请求会写入 `AuthFilter.ATTR_PRINCIPAL`，方便后续链路或日志引用身份信息。

## 3. 配置入口

```yaml
collector:
  auth:
    enabled: true
    permit-all-paths:
      - /health
      - /actuator/**
    token-header: X-Collector-Token
    service-header: X-Collector-Service
    signature-header: X-Collector-Signature
    timestamp-header: X-Collector-Timestamp
    key-version-header: X-Collector-Key-Version
    max-skew-seconds: 300        # 防重放，单位秒
    ip-allow-list:
      - 10.0.0.0/16
      - 127.0.0.1
    ops-tokens:
      ops-dev-token: "DevOps 团队"
      readonly-tool: "只读脚本"
    service-clients:
      cloud-config:
        default-key: v1
        allow-ip-fallback: true
        allow-ips:
          - 100.64.10.0/24
        keys:
          v1: ${CLOUD_CONFIG_KEY_V1}
          v2: ${CLOUD_CONFIG_KEY_V2}
        require-signature: true
        max-skew-seconds: 120
      qa-pipeline:
        require-signature: false    # 只校验 Header，不做 HMAC
```

字段说明：

- `ops-tokens`：Map 形式，Key 为令牌字符串，Value 为描述（仅用于日志）。
- `service-clients`：`serviceId -> ServiceClient`；`keys` 为 `keyVersion -> secret`，`default-key` 指明默认版本。支持按服务设置 `allow-ips`、`allow-ip-fallback`、`max-skew-seconds`。
- `ip-allow-list`：全局白名单，可写 IPv4/IPv6、CIDR、`*`。

## 4. 运维/调试 Token 用法

发送请求时附带 `X-Collector-Token`：

```bash
curl -H "X-Collector-Token: ops-dev-token" \
     http://edge-gw:8080/api/config/devices
```

命中 `ops-tokens` 即放行；否则返回 `401 invalid ops token`。

## 5. 云端服务签名流程

### 5.1 必填 Header

| Header | 说明 |
| --- | --- |
| `X-Collector-Service` | 服务 ID，对应 `service-clients` 的 Key |
| `X-Collector-Timestamp` | Epoch 毫秒（`System.currentTimeMillis()`），用于防重放 |
| `X-Collector-Signature` | Base64(HmacSHA256(secret, canonicalString)) |
| `X-Collector-Key-Version` | 可选，指定哪一把密钥；未填时使用 `default-key` |

### 5.2 Canonical String 规则

```
canonical = timestamp + "\n"
           + UPPERCASE(method) + "\n"
           + requestPath + "\n"
           + (rawQueryString or "")
```

示例：`POST /api/config/device/dev-1` 无查询参数：

```
timestamp=1775182300000
method=POST
path=/api/config/device/dev-1
query=
canonical=1775182300000\nPOST\n/api/config/device/dev-1\n
signature=Base64(HmacSHA256(secret, canonical))
```

### 5.3 请求样例

```bash
timestamp=$(date +%s%3N)
canonical="${timestamp}\nPOST\n/api/config/device/dev-1\n"
signature=$(printf "%s" "$canonical" | \
  openssl dgst -binary -sha256 -hmac "$CLOUD_CONFIG_KEY_V1" | base64)

curl -X POST http://edge-gw:8080/api/config/device/dev-1 \
  -H "X-Collector-Service: cloud-config" \
  -H "X-Collector-Timestamp: ${timestamp}" \
  -H "X-Collector-Key-Version: v1" \
  -H "X-Collector-Signature: ${signature}" \
  -d '{"deviceName":"pump"}'
```

### 5.4 降级策略

- `allow-ip-fallback=true` 且请求 IP 落在服务或全局 allow list 时，可在签名缺失/不匹配时放行，并在日志中记录 `fallback`。
- 若 `require-signature=false`，只要携带 `X-Collector-Service` 并命中 allow list 即可。

## 6. 密钥滚动

1. 同时配置多把密钥：`keys.v1`、`keys.v2`……
2. 云端请求通过 `X-Collector-Key-Version` 按需选择；服务端未带版本时使用 `default-key` 或 `keys` 中的第一项。
3. 滚动流程建议：
   - 写入新密钥并将其设为 `default-key`。
   - 云端更新 Header，确认成功后删除旧密钥。

## 7. 失败排查

| 报错 | 处理建议 |
| --- | --- |
| `missing credential` | 请求未携带 Token/Service Header，或路径不在白名单 |
| `service client disabled or not found` | 没有匹配的 `service-clients` 条目 |
| `timestamp skew too large` | 集群时间差超出 `max-skew-seconds`，请校准时钟 |
| `signature mismatch` | Canonical 字符串不一致或密钥版本错误，优先打印 `canonical` 调试 |
| `invalid ops token` | 令牌未在 `ops-tokens` 中注册 |

所有失败请求会在 `LogFilter` 中生成 `risk=HIGH` 日志，便于与调用时间对照分析。

## 8. 与其他模块协同

- 配置治理接口详见《07-配置治理接口》，这些接口默认受 `AuthFilter` 保护。
- 访问日志治理（《08-访问日志治理》）记录认证类型、`serviceId` 及请求 ID，禁止记录完整 `token`、密码和设备密钥。
- 需要在业务层获知调用身份时，可读取 `request.getAttribute(AuthFilter.ATTR_PRINCIPAL)`。该属性包含 `type`、`id`、`source`。开启多租户后可进一步映射到租户域。 

## 9. 安全整改计划

详细任务见《16-P0_P1实施任务单与改造方案》的 `SEC-P0-01`。

1. 仓库中出现过的凭据必须轮换，基础配置只保留环境变量占位符。
2. 生产环境发现默认令牌、空密码或示例凭据时拒绝启动。
3. 控制台不得预填或公开运维令牌。
4. 只有来自明确可信代理地址的请求才能使用 `X-Forwarded-For` 等代理头。
5. 服务签名必须覆盖请求体摘要、nonce、时间戳、方法、路径和查询参数。
6. nonce 在有效时间窗内只能使用一次，重放状态存入 Redis。
7. IP 白名单默认不能替代令牌或签名；确需启用时必须限制可信网络。
8. 权限后续拆分为查看、设备控制、配置管理和安全管理，逐步替代单一全权令牌。

安全调整只作用于管理面和服务调用，不得改变现场设备连接和采集线程。
