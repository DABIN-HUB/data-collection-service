# MC 协议后续实施清单

本文档用于承接 [22-MC协议P0实施清单](./22-MC协议P0实施清单.md) 之后的工作，把 `MITSUBISHI_MC` 协议后续能力按 `P1 / P2 / 高风险项` 拆成可执行任务。

目标不是把所有 MC 变体一次性堆进去，而是：

1. 先补齐 P0 的半完成项。
2. 再做对当前项目收益最高的性能和联调能力。
3. 最后处理协议变体和控制类高风险能力。

## 1. 当前结论

结合代码与文档，当前状态可以归纳为：

1. `TCP + MC 3E Binary / 3E ASCII / 4E Binary + 轮询读 + 基础写入` 已实现。
2. 地址解析、类型解析、字节编解码、响应校验已落地。
3. 已接入统一采集框架、缓存切面和后处理链路。
4. 已有地址/编解码/帧构造/响应/读计划/Schema 单元测试。
5. 已有真实 Socket 集成测试覆盖 `3E Binary / 3E ASCII / 4E Binary` 主链路，但仍缺少多系列 PLC 实机验证。

## 1.1 当前实施状态补充

截至当前版本，下面这些事项已经完成：

1. 读计划预构建结果已经参与运行时读取，标准调度子批次会优先复用预构建计划。
2. 协议级批量写已经落地，连续标量点会合并成更少的 MC 写请求。
3. 已有基于 `FakeMcServer` 的真实 Socket 集成测试，覆盖单点读写、批量读写、endCode、超时、异常响应头、异常长度等场景。
4. `D100.3` 与 `additionalConfig.bitIndex` 已落地到读写逻辑。
5. 随机读/写命令已接入采集器策略，但当前仅支持稀疏单字标量字设备点位。
6. `3E_ASCII` 与 `4E_BINARY` 已完成 codec、适配层与集成测试闭环。
7. 设备状态与日志已补充 `frameType/random/fallback/endCode/requestUnitCount` 等诊断信息。

下面这些事项仍未完全完成：

1. `ASCII / 4E` 尚未完成多系列 PLC 实机兼容验证。
2. 随机读/写尚未扩展到多字标量、字符串和更广设备组合。
3. 订阅、控制类命令、UDP 传输仍未实现。
4. 已形成正式验证记录模板和交付验收矩阵，但实机结果仍待现场填写和签署。

## 1.2 更实用的判断表

这张表用于快速判断“当前能力能不能上项目、差距在哪、优先补什么”。

| 使用场景 | 核心要求 | 当前实现判断 | 结论 |
|---|---|---|---|
| 内部单项目，PLC 型号明确，按固定点表轮询采集 | `TCP + 3E Binary/ASCII/4E + 批量读 + 基本写入` | 代码已具备，实机验证不足 | `可用于联调/试运行` |
| 单厂家单项目，以三菱 Q/L/R 系列为主，只做采集不上复杂控制 | `稳定轮询 + 批读优化 + 数据链路接入` | 已基本具备 | `3E Binary 可直接上，ASCII/4E 先做现场验证` |
| 需要做通用采集平台，对外接多现场、多型号 PLC | `多帧型 + 多编码 + 更广兼容 + 更强诊断` | 仍明显不足 | `还不能算平台级` |
| 现场明确要求 `ASCII` 报文 | `ASCII 支持` | 已实现但缺实机验证 | `可联调，不宜直接承诺稳定交付` |
| 现场配置依赖 `4E` 帧或更复杂兼容项 | `4E/多帧型兼容` | 已实现但缺实机验证 | `可联调，不宜直接承诺稳定交付` |
| 点表包含 `D100.3` 这类字内位寻址 | `bit offset` 支持 | 已完成 | `可满足该类点位` |
| 地址高度离散，希望减少请求数 | `random read/write` | 已支持稀疏单字标量字设备 | `部分满足` |
| 需要承担 RUN/STOP、远程控制、复杂写入 | `控制类命令与审计治理` | 未完成 | `不建议直接承担` |
| 目标是做对外通用交付的三菱驱动 | `广泛实机兼容验证` | 未完成 | `当前不够` |

## 1.3 当前版本对外判断口径

建议统一按下面这套口径对内外描述：

1. 如果现场是 `TCP + MC 3E Binary + 固定点位轮询`，当前实现可以承担项目采集任务。
2. 如果现场明确要求 `3E_ASCII` 或 `4E_BINARY`，当前可以进入联调，但交付前必须补实机验证。
3. 如果目标是“本项目可交付”，当前主链路已基本具备，短板主要在兼容性广度和实机验证而不是协议骨架。
4. 如果目标是“平台级通用三菱驱动”，当前能力仍不够，需要继续补更广实机验证、更多命令覆盖和更细兼容矩阵。

## 2. 优先级原则

后续任务按下面的原则排序：

1. 优先补“文档已承诺但实现仍偏基础版”的项。
2. 优先补“能明显提升吞吐、稳定性、排障效率”的项。
3. 对控制类和协议变体能力单独收敛，避免污染当前稳定主链路。

## 3. P1 任务

P1 的目标是补齐当前最值得补的能力，让 `MITSUBISHI_MC` 从“P0 可用”提升为“稳定可联调、性能合理、文档与实现基本完全一致”。

### 3.1 任务一：读计划预构建结果真正参与运行时读取

#### 目标

解决当前 `buildReadPlans(...)` 已实现，但运行时 `readPointsByPlan(...)` 仍重新现算的问题。

#### 现状

1. `CollectionManager.rebuildReadPlans(...)` 已会调用采集器重建读计划。
2. `McCollector.buildReadPlans(...)` 已缓存 `configuredReadPlans`。
3. 但 `McCollector.readPointsByPlan(...)` 仍直接 `planReadPoints(readablePoints)`，没有优先使用已缓存计划。

#### 改动点

1. 修改 `src/main/java/com/wangbin/collector/core/collector/protocol/mc/McCollector.java`
2. 为“设备全量点位读取”与“临时子集读取”区分两条路径：
   - 全量标准轮询：优先使用 `configuredReadPlans`
   - 非标准子集读取：按当前点集动态生成计划
3. 为缓存计划增加最小有效性判断：
   - 点位数是否一致
   - 点位标识集合是否一致
   - 地址缓存是否已失效

#### 验收标准

1. 调度链路触发的标准轮询默认复用预构建计划。
2. 非标准点集读取不受影响。
3. 配置变更后不会复用过期计划。
4. 读取结果与现有行为保持一致。

#### 测试项

1. 新增 `McCollector` 级测试，验证读计划复用分支。
2. 覆盖配置重建后计划刷新。
3. 覆盖临时子集读取走动态计划。

### 3.2 任务二：协议级批量写优化

#### 目标

把当前“API 批量写但协议层逐点循环写”提升为“可合并的连续地址一次协议写入”。

#### 现状

1. `McFrameBuilder.buildBatchWrite(...)` 已具备单次批量写帧构造能力。
2. `McCollector.doWritePoints(...)` 目前仍按点循环调用 `doWritePoint(...)`。

#### 改动点

1. 新增 `src/main/java/com/wangbin/collector/core/collector/protocol/mc/plan/McWritePlan.java`
2. 新增 `src/main/java/com/wangbin/collector/core/collector/protocol/mc/plan/McWritePlanItem.java`
3. 新增 `src/main/java/com/wangbin/collector/core/collector/protocol/mc/plan/McWritePlanBuilder.java`
4. 在 `McCollector.doWritePoints(...)` 中：
   - 先按地址连续性、设备类型、单位类型、容量上限做分段
   - 对可合并点位构造一次写请求
   - 对不可合并点位或失败分段回退单点写

#### 设计约束

1. 只做全量覆盖写，不做 read-modify-write。
2. 只合并同设备区、同单位类型、连续地址段。
3. 数组点先纳入设计，但如果复杂度过高，P1 可先只支持标量点合并。

#### 验收标准

1. 连续 `D` 区或 `M` 区写入能合并成更少的请求。
2. 任一分段写失败时，不影响其他分段结果返回。
3. 整体返回结果仍按点位粒度输出。
4. 日志中可观测合并前后请求数量。

#### 测试项

1. 写计划构造测试。
2. 连续地址合并测试。
3. 超容量拆分测试。
4. 单点 fallback 测试。

### 3.3 任务三：MC 协议集成测试与联调脚手架

#### 目标

补齐当前只有单元测试、缺少端到端 request-response 联调验证的问题。

#### 改动点

1. 新增测试辅助类：
   - `FakeMcServer`
   - `FakeMcRequestRouter`
   - `FakeMcMemoryModel`
2. 在 `src/test/java/com/wangbin/collector/core/collector/protocol/mc/` 下新增集成测试：
   - 单点读
   - 批量读
   - 单点写
   - 批量写
   - endCode 错误
   - 超时
   - 非法响应长度

#### 范围

1. 先支持 3E Binary over TCP。
2. 先覆盖 `M/D/X/Y/R/W/ZR` 的基础场景。
3. 先不要求真实 PLC 参与。

#### 验收标准

1. 测试中真实走 Socket request-response。
2. 能验证 `MitsubishiMcConnectionAdapter` 与 `McCollector` 的联动。
3. 关键异常路径有自动化用例。

### 3.4 任务四：可观测性增强

#### 目标

把 MC 相关问题从“只能看异常堆栈”提升到“有明确协议级诊断信息”。

#### 改动点

1. 在 `McCollector` 增加调试级日志：
   - 读计划条数
   - 分段起止地址
   - 请求单位数
   - fallback 次数
2. 在 `MitsubishiMcConnectionAdapter` 增加连接级日志：
   - 建连目标
   - 超时设置
   - 响应长度异常
3. 在设备状态接口中补充：
   - `configuredReadBatchCount`
   - `lastFallbackCount`
   - `lastMcEndCode`
   - `lastRequestUnitCount`

#### 验收标准

1. 现场排障时能明确区分：
   - 连接失败
   - 响应错误码
   - 长度错误
   - 单批失败后 fallback
2. 不输出敏感或过量二进制日志。

### 3.5 任务四当前实施拆分

本轮按下面方式落地，避免一次性做成“大而全”：

1. 先补 `McCollector` 级状态输出和关键 fallback 计数。
2. 再补 `MitsubishiMcConnectionAdapter` 级响应长度、超时、建连目标等连接诊断。
3. endCode、请求单位数、读写批次信息优先进入设备状态和 debug 日志，不做原始二进制报文完整落盘。

## 4. P2 任务

P2 的目标是扩展协议能力和表达能力，但不要求全部落到当前默认主路径。

### 4.1 任务五：位内偏移地址支持

#### 目标

支持类似 `D100.3` 的位内偏移读写。

#### 改动点

1. 扩展 `McAddress`，增加 `bitIndex` 概念。
2. 扩展 `McAddressParser` 支持 `D100.3` 语法。
3. 约束此类点位只能映射为 `BOOL`。
4. 读取逻辑：
   - 先读取字设备原值
   - 再按位提取
5. 写入逻辑：
   - 执行 read-modify-write
   - 仅改目标位

#### 风险说明

1. 写入不再是纯幂等覆盖写。
2. 并发写同一字地址存在竞争窗口。

#### 验收标准

1. `D100.3` 可被解析。
2. 读写结果符合位操作预期。
3. 文档中明确 read-modify-write 风险。

### 4.2 任务六：随机读写命令支持

#### 目标

支持 MC 的随机读写类能力，用于地址不连续场景下降低请求数。

#### 改动点

1. 在 `codec` 层新增随机读写帧构造。
2. 在 `response` 层新增对应解析。
3. 在 `McCollector` 中增加策略选择：
   - 连续地址优先 batch read/write
   - 离散少量地址可选 random read/write

#### 验收标准

1. 在离散地址场景下可减少请求数量。
2. 不影响现有连续块读取逻辑。
3. 命令选择策略可配置或可灰度。

#### 当前实施状态

1. `codec` 层和 `McCollector` 策略层已落地。
2. 当前已支持稀疏、单字、标量、字设备点位的随机读/写。
3. 多字标量、字符串和更广设备组合仍不在当前支持范围。

### 4.3 任务七：伪订阅模式

#### 目标

提供“订阅式使用体验”，但底层仍基于轮询。

#### 实现方式

1. 不实现协议原生推送。
2. 在 `doSubscribe(...)` 中登记点位集合和策略。
3. 由调度器周期轮询这些点位。
4. 值变化后通过现有缓存/上报/实时流链路下发。

#### 设计要求

1. 文档和接口必须明确标注为“轮询模拟订阅”。
2. 不得伪装成协议原生订阅能力。

#### 验收标准

1. 外部调用方可使用订阅接口管理点位集合。
2. 变化值可稳定进入后处理链路。
3. 不破坏现有轮询主流程。

### 4.4 任务八：数组语义增强

#### 目标

把当前数组点“协议透传”提升为“可选进入更多平台处理能力”。

#### 可选方向

1. 支持数组元素级缩放。
2. 支持数组长度校验。
3. 支持数组整体质量状态。
4. 支持数组写入前的元素级类型检查。

#### 约束

1. 默认仍保持当前透传模式，避免影响既有行为。
2. 新行为应通过明确配置开关启用。

## 5. 高风险项

这部分不是不能做，而是必须单独评审、单独灰度、单独验收。

### 5.1 高风险项一：远程 RUN/STOP / RESET 控制

#### 风险

1. 会直接影响 PLC 运行状态。
2. 错误操作可能造成现场停机。
3. 权限、审计、幂等、回滚要求远高于普通点位写入。

#### 前置条件

1. 管理接口必须具备强鉴权。
2. 必须有显式开关默认关闭。
3. 必须记录审计日志。
4. 必须限定设备白名单。

#### 建议

1. 不进入普通 `writePoint` 路径。
2. 仅通过受控命令接口触发。
3. 先做 dry-run / simulator 验证。

### 5.2 高风险项二：ASCII 帧支持

#### 风险

1. 会引入另一套帧编码与长度计算逻辑。
2. 容易和当前 Binary 逻辑交叉污染。

#### 建议做法

1. 抽象 `McFrameCodec` 接口。
2. 新增：
   - `Mc3eBinaryFrameCodec`
   - `Mc3eAsciiFrameCodec`
3. `McCollector` 不直接拼帧，统一委托 codec。

#### 当前实施状态

1. `McFrameCodec` 抽象已落地。
2. `Mc3eAsciiFrameCodec`、连接适配层和集成测试已落地。
3. 当前主要缺口从“代码未实现”变成“实机兼容验证未完成”。

### 5.3 高风险项三：4E 帧支持

#### 风险

1. 需要补充序列号、报文跟踪等额外机制。
2. 可能影响适配器的请求响应匹配模型。

#### 建议做法

1. 在完成 codec 抽象后再做。
2. 单独补一套 4E 集成测试。
3. 不和 P1 性能改造并行推进。

#### 当前实施状态

1. `Mc4eBinaryFrameCodec`、序列号生成、连接适配层和集成测试已落地。
2. 当前主要缺口同样是实机兼容验证，而不是代码骨架缺失。

### 5.4 高风险项四：UDP 传输支持

#### 风险

1. 连接模型和异常模型与 TCP 不同。
2. 超时、重试、乱序、丢包都需要额外处理。
3. 现有 `MitsubishiMcConnectionAdapter` 不能直接复用。

#### 建议做法

1. 新增独立 `McUdpConnectionAdapter`。
2. 抽象 request-response transport 层。
3. 在没有明确现场需求前，不建议优先投入。

## 6. 建议实施顺序

建议按下面顺序推进：

1. P1-读计划真实复用
2. P1-协议级批量写
3. P1-集成测试与联调脚手架
4. P1-可观测性增强
5. P2-位内偏移
6. P2-随机读写
7. P2-伪订阅
8. P2-数组语义增强
9. 高风险项按单独立项评审推进
