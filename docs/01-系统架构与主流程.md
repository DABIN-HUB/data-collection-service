# 系统架构与主流程

## 1. 分层架构

- `api`：控制器层，负责启动/停止采集、查询数据、查询监控。
- `core.collector`：协议采集器、调度器、连接管理、设备生命周期。
- `core.processor`：数据质量、规则处理、结果对象组织。
- `core.cache`：多级缓存、缓存切面、实时流写入。
- `core.report`：设备影子聚合、MQTT/HTTP/TCP 上报。
- `monitor`：健康状态与性能指标聚合。

## 2. 设备采集主流程

1. `CollectionService` 接收启动请求，调用 `CollectionScheduler.startDevice(...)`。
2. `CollectionScheduler` 从 `ConfigManager` 读取设备与点位配置。
3. `CollectionManager.registerDevice(...)` 通过 `CollectorFactory` 创建对应协议采集器。
4. 采集器连接设备后，调度器把点位切成批次并分配到时间片。
5. 每个时间片执行批次读取：
   - `collectionManager.readPoints(...)`
   - 采集器 `BaseCollector.readPoints(...)` 中统一做转换 + 质量处理。
6. 处理后的结果进入缓存切面：
   - 写缓存
   - 触发上报聚合
   - 写入 Redis Stream

## 3. 关键核心类

- 调度核心：`core/collector/scheduler/CollectionScheduler`
- 设备管理：`core/collector/manager/CollectionManager`
- 采集器工厂：`core/collector/factory/CollectorFactory`
- 协议抽象：`core/collector/protocol/base/ProtocolCollector` + `BaseCollector`
- 处理结果：`core/processor/ProcessResult`
- 缓存切面：`core/cache/aspect/CollectorDataCacheAspect`

## 4. 关键配置入口

- `collector.scheduler.*`：时间片/超时/动态调整
- `collector.adaptive-collection.*`：自适应采集频率
- `collector.report.*`：上报模型
- `spring.data.redis.*`：Redis 连接
- `spring.data.redis.stream.*`：Redis Stream 实时流

## 5. 2026-07-14 架构边界与演进约束

当前继续采用模块化单体，不在可靠性问题解决前拆分微服务。核心边界固定为配置、调度、协议采集、遥测处理、缓存与历史、告警、云上行和运维管理。

1. 协议采集层只负责连接、地址、编解码、读写和订阅差异。
2. 采集结果在同步出口形成不可变快照，后处理不得回查可变最新状态。
3. 配置使用版本化快照，加载失败保留最后有效版本。
4. 调度定义与单次执行分离，单次超时不得永久取消周期任务。
5. 缓存、实时流、历史、告警和云上行采用独立资源与失败策略。
6. 本地 `deviceId` 贯穿控制台、配置、调度和缓存；云 `productKey + deviceName` 只负责云路由。
7. 云上行采用持久化 Outbox 和 ACK 幂等，不允许采集线程同步等待云端。
8. 运行状态由最后成功采集、连续失败、积压和下游状态共同计算。

详细实施顺序和验收条件见《16-P0_P1实施任务单与改造方案》第 9 章。
